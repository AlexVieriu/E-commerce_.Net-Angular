**D1.** What is the difference between `npm ci` and `npm install`? Which should you use in CI?

<details><summary>Answer</summary>

`npm ci` deletes `node_modules`, installs exactly from `package-lock.json` (never modifies it), is faster, and fails if the lock file is out of sync. `npm install` may update the lock file and resolve newer versions. Always use `npm ci` in CI for reproducible builds.
</details>

<details><summary>Deep Dive</summary>

**Why `npm install` is non-deterministic by design**

`package.json` specifies version ranges using semver syntax:
- `"^1.2.3"` means ">=1.2.3 <2.0.0" — any compatible minor/patch version
- `"~1.2.3"` means ">=1.2.3 <1.3.0" — only patch updates
- `"1.2.3"` means exactly that version

When you run `npm install`, npm resolves these ranges against the current npm registry state and installs the newest matching version. If a package author publishes `1.2.4` yesterday, your CI run today gets `1.2.4` but your local run from last week had `1.2.3`. Same `package.json`, different result — this is the problem.

**`package-lock.json` — the exact snapshot**

The lock file records the exact resolved version, integrity hash (SHA-512), and full dependency tree for every package installed. It's a complete, reproducible snapshot. When `npm ci` runs, it uses ONLY this file — no registry resolution step, no range evaluation. It simply installs what's listed.

```json
// package-lock.json excerpt
{
  "node_modules/lodash": {
    "version": "4.17.21",
    "resolved": "https://registry.npmjs.org/lodash/-/lodash-4.17.21.tgz",
    "integrity": "sha512-v2kDEe57...",
    "license": "MIT"
  }
}
```

The `integrity` field is a checksum — `npm ci` verifies the downloaded tarball matches this hash. This prevents tampered packages from being silently installed.

**The "out of sync" safety check**

If `package.json` specifies a version that contradicts `package-lock.json` (e.g., you manually edited `package.json` but didn't run `npm install` to update the lock file), `npm ci` throws:

```
npm error `npm ci` can only install packages when your package.json and 
package-lock.json are in sync.
```

This is a feature, not a bug — it forces you to commit intentional updates. `npm install` would silently fix the drift and update the lock file, which can hide errors.

**Performance: why `npm ci` is faster in CI**

`npm ci` skips the dependency resolution graph computation (the slowest part of `npm install`). It also benefits from CI caching: cache `node_modules` keyed on the hash of `package-lock.json`. If the lock file hasn't changed, the cache is restored and no install is needed at all.

GitHub Actions example:
```yaml
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}

- run: npm ci
```

**The .NET equivalent**

`npm ci` ≈ `dotnet restore` with a `packages.lock.json` (generated by `<RestoreLockedMode>true</RestoreLockedMode>`). `npm install` ≈ `dotnet restore` without lock mode. For .NET projects, `dotnet restore` itself is fairly deterministic because NuGet resolves to the minimum compatible version, but `packages.lock.json` gives the same guarantee as `package-lock.json`.
</details>

**D2.** What triggers a GitHub Actions workflow? Name three event types.

<details><summary>Answer</summary>

Common triggers:
- **`push`** — on commit to branches or tags.
- **`pull_request`** — on PR opened/synchronized/merged.
- **`workflow_dispatch`** — manual run from the GitHub UI.
- **`schedule`** — cron-based (e.g. nightly builds).
- **`release`** — on a published GitHub release.

Most CI pipelines use `push` + `pull_request` filtered to specific branches.
</details>

<details><summary>Deep Dive</summary>

**`push` — the most fundamental trigger**

Fires when commits are pushed to the repo. Without filters, this triggers on EVERY push to EVERY branch, which is noisy and wastes minutes. Common filters:

```yaml
on:
  push:
    branches: [main, development]   # only these branches
    paths:                          # only when these files change
      - 'src/**'
      - '*.csproj'
    paths-ignore:                   # ignore docs-only changes
      - 'docs/**'
      - '**.md'
    tags:
      - 'v*'                        # trigger on version tags (release workflow)
```

`paths` and `paths-ignore` are mutually exclusive. The filter is OR-based across paths — if any changed file matches, the workflow runs.

**`pull_request` — gating merges**

Fires on PR activity. The key types are:
- `opened` — new PR created
- `synchronize` — new commit pushed to the PR branch (most common)
- `closed` — PR merged or closed (use `if: github.event.pull_request.merged == true` to run only on merges)
- `reopened` — PR reopened

```yaml
on:
  pull_request:
    branches: [main]        # PR targeting main (not FROM main)
    types: [opened, synchronize, reopened]
```

The workflow runs on the **HEAD commit of the PR branch**, in a context that has access to both the PR branch and the base branch for diffing.

**`workflow_dispatch` — manual with parameters**

Adds a "Run workflow" button in the GitHub Actions UI. Can accept inputs:

```yaml
on:
  workflow_dispatch:
    inputs:
      environment:
        description: 'Target environment'
        required: true
        default: 'staging'
        type: choice
        options: [staging, production]
      debug:
        description: 'Enable debug logging'
        type: boolean
        default: false
```

Used for: manual deploys, running one-off maintenance scripts, debugging CI issues.

**`schedule` — cron-based automation**

```yaml
on:
  schedule:
    - cron: '0 3 * * 1'  # Every Monday at 03:00 UTC
```

Common uses: nightly full test suites, dependency vulnerability scans (`dotnet list package --vulnerable`), database backup jobs, stale branch cleanup. Scheduled workflows run on the default branch only.

**`concurrency` — prevent duplicate runs (critical for cost control)**

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

When a new commit is pushed to a PR while the previous run is in progress, the old run is cancelled. Without this, you pay for running 10 parallel CI runs every time a developer pushes a commit flurry. Essential for teams.
</details>

**D3.** What does `needs: [build]` do in a GitHub Actions job?

<details><summary>Answer</summary>

`needs: [build]` creates a dependency — the current job waits until the `build` job completes successfully before running. If `build` fails, dependent jobs are skipped. This enforces sequential execution: build → test → deploy.
</details>

<details><summary>Deep Dive</summary>

**How GitHub Actions schedules jobs by default**

Without `needs`, ALL jobs run in parallel the moment the workflow triggers. GitHub spins up separate runner VMs for each job simultaneously. This is fast and cheap if jobs are independent — but catastrophic if job B requires job A's artifact.

```yaml
# WITHOUT needs — all three start at the same time:
jobs:
  build:    # starts at T=0
  test:     # starts at T=0 (no artifact from build yet → fails)
  deploy:   # starts at T=0 (definitely not ready)
```

**`needs` creates a directed acyclic graph (DAG)**

```yaml
jobs:
  build:
    runs-on: ubuntu-latest

  test-unit:
    needs: [build]      # waits for build

  test-integration:
    needs: [build]      # also waits for build (parallel with test-unit)

  deploy:
    needs: [test-unit, test-integration]  # waits for BOTH
```

This creates the graph:
```
build → test-unit ──┐
      └ test-integration ──┴─→ deploy
```

Unit and integration tests run in parallel (faster!), deploy only runs when both pass.

**Accessing outputs from upstream jobs**

Jobs can pass data to downstream jobs via outputs:

```yaml
jobs:
  build:
    outputs:
      image-tag: ${{ steps.tag.outputs.value }}
    steps:
      - id: tag
        run: echo "value=sha-${{ github.sha }}" >> $GITHUB_OUTPUT

  deploy:
    needs: [build]
    steps:
      - run: echo "Deploying image ${{ needs.build.outputs.image-tag }}"
```

This is how CI pipelines pass Docker image tags, artifact paths, or version numbers between stages.

**Conditional execution on failure**

By default, if a `needs` job fails, the dependent job is SKIPPED (not failed). Use `if:` to override:

```yaml
notify-failure:
  needs: [deploy]
  if: failure()  # runs ONLY if deploy failed
  steps:
    - run: curl -X POST $SLACK_WEBHOOK -d '{"text":"Deploy failed!"}'

cleanup:
  needs: [deploy]
  if: always()  # runs regardless of deploy result
  steps:
    - run: rm -rf /tmp/build-artifacts
```

**`needs` with matrix jobs**

If `build` uses a matrix strategy (e.g., testing on multiple OS or .NET versions), `needs: [build]` waits for ALL matrix instances to complete successfully before starting. If any matrix instance fails, downstream jobs are skipped.
</details>

**D4.** In the .NET config provider chain, if the same key exists in `appsettings.json` and User Secrets, which wins? Why?

<details><summary>Answer</summary>

User Secrets wins. .NET config uses a last-wins strategy — providers registered later override earlier ones. Default order: `appsettings.json` → `appsettings.{Environment}.json` → User Secrets → Environment Variables → Command Line.
</details>

<details><summary>Deep Dive</summary>

**How the config system is built — under the hood**

`IConfiguration` is backed by a `ConfigurationRoot` which holds an ordered list of `IConfigurationProvider` instances. When you access a key, it walks the provider list in REVERSE (from last to first) and returns the first non-null value found. This is the "last wins" rule.

The `WebApplication.CreateBuilder()` default setup calls these in order (each one added after the previous = higher priority):

```
1. appsettings.json              (JsonConfigurationProvider)
2. appsettings.{Environment}.json (JsonConfigurationProvider)
3. User Secrets                   (UserSecretsConfigurationProvider) — only in Development
4. Environment Variables          (EnvironmentVariablesConfigurationProvider)
5. Command Line Arguments         (CommandLineConfigurationProvider)
```

The key insight: if you add `AddAzureKeyVault()` after this setup in `Program.cs`, Key Vault becomes priority #6 and overrides everything — including environment variables. Be intentional about where you add custom providers.

**Key flattening and the `:` separator**

Nested JSON configuration:
```json
{
  "ConnectionStrings": {
    "Default": "Server=localhost;Database=skinet"
  },
  "Stripe": {
    "SecretKey": "sk_test_..."
  }
}
```

is stored in the config system as flat key-value pairs with `:` as separator:
- `"ConnectionStrings:Default"` → `"Server=localhost;Database=skinet"`
- `"Stripe:SecretKey"` → `"sk_test_..."`

**Environment variables and the `__` trick**

On Linux/Docker, `:` in environment variable names is invalid (it's a PATH separator). .NET accepts `__` (double underscore) as the `:` equivalent:

```bash
# Linux/Docker:
export ConnectionStrings__Default="Server=prod-db;Database=skinet"

# Windows (colon works fine):
set ConnectionStrings:Default=Server=prod-db;Database=skinet
```

The config system normalizes both to the same key. This is how you configure .NET apps in Kubernetes — environment variables use `__` for nested keys.

**User Secrets — where the file actually lives**

User Secrets are stored in:
- **Windows**: `%APPDATA%\Microsoft\UserSecrets\<userSecretsId>\secrets.json`
- **Linux/Mac**: `~/.microsoft/usersecrets/<userSecretsId>/secrets.json`

The `<userSecretsId>` is a GUID in your `.csproj`:
```xml
<PropertyGroup>
  <UserSecretsId>5c23b6f8-4d2a-4e7b-9c1a-23456789abcd</UserSecretsId>
</PropertyGroup>
```

The file is never in your project directory — it's entirely outside the repo, which is why it's safe.

**Building on top of the chain: environment-specific Key Vault**

A real production setup:

```csharp
var builder = WebApplication.CreateBuilder(args);

// Add Key Vault last — it wins over everything
if (builder.Environment.IsProduction())
{
    var keyVaultUri = new Uri(builder.Configuration["KeyVaultUri"]!);
    builder.Configuration.AddAzureKeyVault(keyVaultUri, new DefaultAzureCredential());
}
```

The Key Vault URI itself comes from `appsettings.Production.json` (committed, not secret). The secrets inside Key Vault override everything. This way, local dev uses User Secrets and prod uses Key Vault — no code change needed.
</details>

**D5.** Your CI pipeline has three jobs: `build`, `test`, `deploy`. The `deploy` job runs even when `test` fails. What's wrong? Write the corrected YAML.

<details><summary>Answer</summary>

The original is missing `needs` directives — without them, all jobs run in parallel.

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: dotnet build

  test:
    needs: [build]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: dotnet test

  deploy:
    needs: [test]
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying..."
```

Now if build fails, test is skipped. If test fails, deploy is skipped.
</details>

<details><summary>Deep Dive</summary>

**Storing and accessing build artifacts between jobs**

When `test` completes, any compiled binaries (in `bin/` directory) are on the job's runner VM. When `deploy` starts on a fresh runner VM, those artifacts are gone. You must either:

1. Re-checkout and re-build (wasteful).
2. Upload artifacts in `build`, download in downstream jobs:

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: dotnet build --configuration Release
      - uses: actions/upload-artifact@v4
        with:
          name: build-artifacts
          path: bin/Release/

  deploy:
    needs: [build]
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: build-artifacts
          path: bin/Release/
      - run: dotnet publish bin/Release/MyApp.dll
```

Artifacts are typically 50MB–500MB. GitHub Actions gives 5GB free storage per repo, so use carefully.

**Conditional execution with job outputs**

```yaml
jobs:
  build:
    outputs:
      version: ${{ steps.version.outputs.number }}
    steps:
      - id: version
        run: echo "number=1.2.3" >> $GITHUB_OUTPUT

  deploy:
    needs: [build]
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying version ${{ needs.build.outputs.version }}"
```

Outputs pass data between jobs without uploading files.
</details>

**D6.** You have secrets stored in: `appsettings.json`, `appsettings.Development.json`, environment variables, User Secrets, and Azure Key Vault. Draw the provider chain. For each: when used, what belongs there, committed to git?

<details><summary>Answer</summary>

Chain (last wins):
1. `appsettings.json` — base config (URLs, feature flags). **Committed**.
2. `appsettings.{Env}.json` — env-specific overrides (logging levels). **Committed**.
3. User Secrets — local dev secrets (API keys). **NOT committed**.
4. Env vars — CI/CD, Docker config. **NOT committed**.
5. Key Vault — production secrets (connection strings, keys). **NOT committed**.

Rule: anything secret → User Secrets locally, Key Vault in prod. Never commit secrets.
</details>

<details><summary>Deep Dive</summary>

**Why "last wins" matters for testing**

In tests, you might override a setting via environment variable or a test configuration provider:

```csharp
[Theory]
[InlineData("Production", true)]
[InlineData("Development", false)]
public void LoggingBehavior(string env, bool expectedVerbose)
{
    var config = new ConfigurationBuilder()
        .AddJsonFile("appsettings.json")
        .AddJsonFile($"appsettings.{env}.json")
        .AddInMemoryCollection(new[] { new KeyValuePair<string, string>("Logging:IsVerbose", expectedVerbose.ToString()) })
        .Build();
    
    // In-memory collection is last, so it wins — test controls the value
}
```

**Docker and 12-Factor App**

In containerized environments, all environment-specific config comes from environment variables (set in `docker run -e` or Kubernetes `env:`). Never bake config into the image.

```dockerfile
FROM mcr.microsoft.com/dotnet/aspnet:8.0
COPY bin/Release/net8.0/publish /app
WORKDIR /app
ENTRYPOINT ["dotnet", "MyApp.dll"]
```

At runtime:
```bash
docker run -e "ConnectionStrings:Default=Server=prod-db" -e "Stripe:SecretKey=$STRIPE_KEY" MyApp:latest
```
</details>

**D7.** What is OIDC federation in the context of GitHub Actions and Azure? Why is it better than storing a client secret in GitHub Secrets?

<details><summary>Answer</summary>

OIDC federation lets GitHub Actions get a short-lived token from Azure AD per workflow run — no stored secrets. GitHub presents a JWT to Azure, Azure validates it against configured trust (repo, branch, environment), and issues an access token.

Better than stored client secrets because:
- No secret to rotate, leak, or expire.
- Tokens are short-lived (minutes).
- Scoped to specific repos/branches — forks can't abuse it.
- All token requests are audit-logged in Azure AD.

Setup: Azure AD app registration + federated credential pointing to GitHub's OIDC provider.
</details>

<details><summary>Deep Dive</summary>

**Trust relationship — only THIS repo can authenticate**

The federated credential in Azure AD specifies:
```json
{
  "issuer": "https://token.actions.githubusercontent.com",
  "subject": "repo:my-org/my-repo:ref:refs/heads/main",
  "audience": "api://AzureADTokenExchange"
}
```

Only commits to the `main` branch of `my-org/my-repo` can request tokens — forks, other repos, and other branches are denied. This prevents a leaked credential file from being exploited — the credential is replaced by a trust relationship that's inherently scoped.

**How GitHub Actions uses it**

In the workflow:
```yaml
jobs:
  deploy:
    environment: production
    permissions:
      id-token: write
    steps:
      - uses: azure/login@v1
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
```

The `azure/login` action:
1. Generates a JWT from the workflow context (repo, branch, commit).
2. Sends it to Azure AD.
3. Azure validates the JWT signature against GitHub's public key.
4. Azure checks if the subject matches the federated credential.
5. If all pass, Azure issues a temporary access token.
6. The action uses that token to authenticate to Azure.

No client secret is ever stored in GitHub — it's only in Azure AD's configuration.
</details>

**D8.** Your `dotnet test` passes locally but fails on CI. The error is "Unable to find testhost." Name three common causes and how you'd debug each.

<details><summary>Answer</summary>

1. Missing `Microsoft.NET.Test.Sdk` NuGet — required for test discovery. Check `.csproj`.
2. SDK version mismatch — CI has older SDK that doesn't support the target framework. Fix: add `global.json` or specify SDK version in CI.
3. Runtime identifier mismatch — test project targets a framework not installed on CI agent.

Debug: run `dotnet test --verbosity detailed`, check `dotnet --info` on CI, ensure all test projects reference the SDK package.
</details>

<details><summary>Deep Dive</summary>

**Test discovery — how dotnet test finds tests**

`dotnet test` uses the test SDK to discover test methods (decorated with `[Fact]` or `[Theory]`). Discovery and execution happen in a separate `testhost` process (part of `Microsoft.NET.Test.Sdk`). If the test SDK NuGet is missing, the testhost binary isn't produced and discovery fails with "Unable to find testhost."

The test SDK also includes the test adapter (for xUnit, NUnit, MSTest) — it translates test methods into executable items.

**SDK version compatibility**

If CI has `.NET 8.0` SDK but the test project targets `net9.0`, the SDK can't build it. The error message is cryptic ("Unable to find testhost" or "target framework not supported"). The fix: ensure CI has the right SDK version.

Use `global.json` to pin the SDK version across the repo:
```json
{
  "sdk": { "version": "8.0.100" }
}
```

On CI, the action `setup-dotnet@v4` installs the right SDK automatically if `global.json` exists.

**Test logger and console output**

To debug test discovery, add the detailed logger:
```bash
dotnet test --logger "console;verbosity=detailed"
```

This shows which tests were discovered and which failed.
</details>

**D9.** You rotate the Stripe secret key in Azure Key Vault. Your production app still uses the old key. Why? How do you fix it without downtime?

<details><summary>Answer</summary>

- **Root cause** — Key Vault config is loaded once at startup and cached. The app doesn't poll for changes.
- **Fix** — set `AzureKeyVaultConfigurationOptions.ReloadInterval` (e.g. 5 min); use `IOptionsMonitor<StripeSettings>` to receive live updates without restart.
- **Zero-downtime rotation** — add the new key in Key Vault, wait for the reload interval to propagate, then deactivate the old key. Or use a blue-green deployment swap.
</details>

<details><summary>Deep Dive</summary>

**Polling vs push for config changes**

The Azure Key Vault config provider polls on an interval (default 1 minute for App Configuration, customizable for Key Vault). Between polls, the app uses the cached value. If you rotate a secret and the poll hasn't fired yet, the app continues using the old key.

The polling interval is a tradeoff: shorter intervals = faster updates but higher API calls and costs. Longer intervals = slower updates but cheaper.

For secrets that rotate frequently (API keys, database passwords), set a 5–10 minute interval. For less critical settings, 30 minutes is fine.

**Blue-green deployment for zero-downtime**

Deploy a second instance with the new key, warm it up, then switch traffic to it. The old instance shuts down gracefully. During the switch, there's a moment where traffic may split between both versions, but both have valid keys.
</details>

**D10.** CI ran `dotnet test` and 12 tests failed on the first push — but they passed locally. What categories of bugs cause this and how do you investigate?

<details><summary>Answer</summary>

Categories:
1. **Environment-dependent**: hardcoded paths (`C:\...`), timezone assertions, culture-specific string formatting.
2. **Missing dependencies**: database not available, no test data seeded, missing env vars.
3. **Race conditions**: async tests with timing assumptions, tests sharing static state.
4. **Test ordering**: tests depend on execution order or shared mutable state.
5. **Resource conflicts**: port conflicts, file locks.

Debug: read CI log line by line, run locally with `--verbosity detailed`, reproduce in Docker.
</details>

<details><summary>Deep Dive</summary>

**The hardcoded path trap**

```csharp
[Fact]
public void ParseConfigFile()
{
    var content = File.ReadAllText("C:\\dev\\myapp\\config.json");  // FAILS on CI (Linux) and Mac
    Assert.NotNull(content);
}
```

CI typically runs on Linux (Ubuntu). Windows paths don't exist. The fix: use relative paths or `Path.Combine`:

```csharp
var configPath = Path.Combine(AppDomain.CurrentDomain.BaseDirectory, "config.json");
var content = File.ReadAllText(configPath);
```

**Culture-specific failures**

```csharp
[Fact]
public void ParsePrice()
{
    var price = decimal.Parse("1.50");  // Uses CurrentCulture — fails in fr-FR (1,50)
    Assert.Equal(1.5m, price);
}
```

Fix: parse with an invariant culture:
```csharp
var price = decimal.Parse("1.50", CultureInfo.InvariantCulture);
```

**Timezone bugs**

```csharp
[Fact]
public void TimestampTest()
{
    var now = DateTime.Now;
    var utcNow = DateTime.UtcNow;
    Assert.Equal(now, utcNow);  // FAILS if CI is in a different timezone
}
```

Always use `DateTime.UtcNow` in tests, not `DateTime.Now`.

**Docker reproduction**

To reproduce CI failures locally, run the test in Docker with the same image CI uses:

```bash
docker run --rm -v $(pwd):/src mcr.microsoft.com/dotnet/sdk:8.0 \
  sh -c "cd /src && dotnet test --verbosity detailed"
```

This replicates the CI environment exactly.
</details>

**D11.** Your `dotnet test` in CI passes but `ng build` fails. The deploy job still runs. What's missing?

<details><summary>Answer</summary>

The deploy job only depends on the backend test job (or has no `needs` at all).

Fix: add separate `build-frontend` job with `ng build`, and make `deploy` need BOTH:

```yaml
deploy:
  needs: [test-backend, build-frontend]
```

If either fails, deploy is skipped.
</details>

<details><summary>Deep Dive</summary>

**Separate build for frontend and backend**

Full-stack apps need both to succeed before deploy. If only the backend test is a dependency, the frontend could fail silently and deploy would proceed with a broken frontend.

```yaml
jobs:
  build-backend:
    steps: [checkout, dotnet build]
  
  build-frontend:
    steps: [checkout, npm ci, npm run build]
  
  test-backend:
    needs: [build-backend]
    steps: [dotnet test]
  
  deploy:
    needs: [test-backend, build-frontend]
    steps: [deploy-to-azure]
```

This ensures both pipelines are validated before deploying.
</details>

### HARD

**D12.** Design a CI/CD pipeline for an e-commerce app with: staging and production environments, database migrations, feature flags, rollback capability, and zero-downtime deployment. Include the YAML structure and explain each step.

<details><summary>Answer</summary>

Pipeline: build → test → deploy-staging (auto on `develop`) → deploy-prod (manual approval on `main`).

DB migrations run as a separate step BEFORE deploy — must be backward-compatible (add columns, not rename). Feature flags (LaunchDarkly/Azure App Config) decouple deploy from release.

Zero-downtime: Azure deployment slots — deploy to staging slot, warm up, swap to production. Rollback: swap back.

Structure migrations to be additive so rollback doesn't break the DB.

```yaml
jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps: [checkout, build, test]

  deploy-staging:
    needs: [build-and-test]
    if: github.ref == 'refs/heads/develop'
    environment: staging
    steps: [migrate-staging-db, deploy-to-staging-slot]

  deploy-prod:
    needs: [build-and-test]
    if: github.ref == 'refs/heads/main'
    environment: production  # requires manual approval
    steps: [migrate-prod-db, deploy-to-prod-slot, swap-slots]
```
</details>

<details><summary>Deep Dive</summary>

**Backward-compatible migrations — the critical rule**

A production deployment must never break existing code. When deploying a new version, the old version is still running (on other instances) until the swap.

```sql
-- GOOD: additive
ALTER TABLE Orders ADD COLUMN NewField INT NULL;

-- BAD: breaking
ALTER TABLE Orders DROP COLUMN OldField;  -- old code still reads this → error
```

Run the migration BEFORE deploying the new code:

```yaml
- name: Run DB migrations
  run: dotnet ef database update --context AppDb
  
- name: Deploy app (which uses NewField)
  run: az webapp up ...
```

Old instances still see the old schema. Migration has already added NewField. New instances see NewField and use it. No downtime.

**Feature flags for phased rollout**

Deploy all instances immediately, but use a feature flag to enable the new code:

```csharp
if (featureToggle.IsEnabled("NewCheckoutFlow"))
{
    return new CheckoutService().ProcessAsync();  // new code
}
else
{
    return new LegacyCheckoutService().ProcessAsync();  // old code
}
```

Initially, the flag is off. All traffic uses old code. Gradually enable for 10%, 50%, 100% of users. If bugs appear, disable the flag instantly (no redeploy needed).

**Azure deployment slots for zero-downtime**

Production has two slots: blue (running) and green (idle).
1. Deploy to green.
2. Warm up green (smoke tests, load tests).
3. Swap: traffic switches to green, blue becomes idle.
4. If issues, swap back to blue instantly.

This is pure infrastructure — no code changes needed.
</details>

**D14.** A junior developer accidentally pushes a secret to GitHub. The secret is now in the git history. What are the immediate steps (first 5 minutes)? What are the follow-up steps? Why is `git rebase` not enough?

<details><summary>Answer</summary>

**First 5 minutes:** ROTATE THE SECRET immediately (new API key, new password). Revoke the old one. The secret is compromised the moment it's pushed — bots scrape GitHub in seconds.

**Follow-up:** use BFG Repo-Cleaner or `git filter-repo` to remove from history, force-push, have all contributors re-clone.

**Why rebase isn't enough:** the old commits exist in reflog, forks, GitHub's cache, any CI that fetched the repo, and GitHub's event API.

**Prevention:** `.gitignore`, `git-secrets` pre-commit hooks, GitHub secret scanning.
</details>

<details><summary>Deep Dive</summary>

**Why bots find secrets in seconds**

GitHub has public event streams. Minutes after you push, crawlers have indexed the commit. If the commit contains an API key, bots try it against the service. A Stripe key can be charged within seconds.

**BFG Repo-Cleaner vs git filter-repo**

Both rewrite history to remove files/content. BFG is simpler, focused on removing secrets:

```bash
bfg --replace-text passwords.txt repo.git
```

Then force-push:

```bash
git push origin --force-with-lease --all
git push origin --force-with-lease --tags
```

All contributors must re-clone (old clones have the old commits in reflog).

**Git secrets hook — the prevention**

Install pre-commit hook that blocks commits containing patterns:

```bash
brew install git-secrets
git secrets --install
git secrets --register-aws
git secrets --add 'sk_live_'  # Stripe pattern
```

Now any commit with `sk_live_` is rejected before pushing.

**GitHub secret scanning**

GitHub automatically scans pushes for known patterns (AWS keys, Stripe keys, etc.). If found, it sends alerts and revokes some keys automatically. Not foolproof, but catches obvious mistakes.
</details>

**D15.** Your team wants to add a staging environment. Staging deploys on merge to `development`, production on merge to `main`. Both use Key Vault but with different secrets. Design the pipeline and config changes.

<details><summary>Answer</summary>

**Pipeline:** two GitHub environments (`staging`, `production`) with separate OIDC credentials. Two Key Vaults: `kv-myapp-staging`, `kv-myapp-prod`.

Workflow: push to `development` → build → test → deploy to staging (auto). PR to `main` → build → test → deploy to prod (requires approval).

Each deploy job uses `environment:` to select the right secrets. Config: `appsettings.Staging.json` + staging Key Vault, `appsettings.Production.json` + prod Key Vault. `ASPNETCORE_ENVIRONMENT` set per deployment slot.
</details>

<details><summary>Deep Dive</summary>

**Separate environments isolate blast radius**

If a script breaks production, staging is unaffected. Developers deploy to staging daily, production is manually approved. Different Keys Vaults mean staging secrets (test keys, lower quotas) don't leak into prod.

**OIDC federation per environment**

Staging and prod have different OIDC credentials. The GitHub Actions job specifies which environment:

```yaml
deploy-staging:
  environment: staging
  steps:
    - uses: azure/login@v1
      with:
        client-id: ${{ secrets.AZURE_CLIENT_ID_STAGING }}
        tenant-id: ${{ secrets.AZURE_TENANT_ID }}
        subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID_STAGING }}
```

Each environment has its own secrets in GitHub. Staging secrets are useless for production (different tenant, different subscription).

**ASPNETCORE_ENVIRONMENT controls behavior**

Setting `ASPNETCORE_ENVIRONMENT=Staging` in the deployment slot loads `appsettings.Staging.json`, connects to staging Key Vault, uses test database, etc. Same app binary, different behavior by environment.
</details>

**D16.** You need to add secret rotation without downtime. The current setup loads secrets at startup only. Design a solution. Compare: polling `ReloadInterval`, blue-green deploy, and `IOptionsSnapshot<T>`.

<details><summary>Answer</summary>

1. **`ReloadInterval` (e.g., 5min) + `IOptionsMonitor<T>`**: provider polls Key Vault in background, `IOptionsMonitor.OnChange` updates cached values. Simple, no restart needed. Risk: up to N minutes of stale secrets.

2. **Blue-green deploy**: deploy new instance with fresh config, swap traffic. Zero stale time but requires a deployment.

3. **`IOptionsSnapshot<T>`**: Scoped, re-reads from providers per request — but only sees changes if the provider has already reloaded.

**Best approach:** `ReloadInterval` + `IOptionsMonitor<T>` for live rotation + blue-green for major changes.
</details>
