The repository executes specs against any EF provider.</p><pre class="p"><code>// Without spec — query in service (anti-pattern)<br>var products = await _context.Products<br>    .Where(p =&gt; p.Name.Contains(search) &amp;&amp; brands.Contains(p.Brand))<br>    .OrderBy(p =&gt; p.Price).Skip(skip).Take(take).ToListAsync();<br><br>// With spec — query encapsulated (correct)<br>var spec = new ProductSpecification(new ProductSpecParams { Search = search, Brands = brands });<br>var products = await _repo.GetAllAsync(spec);</code></pre><p><b>Why specs:</b></p><ol><li><b>Testable in isolation</b> — <code class="c">ProductSpecification</code> is a plain C# object; verify filter logic without EF</li><li><b>Single source of truth</b> — one spec class, not 5 copies of the same LINQ across different services</li><li><b>Repository stays generic</b> — <code class="c">IGenericRepository&lt;T&gt;</code> has ~6 methods covering all entities. Without specs, you'd need <code class="c">GetProductsByBrand</code>, <code class="c">GetProductsByBrandAndSearch</code>, etc. — combinatorial explosion.</li><li><b>Projection support</b> — <code class="c">BaseSpecification&lt;T, TResult&gt;</code> maps entities to DTOs in the database, avoiding over-fetching</li></ol></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"Add <code class="c">GetProductsByBrand(string brand)</code> to <code class="c">IProductRepository</code>." N entity types × M query variations = an unmanageable interface that changes with every business requirement.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning that specifications can be <b>composed</b> — <code class="c">ProductSpecification</code> can accept multiple optional filters in one constructor. The alternative (separate methods per filter combination) grows exponentially and creates N×M method counts for N filters and M sort options. Specs keep the combinatorial complexity in one place.</p></div></div>

# D3 — [MEDIUM][HIGH] This spec crashes on SQL Server but works fine in SQLite. Find the bug:
# ────────────────────────────────────────────────────────────────────────────
<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><p><b>Bug:</b> casting <code class="c">decimal</code> to <code class="c">double</code> inside a LINQ expression that EF Core translates to SQL.</p><p><b>What happens per provider:</b></p><ul><li><b>SQLite (dev):</b> stores decimals as <code class="c">REAL</code> (float). EF's SQLite provider handles the cast silently. Tests pass, sort order appears correct.</li><li><b>SQL Server (prod):</b> EF generates <code class="c">CAST(Price AS float)</code>. SQL Server executes the cast: <code class="c">9.995</code> becomes <code class="c">9.994999...</code> in floating point. Sort order can change — products with prices that round differently as floats swap positions.</li></ul><p><b>Fix:</b></p><pre class="p"><code>AddOrderByAsc(x =&gt; (object)x.Price);</code></pre><p><code class="c">(object)</code> satisfies the <code class="c">Expression&lt;Func&lt;T, object&gt;&gt;</code> signature without any type conversion. EF Core translates this to <code class="c">ORDER BY Price</code> with no <code class="c">CAST</code> — the decimal column sorts precisely.</p><p><b>Production consequence:</b> product price ordering silently changes in production for items with prices like <code class="c">$9.995</code> and <code class="c">$10.004</code>. Subtle, hard to reproduce, causes customer complaints about "wrong" sort order.</p></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"Cast to <code class="c">decimal</code> explicitly instead." <code class="c">decimal</code> is already the column type — an explicit <code class="c">(decimal)</code> cast is a no-op in C# but still generates a <code class="c">CAST</code> in some providers. <code class="c">(object)</code> is the correct pattern precisely because it avoids any SQL-level cast.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning this is explicitly documented in the project's Common Mistakes. The broader lesson: any cast or method call inside a LINQ <code class="c">Expression&lt;...&gt;</code> is translated to SQL — C# semantics don't apply. Always verify expression translation on the production DB provider, not just SQLite.</p></div></div>

# D6 — [HARD][HIGH] The UnitOfWork caches GenericRepository<T> instances in a ConcurrentD...
# ────────────────────────────────────────────────────────────────────────────
<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><p><b>Problem it solves:</b></p><p>Multiple calls to <code class="c">unitOfWork.Repository&lt;Product&gt;()</code> within a single HTTP request return the <b>same repository instance</b> — same underlying <code class="c">DbContext</code>. This ensures:</p><ol><li>All tracked entities across repositories share one change tracker</li><li><code class="c">unitOfWork.Complete()</code> (<code class="c">SaveChangesAsync</code>) atomically commits all pending changes from all repositories</li><li>No "entity already tracked by another context" <code class="c">InvalidOperationException</code></li></ol><p><b>The ConcurrentDictionary pattern:</b></p><pre class="p"><code>private ConcurrentDictionary&lt;string, object&gt; _repos = new();<br><br>public IGenericRepository&lt;T&gt; Repository&lt;T&gt;() where T : BaseEntity<br>    =&gt; (IGenericRepository&lt;T&gt;)_repos.GetOrAdd(typeof(T).Name,<br>        _ =&gt; new GenericRepository&lt;T&gt;(_context));</code></pre><p><b>Singleton bug:</b></p><p><code class="c">DbContext</code> is <b>not thread-safe</b>. If <code class="c">UnitOfWork</code> is <code class="c">Singleton</code>, all concurrent HTTP requests share one <code class="c">DbContext</code> instance:</p><ul><li>Request A reads User #1 → tracked</li><li>Request B reads User #1 simultaneously → <code class="c">InvalidOperationException: "An item with the same key has already been added"</code></li><li>Or: Request A's pending <code class="c">Order</code> gets saved with Request B's <code class="c">Product</code> update — cross-request data corruption</li></ul><p><b>Correct lifetime:</b> <code class="c">AddScoped&lt;IUnitOfWork, UnitOfWork&gt;()</code> — one <code class="c">UnitOfWork</code> (and one <code class="c">DbContext</code>) per HTTP request.</p><p><b>Production consequence:</b> singleton <code class="c">DbContext</code> causes intermittent 500 errors under concurrent load — impossible to reproduce under single-threaded testing, appears only in production or load tests.</p></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"Register as Singleton for performance — creating a new context is expensive." <code class="c">DbContext</code> creation is cheap (it's just object allocation, not a DB connection). The connection pool manages actual SQL connections. Singleton DbContext is a data corruption bug, not a performance optimisation.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning that <code class="c">ConcurrentDictionary</code> is used because <code class="c">UnitOfWork</code> could theoretically be accessed from multiple threads in async code paths (e.g., background services using <code class="c">IServiceScopeFactory</code>). Within a web request, there's typically only one thread, but defensive thread-safety in a dictionary that's cheap to make thread-safe is a reasonable choice.</p></div></div>
