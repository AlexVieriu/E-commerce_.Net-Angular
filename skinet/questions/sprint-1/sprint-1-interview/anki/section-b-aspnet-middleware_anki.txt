S02.01.Easy. What is middleware in ASP.NET Core? How is it different from a filter?	<ul><li><b>Middleware</b> — handles every HTTP request/response (logging, auth, CORS, exceptions); runs before routing; broader scope.</li><li><b>Filters</b> — run only around controller actions (action/result/exception filters); MVC-specific.</li></ul><p>Order: <code>Middleware pipeline → Routing → Filters → Action</code>.</p>
S02.02.Easy. What is the difference between <code>AddScoped</code>, <code>AddTransient</code>, and <code>AddSingleton</code>? Give a real-world example for each.	<ul><li><b><code>Singleton</code></b> — one instance for the entire app lifetime (e.g. <code>IMemoryCache</code>, config service).</li><li><b><code>Scoped</code></b> — one instance per HTTP request (e.g. <code>DbContext</code>, <code>ICurrentUser</code>).</li><li><b><code>Transient</code></b> — new instance every injection (e.g. lightweight stateless services, validators).</li></ul><p>Rule: <code>DbContext</code> is almost always <code>Scoped</code>.</p>
S02.03.Easy. What does <code>app.UseAuthentication()</code> do? What happens if you put it AFTER <code>app.UseAuthorization()</code> in the pipeline?	<ul><li><b><code>UseAuthentication</code></b> — reads the token/cookie and populates <code>HttpContext.User</code>.</li><li><b><code>UseAuthorization</code></b> — checks <code>[Authorize]</code> attributes against that user.</li></ul><p>If auth comes <b>after</b> authorization, the user identity isn't set yet — every <code>[Authorize]</code> endpoint returns 401. Order matters: Authentication first, then Authorization.</p>
S02.04.Easy. What does <code>[ApiController]</code> attribute do on a controller? Name at least three behaviors it enables.	<li>Automatic model validation — returns 400 if <code>ModelState</code> is invalid (no manual check needed).</li><li>Binding source inference — complex types from <code>[FromBody]</code>, simple types from <code>[FromQuery]</code>/<code>[FromRoute]</code>.</li><li>Problem details for errors (RFC 7807).</li><p>Also: requires <code>[Route]</code> attribute, disables <code>IActionResult</code> null returns.</p>
S02.05.Medium. Your API returns 500 on every request. In production, how do you handle exceptions without leaking internals? Design an exception handling middleware.	<ul><li>Wrap <code>await next()</code> in try/catch.</li><li>Catch exceptions, log full details (Serilog/AppInsights).</li><li>Return a generic <code>ProblemDetails</code> with status 500 and a correlation ID — never expose stack traces.</li><li>Map known domain exceptions (<code>NotFoundException</code> → 404, <code>ValidationException</code> → 400).</li><li>Register <b>first</b> in the pipeline so it catches everything downstream.</li></ul>
S02.06.Medium. What is the request pipeline order for: <code>UseRouting</code>, <code>UseCors</code>, <code>UseAuthentication</code>, <code>UseAuthorization</code>, <code>UseEndpoints</code>? What breaks if you swap <code>UseCors</code> and <code>UseAuthentication</code>?	<p>Correct order: <code>UseRouting</code> → <code>UseCors</code> → <code>UseAuthentication</code> → <code>UseAuthorization</code> → <code>UseEndpoints</code>.</p><ul><li><code>UseRouting</code> first — selects the endpoint (CORS needs this to match a policy).</li><li><code>UseCors</code> before auth — otherwise preflight <code>OPTIONS</code> requests hit auth and return 401, blocking the browser.</li><li><code>UseAuthentication</code> before <code>UseAuthorization</code> — must establish WHO before checking WHAT they can access.</li></ul>
S02.07.Medium. Explain <code>IOptions<T></code>, <code>IOptionsSnapshot<T></code>, and <code>IOptionsMonitor<T></code>. Which reloads on config change? Which is safe for Singleton services? Which would you use for secrets that rotate?	<p><code>IOptions<T></code>: Singleton, reads config once at startup, never reloads. Safe in Singletons.</p><p><code>IOptionsSnapshot<T></code>: Scoped, reloads per request from config source — NOT safe in Singletons.</p><p><code>IOptionsMonitor<T></code>: Singleton-safe AND reloads — uses change tokens and <code>OnChange</code> callback.</p><p>Use <code>IOptionsMonitor<T></code> for rotating secrets (Key Vault with <code>ReloadInterval</code>).</p>
S02.08.Medium. What does <code>[FromBody]</code>, <code>[FromQuery]</code>, <code>[FromRoute]</code>, and <code>[FromHeader]</code> do? When does <code>[ApiController]</code> infer the source automatically?	<ul><li><b><code>[FromBody]</code></b> — deserialize request body (JSON).</li><li><b><code>[FromQuery]</code></b> — bind from the query string.</li><li><b><code>[FromRoute]</code></b> — bind from the URL route template.</li><li><b><code>[FromHeader]</code></b> — bind from an HTTP header.</li></ul><p>With <code>[ApiController]</code> auto-inference: complex types → <code>[FromBody]</code>; <code>IFormFile</code> → <code>[FromForm]</code>; name matches route template → <code>[FromRoute]</code>; otherwise → <code>[FromQuery]</code>.</p>
S02.09.Medium. You deploy to Azure App Service. The app starts but returns 500 on all endpoints. The log says "Unable to resolve service for type 'IOrderService'." What happened? How do you fix it?	<p>The service wasn't registered in the DI container. Common causes:</p><ul><li>Forgot to register it in <code>Program.cs</code>.</li><li>Registered the concrete type (<code>AddScoped<OrderService>()</code>) but injecting by interface (<code>IOrderService</code>).</li><li>Typo in namespace — wrong type resolved.</li><li>The service has an unresolvable transitive dependency.</li></ul><p>Prevention: use <code>ValidateOnBuild = true</code> (.NET 8+), or add an integration test that resolves all registered services.</p>
S02.10.Hard. Design the middleware pipeline for an e-commerce API that needs: exception handling, CORS, CSP headers, authentication, authorization, rate limiting, and request logging. Draw the order and explain why each piece goes where it does.	<p>Order:</p><li><code>ExceptionHandler</code> — outermost, catches everything downstream.</li><li><code>RequestLogging</code> — captures timing for all requests (including failed ones).</li><li><code>SecurityHeaders</code>/CSP — adds headers before response.</li><li><code>UseRouting</code> — selects endpoint (needed by CORS).</li><li><code>UseCors</code> — needs endpoint info, must be before auth.</li><li><code>RateLimiting</code> — reject before expensive auth work.</li><li><code>UseAuthentication</code> — identity must be established.</li><li><code>UseAuthorization</code> — check permissions after identity.</li><li><code>UseEndpoints</code> — execute the action.</li><p>Reasoning: each layer depends on the one before it, and security layers run outside business logic.</p>
S02.11.Hard. You're building a multi-tenant SaaS app. Each tenant has its own database. How do you resolve a <code>DbContext</code> with a connection string that depends on the current request's tenant header? Which DI lifetime do you use and why?	<p>Use Scoped lifetime. Create middleware that reads the tenant header and stores the tenant ID in <code>HttpContext.Items</code> or a scoped <code>ITenantContext</code>. Register <code>DbContext</code> as Scoped with a factory:</p><pre><code>AddDbContext&lt;AppDb&gt;((sp, opt) =&gt; {     var tenant = sp.GetRequiredService&lt;ITenantContext&gt;();     opt.UseSqlServer(GetConnString(tenant.Id)); });</code></pre><p>Scoped ensures one <code>DbContext</code> per request with the correct tenant. Cache connection strings. Singleton would be dangerous (shared DB across tenants). Transient would create a new context on every injection.</p>
