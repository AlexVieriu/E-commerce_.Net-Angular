# A1 — [EASY][HIGH] What is the difference between pull_request and push triggers in GitH...
# ────────────────────────────────────────────────────────────────────────────
<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><ul><li><code class="c">pull_request</code> fires on the <b>proposed change</b> — before merge. This catches conflicts introduced by parallel PRs — a scenario that branch-only CI misses entirely.</p></div></div>

# A2 — [EASY][HIGH] What is OIDC-based authentication for Azure deployments? Why is it sa...
# ────────────────────────────────────────────────────────────────────────────
<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><ul><li><b>OIDC (OpenID Connect)</b> — GitHub and Azure establish a trust relationship via a <b>federated credential</b> on a Managed Identity. No password is stored anywhere.</li><li>GitHub requests a <b>short-lived token</b> per workflow run from Azure's STS(Security Token Service). The token is scoped to the run and expires within minutes.</li><li>Compare to a stored client secret: stored in GitHub Secrets as a long-lived credential, must be manually rotated, and is compromised if the secret store is breached.</li></ul><pre class="p"><code>- uses: azure/login@v2<br>  with:<br>    client-id: ${{ secrets.AZURE_CLIENT_ID }}       # identifier, not a secret<br>    tenant-id: ${{ secrets.AZURE_TENANT_ID }}<br>    subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}</code></pre><p>These are IDs — not credentials. No password is stored or transmitted.</p><p><b>Production consequence:</b> a leaked client secret grants persistent access until manually rotated. A leaked OIDC token is useless after minutes — and is scoped to one workflow run.</p></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"OIDC is just another password stored differently." Wrong — it's a fundamentally different trust model. No credential is stored; trust is asserted cryptographically via GitHub's identity.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning that OIDC tokens are bound to the specific repository, branch, and environment. A token generated for <code class="c">main</code> cannot be used by a forked repo or a different branch — unlike a static secret that any holder can use from anywhere.</p></div></div>

Developers merging feature work multiple times a day would each cause a production deployment — including half-finished features and work-in-progress branches.</p><p><b>Fix — separate triggers:</b></p><pre class="p"><code>on:<br>  pull_request:<br>    branches: [main, development]  # CI only<br>  push:<br>    branches: [main]               # deploy only</code></pre></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"Add <code class="c">environment: production</code> to the job." This eliminates trigger-bleed entirely: a CI workflow physically cannot deploy, and a deploy workflow physically cannot run tests. # A5 — [MEDIUM][MEDIUM] npm install passes on CI but installs a different version than local....
# ────────────────────────────────────────────────────────────────────────────
<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><p><b>Why it happens:</b></p><p><code class="c">npm install</code> resolves semver ranges in <code class="c">package.json</code>. If <code class="c">"@angular/core": "^18.0.0"</code> and a new patch <code class="c">18.0.3</code> was released between the developer's last <code class="c">npm install</code> and the CI run, CI installs <code class="c">18.0.3</code> while local has <code class="c">18.0.1</code>.</p><p><b>How <code class="c">npm ci</code> prevents it:</b></p><ul><li>Reads <code class="c">package-lock.json</code> <b>exactly</b> — no range resolution</li><li>If <code class="c">package.json</code> and <code class="c">package-lock.json</code> are out of sync, <code class="c">npm ci</code> <b>fails</b> immediately, forcing an intentional update</li><li>Deletes <code class="c">node_modules</code> before installing — guarantees a clean state, no leftover artefacts</li></ul><p><b>Practical failure mode:</b></p><pre class="p"><code>Local:  @angular/material@18.0.1 (installed 3 months ago)<br>CI:     @angular/material@18.2.0 (latest in ^18 range)<br>→ Angular build passes locally, fails on CI due to breaking change in 18.2.0</code></pre></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"Commit <code class="c">node_modules</code> to avoid version drift." Bloats the repo with tens of thousands of files, breaks cross-platform CI (Linux binaries committed from Windows), and makes diffs unreadable.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning <code class="c">--frozen-lockfile</code> is the <code class="c">yarn</code> equivalent, and <code class="c">pnpm ci</code> for pnpm. Also: <code class="c">npm ci</code> is significantly faster on CI because it skips dependency resolution entirely — it reads the lock file and extracts packages directly, bypassing the semver solver.</p></div></div>

# A6 — [MEDIUM][HIGH] A developer rapidly pushes 4 commits to the same PR branch. Four full...
# ────────────────────────────────────────────────────────────────────────────
<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><p><b>Without <code class="c">concurrency:</code></b>, every push queues a fresh run. Five pushes in a minute = five full <code class="c">dotnet test</code> + <code class="c">ng build</code> cycles against the first four stale commits. Minutes billed, runners clogged, and completion order can diverge from push order (one run on a slow runner finishes after a later run on a fast runner).</p><p><b>The fix — one block under <code class="c">on:</code>:</b></p><pre class="p"><code>concurrency:<br>  group: ${{ github.workflow }}-${{ github.ref }}<br>  cancel-in-progress: true</code></pre><ul><li><code class="c">group: workflow-ref</code> groups all runs on the same branch for the same workflow file</li><li><code class="c">cancel-in-progress: true</code> cancels the in-flight run when a new one enters the group</li></ul><p><b>Why <code class="c">github.run_id</code> breaks it:</b></p><p><code class="c">github.run_id</code> is <b>unique per run</b> — each run lands in a group of size 1. The concurrency mechanism only activates when two runs share a group, so nothing is ever cancelled. Every push still runs to completion.</p><p><code class="c">github.ref</code> is the correct key: "same branch = same group = new push cancels the old."</p><p><b>Production consequence:</b> on a busy repo with 15-minute CI, a developer force-pushing a fix while the old run is still going creates a race. Without <code class="c">cancel-in-progress</code>, whichever finishes first triggers deploy logic downstream. If the old (broken) run completes seconds before the fixed one, the broken SHA ships.</p></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"We'll cancel old runs manually in the Actions UI." Manual intervention across a dozen PRs per day is infeasible — and the first missed one deploys broken code. Concurrency is 3 lines of YAML.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Knowing that deploy jobs should <b>not</b> have <code class="c">cancel-in-progress: true</code> — cancelling a half-finished Azure deploy leaves the App Service in a partial state (slot swap aborted, files mid-transfer). Split the workflow: CI uses cancellation, deploy uses a separate concurrency group without it — or no concurrency at all.</p></div></div>

# A7 — [HARD][HIGH] The CI pipeline found 12 pre-existing test failures on first run. Wal...
# ────────────────────────────────────────────────────────────────────────────
<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><p><b>The specific bug:</b></p><p>StackExchange.Redis 2.12.x added a new <code class="c">StringSetAsync</code> overload with <code class="c">Expiration</code> and <code class="c">ValueCondition</code> parameters. Production code was updated to use the new overload, but the Moq setup still used the old parameter types:</p><pre class="p"><code>// Old overload (no longer matched):<br>mockDatabase.As&lt;IDatabaseAsync&gt;()<br>    .Setup(x =&gt; x.StringSetAsync(<br>        It.IsAny&lt;RedisKey&gt;(),<br>        It.IsAny&lt;RedisValue&gt;(),<br>        It.IsAny&lt;TimeSpan?&gt;(),      // ← old type<br>        It.IsAny&lt;When&gt;(),           // ← old type<br>        It.IsAny&lt;CommandFlags&gt;()))<br>    .ReturnsAsync(false);<br><br>// New overload (what production code calls):<br>// StringSetAsync(RedisKey, RedisValue, Expiration, ValueCondition, CommandFlags)</code></pre><p>Moq sees no matching setup → returns <code class="c">false</code> (default for <code class="c">bool</code>) → <code class="c">SetCartAsync</code> returns <code class="c">null</code> → assertion <code class="c">result.Should().BeNull()</code> passes — but for the <b>wrong reason</b>. The mock was never called.</p><p><b>Why local missed it:</b></p><p>Developer machines may have different package versions cached, or a different Redis library version in their local <code class="c">packages.lock.json</code>. Existing mock setups become silently inoperative because Moq's type matching is exact, not coercive.</p><p><b>Production consequence:</b> the test appeared to cover <code class="c">SetCartAsync</code> failure behaviour.
