Specs keep the combinatorial complexity in one place.</p></div></div>

EF's SQLite provider handles the cast silently. Tests pass, sort order appears correct.</li><li><b>SQL Server (prod):</b> EF generates <code class="c">CAST(Price AS float)</code>. EF Core translates this to <code class="c">ORDER BY Price</code> with no <code class="c">CAST</code> — the decimal column sorts precisely.</p><ul><li><b>Note:</b> the project's <code class="c">specifications.md</code> mandates this pattern. Always verify the generated SQL via EF Core query logging (<code class="c">Microsoft.EntityFrameworkCore.Database.Command</code> at <code class="c">Information</code>) when switching providers.</li></ul><p><b>Production consequence:</b> product price ordering silently changes in production for items with prices like <code class="c">$9.995</code> and <code class="c">$10.004</code>. Subtle, hard to reproduce, causes customer complaints about "wrong" sort order.</p></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"Cast to <code class="c">decimal</code> explicitly instead." <code class="c">decimal</code> is already the column type — an explicit <code class="c">(decimal)</code> cast is a no-op in C# but still generates a <code class="c">CAST</code> in some providers. <code class="c">(object)</code> is the correct pattern precisely because it avoids any SQL-level cast.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning this is explicitly documented in the project's Common Mistakes. The broader lesson: any cast or method call inside a LINQ <code class="c">Expression&lt;...&gt;</code> is translated to SQL — C# semantics don't apply. Always verify expression translation on the production DB provider, not just SQLite.</p></div></div>
