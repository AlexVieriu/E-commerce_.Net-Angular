S06.01.Easy. What is the difference between <code>ngOnInit</code> and the constructor in an Angular component?	<ul><li><b>Constructor</b> — called by the JS engine; used for DI injection only — keep it lightweight.</li><li><b><code>ngOnInit</code></b> — called by Angular after <code>@Input()</code> values are set; use for HTTP calls, subscription setup, complex initialization.</li></ul><p>Key: <code>@Input()</code> values are <code>undefined</code> in the constructor — they're only available from <code>ngOnInit</code> onwards.</p>
S06.02.Easy. What is dependency injection in Angular? How do you inject a service into a component?	<ul><li>Angular creates and provides service instances to components that need them.</li><li><b>Constructor injection</b>: <code>constructor(private productService: ProductService)</code> — Angular's injector resolves and injects the instance.</li><li><b><code>inject()</code> function</b> (Angular 14+): functional alternative; works in constructors, field initializers, functional guards/interceptors.</li></ul>
S06.03.Easy. What does <code>providedIn: 'root'</code> do on a service? What's the alternative?	<ul><li><b><code>providedIn: 'root'</code></b> — singleton in the root injector; available app-wide; tree-shakable (removed from bundle if nothing injects it). Preferred for most services.</li><li><b><code>providers: []</code> on a component</b> — new instance per component; lives and dies with that component.</li><li><b><code>providers: []</code> on a module</b> — one instance per module injector; breaks tree-shaking.</li></ul>
S06.04.Easy. What is the difference between <code>*ngIf</code> and <code>@if</code> (new control flow syntax)?	<ul><li><b><code>*ngIf</code></b> (Angular <17) — structural directive, requires <code>CommonModule</code> import, no native <code>@else if</code>.</li><li><b><code>@if</code></b> (Angular 17+) — built-in template syntax, no import needed, full TypeScript type narrowing, native <code>@else if</code>.</li></ul><p><code>@if</code> is more readable and compiles to faster output (no directive overhead).</p>
S06.05.Easy. What does the <code>async</code> pipe do? Why is it preferred over manually subscribing in the component?	<p><code>async</code> pipe subscribes to an Observable/Promise in the template and auto-unsubscribes on component destroy. Preferred because:</p><li>No memory leaks (auto-cleanup).</li><li>Works with <code>OnPush</code> change detection.</li><li>Less boilerplate (no manual subscribe/unsubscribe).</li><li>Template stays reactive.</li><p>Pattern: <code>products$ | async</code> in template instead of <code>subscribe()</code> in component.</p>
S06.06.Medium. Explain Angular's change detection. What triggers it? What is <code>OnPush</code> change detection? When does <code>OnPush</code> NOT trigger change detection?	<p>Default: Angular checks every component top-down on any async event (click, HTTP, setTimeout).</p><p>OnPush only runs change detection when:</p><li><code>@Input()</code> reference changes (not mutation!).</li><li>DOM event originates in the component.</li><li><code>async</code> pipe emits.</li><li>Manually via <code>ChangeDetectorRef.markForCheck()</code>.</li><p>OnPush SKIPS when: parent mutates an input object without creating a new reference, or external observable emits without <code>async</code> pipe.</p>
S06.07.Medium. What is <code>ViewEncapsulation</code> in Angular? What are the three modes? Why does Angular Material use <code>ViewEncapsulation.None</code>?	<p><b>Emulated</b> (default): Angular rewrites selectors with <code>_ngcontent-xxx</code> attributes — styles are scoped but CSS-only (no true shadow DOM).</p><p><b>ShadowDom:</b> uses native Shadow DOM — true encapsulation, styles can't leak in or out.</p><p><b>None:</b> styles are global — no scoping at all.</p><p>Angular Material uses <code>None</code> because its components need global theme styles (typography, colors, density) to cascade in from the app's theme. Scoping would block theme customization.</p>
S06.08.Medium. What is the difference between <code>template-driven</code> forms and <code>reactive</code> forms? When would you choose each? Which is easier to test?	<p><b>Template-driven:</b> defined in HTML with <code>ngModel</code>, two-way binding, simpler for small forms (login, search). Async by nature (directives).</p><p><b>Reactive:</b> defined in TypeScript with <code>FormGroup</code>/<code>FormControl</code>, explicit, synchronous, powerful validation and dynamic fields.</p><p>Easier to test: reactive forms (no template rendering needed — test the <code>FormGroup</code> directly).</p><p>Choose template-driven for simple forms, reactive for complex forms (dynamic fields, cross-field validation, arrays).</p>
S06.09.Medium. Explain Angular routing: what is a <code>RouterOutlet</code>? What is lazy loading? How do you lazy-load a standalone component? What is a route guard?	<ul><li><b><code>RouterOutlet</code></b> — placeholder directive where Angular renders the matched route's component.</li><li><b>Lazy loading</b> — <code>loadComponent: () => import('./product.component').then(m => m.ProductComponent)</code>; downloads the component only when the route is visited, reducing initial bundle size.</li><li><b>Route guards</b> — <code>CanActivate</code> (auth check), <code>CanDeactivate</code> (unsaved changes warning), <code>Resolve</code> (pre-fetch data before render). In Angular 15+, guards can be plain functions via <code>CanActivateFn</code>.</li></ul>
S06.10.Medium. What does this code do? Is there a memory leak?  ``<code>typescript @Component({...}) export class ProductListComponent implements OnInit {   products: Product[] = [];    constructor(private productService: ProductService) {}    ngOnInit() {     this.productService.getAll().subscribe(p => this.products = p);   } } </code>``	<p>It fetches products on init and assigns them. Memory leak? <b>It depends:</b></p><ul><li><b>HTTP Observable</b> (<code>HttpClient</code>) — no leak; it emits once and auto-completes.</li><li><b>Long-lived observable</b> (WebSocket, interval, <code>Subject</code>) — yes, the subscription lives after the component is destroyed.</li></ul><p>Best practice: always use <code>async</code> pipe, <code>takeUntilDestroyed()</code>, or manual unsubscribe in <code>ngOnDestroy</code>.</p>
S06.11.Medium. What is an Angular interceptor? Give three real-world use cases. How do you register one with the new <code>provideHttpClient(withInterceptors([...]))</code> syntax?	<p>Interceptor is middleware that processes every HTTP request/response. Use cases:</p><li>Attach auth token to every request (<code>Authorization: Bearer ...</code>).</li><li>Global error handling (catch 401 → redirect to login).</li><li>Request/response logging or loading spinner.</li><p>Register with <code>withInterceptors</code>:</p><pre><code>// app.config.ts provideHttpClient(withInterceptors([authInterceptor, loggingInterceptor]))  // interceptor export const authInterceptor: HttpInterceptorFn = (req, next) =&gt; {   const newReq = req.clone({ setHeaders: { Authorization: 'Bearer ...' } });   return next(newReq); };</code></pre>
S06.12.Hard. Explain RxJS operators: <code>switchMap</code>, <code>mergeMap</code>, <code>concatMap</code>, <code>exhaustMap</code>. For each, give a real-world use case and explain what happens when a new observable emits before the previous one completes.	<p><code>switchMap</code>: cancels previous inner observable. Use: search typeahead — new keystroke cancels pending request.</p><p><code>mergeMap</code>: runs all inner observables concurrently. Use: batch file uploads — all in parallel. Risk: flooding.</p><p><code>concatMap</code>: queues — waits for previous to complete before starting next. Use: ordered operations (chat messages, sequential API calls).</p><p><code>exhaustMap</code>: ignores new emissions while current is active. Use: login/submit button — prevents duplicate submissions.</p>
S06.13.Hard. What is tree-shaking? How does Angular's build process use it? What prevents a service from being tree-shaken? How does <code>providedIn: 'root'</code> enable tree-shaking compared to registering in <code>providers: []</code>?	<p>Tree-shaking removes unused code via static analysis of ES module imports.</p><ul><li><b><code>providedIn: 'root'</code></b> — tree-shakable: if nothing injects the service, the bundler finds no import path and removes it.</li><li><b><code>providers: []</code> in a module</b> — NOT tree-shakable: the module imports the service file, keeping it in the bundle regardless of usage.</li></ul><p>Tree-shaking blockers:</p><ul><li>Side effects in the constructor (bundler plays it safe and keeps the code).</li><li>Barrel files (<code>export * from ...</code>) — force the entire file into the bundle.</li><li>Dynamic <code>import()</code> patterns the bundler can't statically analyze.</li></ul>
