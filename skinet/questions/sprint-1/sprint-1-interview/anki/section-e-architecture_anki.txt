S05.01.Easy. What is the Repository pattern? Why use it instead of injecting <code>DbContext</code> directly into controllers?	<p>Repository abstracts data access behind an interface. Benefits:</p><li>Testability — mock the repository instead of DbContext.</li><li>Separation of concerns — controllers don't know about EF/SQL.</li><li>Single responsibility — data access logic lives in one place.</li><li>Swappable persistence — change from EF to Dapper without touching business logic.</li>
S05.02.Easy. What is the difference between the Repository pattern and the Unit of Work pattern? How do they work together?	<ul><li><b>Repository</b> — encapsulates data access for a single entity type (CRUD operations).</li><li><b>Unit of Work</b> — coordinates multiple repositories in one transaction; tracks changes across entities and commits atomically.</li></ul><p>In EF Core, <code>DbContext</code> IS the Unit of Work (change tracker) and <code>DbSet<T></code> is a basic Repository. Custom wrappers add a clean abstraction layer on top.</p>
S05.03.Medium. Your app has three layers: Core (domain), Application (services), Infrastructure (EF, Redis, Stripe). Draw the dependency graph. Which layer depends on which? What is the Dependency Inversion Principle and how does your architecture apply it?	<p>Dependencies point inward: <code>Infrastructure → Application → Core</code>. Core depends on <b>nothing</b>.</p><ul><li>Interfaces (<code>IRepository</code>, <code>IEmailService</code>) live in <b>Core</b>; implementations live in <b>Infrastructure</b>.</li><li>This is Dependency Inversion: Core (high-level) defines the abstraction; Infrastructure (low-level) implements it.</li><li>At runtime the DI container wires <code>IOrderRepository</code> → <code>SqlOrderRepository</code>.</li><li><b>Benefits</b>: Core is testable in isolation; Infrastructure is swappable without touching business logic.</li></ul>
S05.04.Medium. What is the difference between the MVC pattern and the API controller pattern in ASP.NET Core? Why don't you return Views from an API controller?	<ul><li><b>MVC controllers</b> — return <code>Views</code> (HTML rendered server-side via Razor); tightly coupled to the UI.</li><li><b>API controllers</b> — return data (DTOs as JSON/XML) for client-side rendering; use <code>[ApiController]</code>, no Views folder, return <code>IActionResult</code> with HTTP status codes.</li></ul><p>Separation: the API serves data, the frontend (Angular/React) handles presentation. This enables multiple clients — web, mobile, third-party — from the same backend.</p>
S05.05.Medium. You need to add a "wishlist" feature. Walk through which layer each piece of code goes in: entity, repository interface, repository implementation, service, controller, DTO. Why does the repository interface live in Core and the implementation in Infrastructure?	<ul><li><b>Core:</b> <code>WishlistItem</code> entity + <code>IWishlistRepository</code> interface.</li><li><b>Infrastructure:</b> <code>WishlistRepository : IWishlistRepository</code> (EF implementation) + <code>WishlistConfiguration</code> (Fluent API).</li><li><b>Application:</b> <code>WishlistService</code> (business logic: add, remove, check duplicates) + <code>WishlistDto</code>.</li><li><b>API:</b> <code>WishlistController</code> (endpoints: GET /wishlist, POST /wishlist, DELETE /wishlist/{id}).</li></ul><p>Interface in Core because: Core defines WHAT operations exist (abstraction), Infrastructure defines HOW (implementation). This inverts the dependency — Core never references EF.</p>
S05.06.Hard. Compare these architectures for an e-commerce backend: (1) modular monolith, (2) microservices, (3) serverless functions. For each: how would you split orders/payments/inventory? What's the communication pattern? Where does the transaction boundary live? When would you choose each?	<p><b>Modular monolith:</b> modules (Orders, Payments, Inventory) in one app with clear boundaries (separate folders/projects). Communication: in-process method calls or MediatR. Transactions: single DB, ACID across modules. Choose: early stage, small team, simple ops.</p><p><b>Microservices:</b> separate services with own DBs. Communication: HTTP/gRPC + message queues (RabbitMQ). Transactions: saga pattern (no distributed transactions). Choose: large team, independent scaling, fault isolation needed.</p><p><b>Serverless:</b> functions per operation, event-driven (Lambda + SQS). Cheap at low scale, expensive at high scale. Choose: sporadic traffic, event-driven workflows.</p>
