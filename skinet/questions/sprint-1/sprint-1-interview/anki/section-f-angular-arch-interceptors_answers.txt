# F2 — [EASY][HIGH] What is ChangeDetectionStrategy.OnPush and why is it mandatory for ev...
# ────────────────────────────────────────────────────────────────────────────
<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><p><b>Default strategy:</b> Angular checks every component after every async event (click, HTTP response, timer). Even components unrelated to the change are re-evaluated.</p><p><b><code class="c">OnPush</code>:</b> Angular re-checks a component only when:</p><ol><li>An <code class="c">@Input()</code> receives a new reference</li><li>An event originates inside the component</li><li>An Observable via <code class="c">AsyncPipe</code> emits a new value</li><li><b>A signal the component reads changes</b> ← the key trigger in this project</li><li><code class="c">ChangeDetectorRef.markForCheck()</code> is explicitly called</li></ol><p><b>Why mandatory in this project (zoneless mode):</b></p><p><code class="c">provideZonelessChangeDetection()</code> removes Zone.js. Zone.js normally monkey-patches <code class="c">setTimeout</code>, <code class="c">Promise</code>, XHR, and triggers change detection after every async event. Without it, CD only runs when one of the 5 triggers above fires.</p><p>Without <code class="c">OnPush</code> in zoneless mode: a component with the default strategy never gets re-checked automatically — it's frozen after initial render. Data updates but the view stays stale.</p><p><b>With <code class="c">OnPush</code> + signals:</b> Angular runs CD precisely on affected component trees when signals change. This is O(changed) vs O(all) — the architecture for scalable Angular apps.</p></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"<code class="c">OnPush</code> is optional for performance — just use it on slow components." In zoneless mode, it's not optional. Default strategy components literally never update without Zone.js. Omitting <code class="c">OnPush</code> is a correctness bug, not a performance choice.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning that migrating from zone-based to zoneless Angular exposes a long tail of existing <code class="c">OnPush</code> violations — components that "worked" with Zone.js because the zone triggered CD incidentally are suddenly broken. Zoneless migration is as much a bug-hunt as an architecture change. Running <code class="c">ng build --configuration zoneless</code> as a CI check surfaces these early.</p></div></div>

# F3 — [MEDIUM][HIGH] The interceptor order is: register errorInterceptor first, then loadi...
# ────────────────────────────────────────────────────────────────────────────
<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><p>Angular interceptors form a chain where the <b>request path</b> follows registration order and the <b>response path</b> is reversed:</p><pre class="p"><code>Request:  error → loading → auth → HTTP server<br>Response: error ← loading ← auth ← HTTP server</code></pre><p><b>Why <code class="c">authInterceptor</code> last (closest to HTTP on request):</b></p><p>It adds <code class="c">withCredentials: true</code> to the outgoing request. Being last on the request path means it's applied as the final transform — nothing downstream can strip it. On the response path, it runs first — it sees the raw response before error handling.</p><p><b>Why <code class="c">errorInterceptor</code> first (registered first = runs last on responses):</b></p><p>It must be the final interceptor to see errors so it can dispatch <code class="c">router.navigate</code>, snackbar messages, and cart reloads as the last action — after loading spinner cleanup.</p><p><b>If auth and error are reversed:</b></p><ul><li>Response path: auth interceptor runs after error → <code class="c">router.navigate('/login')</code> fires first, then auth tries to process a response that's already been redirected</li><li>401 on <code class="c">/api/account/user-info</code> (expected for anonymous users) → error interceptor fires, navigates to login → auth interceptor runs after on a dead response → state corruption</li></ul><p><b>Observable chain:</b></p><pre class="p"><code>// Each interceptor wraps the next:<br>authInterceptor → loadingInterceptor → errorInterceptor → HTTP<br>// Response travels back through:<br>HTTP → errorInterceptor → loadingInterceptor → authInterceptor</code></pre></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"Interceptor order doesn't matter for most cases." The response pipeline is always the reverse of the request pipeline. Getting this wrong causes subtle state bugs — the spinner stays active after a 401 redirect, or navigation fires before cleanup.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning that <code class="c">HttpInterceptorFn</code> interceptors compose via the <code class="c">next</code> function — you can trace the exact processing order by logging in each interceptor's request and response paths in dev. Middleware composition is explicit, not implicit — understanding the model eliminates guesswork about ordering.</p></div></div>

On a page with multiple child routes each having <code class="c">canActivate: [authGuard]</code>, multiple concurrent calls fire on a single navigation. A checkout flow with 4 steps, each guarded, would fire 4 auth requests before the first step renders.</p><p><b>With the signal check:</b></p><pre class="p"><code>const canActivate: CanActivateFn = (): Observable&lt;boolean&gt; | boolean =&gt; {<br>    const user = inject(AccountService).currentUser();<br><br>    if (user) return true;  // signal set → allow immediately, no HTTP<br><br>    return inject(AccountService).getAuthState().pipe(<br>        map(state =&gt; state.isAuthenticated || (router.navigate(['/login']), false))<br>    );<br>};</code></pre><p>The signal is populated during app initialization before any route renders — it's authoritative for the current session. HTTP is only called when the signal is empty (fresh tab, session check needed).</p><p><b>Failure scenario without short-circuit on slow networks:</b></p><p>User navigates to <code class="c">/checkout/step-2</code>. Guard fires HTTP, 300ms RTT. Another navigation fires before the first resolves. RxJS pipelines overlap. Angular cancels the first guard resolution and restarts — infinite redirect loop under poor conditions.</p></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"Always call the API to ensure accuracy — the signal might be stale." The signal is set from the server-authoritative <code class="c">/user-info</code> response on startup. If the session expires mid-session, the next actual API call returns 401 and the error interceptor handles the redirect. The signal doesn't need constant revalidation.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning <code class="c">canMatch</code> as the modern alternative for some guard use cases — it runs before route matching and can prevent lazy module loading. <code class="c">canActivate</code> runs after the route is matched and the component starts loading. For cases where you want to prevent code download for unauthorized users, <code class="c">canMatch</code> is more appropriate than <code class="c">canActivate</code>.</p></div></div>

<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><p><b>Without <code class="c">withComponentInputBinding()</code>:</b></p><p>Route params require <code class="c">ActivatedRoute</code> injection:</p><pre class="p"><code>constructor(private route: ActivatedRoute) {}<br><br>ngOnInit() {<br>    // Option 1: snapshot (misses param changes on same component)<br>    this.id = this.route.snapshot.paramMap.get('id')!;<br><br>    // Option 2: Observable subscription (requires cleanup)<br>    this.route.params.pipe(takeUntilDestroyed()).subscribe(p =&gt; this.id = p['id']);<br>}</code></pre><p><b>With <code class="c">withComponentInputBinding()</code> (in <code class="c">app.config.ts</code>):</b></p><pre class="p"><code>@Input() id!: string;       // route param :id bound directly<br>@Input() search?: string;   // query param ?search= bound directly</code></pre><p>Router uses Angular's input binding system — same mechanism as parent components passing values. No <code class="c">ActivatedRoute</code> injection, no Observable, no subscription cleanup.</p><p><b>Code eliminated:</b></p><ul><li><code class="c">ActivatedRoute</code> import and injection</li><li><code class="c">ngOnInit</code> with param subscription</li><li><code class="c">takeUntilDestroyed()</code> for cleanup</li></ul><p><b>Zoneless-specific benefit:</b></p><p><code class="c">ActivatedRoute.params</code> is a <code class="c">Subject</code> (Observable). In zoneless mode, subscribing to it without <code class="c">AsyncPipe</code> requires <code class="c">markForCheck()</code> after each emission — easy to forget, causing silent view staleness. <code class="c">@Input()</code> binding is synchronous and part of Angular's native input change detection — no subscription, no cleanup, automatic CD integration.</p></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"You still need <code class="c">ActivatedRoute</code> for query params and resolve data." This is the future-facing pattern; <code class="c">@Input()</code> decorator still works but doesn't expose the value as a signal.</p><p><b>Production consequence:</b> without <code class="c">withComponentInputBinding()</code>, navigating from <code class="c">/products/1</code> to <code class="c">/products/2</code> when Angular reuses the component leaves <code class="c">ActivatedRoute.snapshot.paramMap.get('id')</code> returning <code class="c">1</code> — the component renders the wrong product without any error. Only Observable-based param subscription catches param changes mid-lifecycle, and missing <code class="c">takeUntilDestroyed()</code> on that subscription leaks memory on every navigation.</p></div></div>

Can't be used in <code class="c">computed()</code> or <code class="c">effect()</code>. Requires <code class="c">| async</code> syntax in every template binding.</li><li><b><code class="c">toSignal(obs$)</code></b> — creates one subscription, exposes the value as a <b>composable signal</b> usable in <code class="c">computed()</code>, <code class="c">effect()</code>, and template expressions. Cleans up automatically on component destroy.</li></ul><p><b>Prefer <code class="c">toSignal</code> when:</b></p><ul><li>The value is read in multiple template locations (one subscription vs many)</li><li>The value feeds into <code class="c">computed()</code> or <code class="c">effect()</code></li><li>You want a synchronous initial value: <code class="c">toSignal(obs$, { initialValue: [] })</code></li></ul><pre class="p"><code>products = toSignal(this.productService.getAll(), { initialValue: [] });<br>filteredCount = computed(() =&gt; this.products().filter(p =&gt; p.price &lt; 10).length);</code></pre></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>Using <code class="c">AsyncPipe</code> for a value also needed inside <code class="c">computed()</code> — <code class="c">AsyncPipe</code> is template-only; you'd need a separate subscription in the component class, creating two subscriptions to the same Observable. <code class="c">toSignal</code> unifies them.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Knowing <code class="c">toSignal</code> requires an injection context (called at field initialization time, not inside a method). For late-created signals, use <code class="c">runInInjectionContext(injector, () =&gt; toSignal(...))</code> or restructure so the signal is created at construction time.</p></div></div>
