S04.01.Easy. What is the difference between <code>npm ci</code> and <code>npm install</code>? Which should you use in CI?	<p><code>npm ci</code> deletes <code>node_modules</code>, installs exactly from <code>package-lock.json</code> (never modifies it), is faster, and fails if the lock file is out of sync. <code>npm install</code> may update the lock file and resolve newer versions. Always use <code>npm ci</code> in CI for reproducible builds.</p>
S04.02.Easy. What triggers a GitHub Actions workflow? Name three event types.	<p>Common triggers:</p><ul><li><b><code>push</code></b> — on commit to branches or tags.</li><li><b><code>pull_request</code></b> — on PR opened/synchronized/merged.</li><li><b><code>workflow_dispatch</code></b> — manual run from the GitHub UI.</li><li><b><code>schedule</code></b> — cron-based (e.g. nightly builds).</li><li><b><code>release</code></b> — on a published GitHub release.</li></ul><p>Most CI pipelines use <code>push</code> + <code>pull_request</code> filtered to specific branches.</p>
S04.03.Easy. What does <code>needs: [build]</code> do in a GitHub Actions job?	<p><code>needs: [build]</code> creates a dependency — the current job waits until the <code>build</code> job completes successfully before running. If <code>build</code> fails, dependent jobs are skipped. This enforces sequential execution: build → test → deploy.</p>
S04.04.Easy. In the .NET config provider chain, if the same key exists in <code>appsettings.json</code> and User Secrets, which wins? Why?	<p>User Secrets wins. .NET config uses a last-wins strategy — providers registered later override earlier ones. Default order: <code>appsettings.json</code> → <code>appsettings.{Environment}.json</code> → User Secrets → Environment Variables → Command Line.</p>
S04.05.Medium. Your CI pipeline has three jobs: <code>build</code>, <code>test</code>, <code>deploy</code>. The <code>deploy</code> job runs even when <code>test</code> fails. What's wrong? Write the corrected YAML.	<p>The original is missing <code>needs</code> directives — without them, all jobs run in parallel.</p><pre><code>jobs:   build:     runs-on: ubuntu-latest     steps:       - uses: actions/checkout@v4       - run: dotnet build    test:     needs: [build]     runs-on: ubuntu-latest     steps:       - uses: actions/checkout@v4       - run: dotnet test    deploy:     needs: [test]     runs-on: ubuntu-latest     steps:       - run: echo "Deploying..."</code></pre><p>Now if build fails, test is skipped. If test fails, deploy is skipped.</p>
S04.06.Medium. You have secrets stored in: <code>appsettings.json</code>, <code>appsettings.Development.json</code>, environment variables, User Secrets, and Azure Key Vault. Draw the provider chain. For each: when used, what belongs there, committed to git?	<p>Chain (last wins):</p><li><code>appsettings.json</code> — base config (URLs, feature flags). <b>Committed</b>.</li><li><code>appsettings.{Env}.json</code> — env-specific overrides (logging levels). <b>Committed</b>.</li><li>User Secrets — local dev secrets (API keys). <b>NOT committed</b>.</li><li>Env vars — CI/CD, Docker config. <b>NOT committed</b>.</li><li>Key Vault — production secrets (connection strings, keys). <b>NOT committed</b>.</li><p>Rule: anything secret → User Secrets locally, Key Vault in prod. Never commit secrets.</p>
S04.07.Medium. What is OIDC federation in the context of GitHub Actions and Azure? Why is it better than storing a client secret in GitHub Secrets?	<p>OIDC federation lets GitHub Actions get a short-lived token from Azure AD per workflow run — no stored secrets. GitHub presents a JWT to Azure, Azure validates it against configured trust (repo, branch, environment), and issues an access token.</p><p>Better than stored client secrets because:</p><ul><li>No secret to rotate, leak, or expire.</li><li>Tokens are short-lived (minutes).</li><li>Scoped to specific repos/branches — forks can't abuse it.</li><li>All token requests are audit-logged in Azure AD.</li></ul><p>Setup: Azure AD app registration + federated credential pointing to GitHub's OIDC provider.</p>
S04.08.Medium. Your <code>dotnet test</code> passes locally but fails on CI. The error is "Unable to find testhost." Name three common causes and how you'd debug each.	<li>Missing <code>Microsoft.NET.Test.Sdk</code> NuGet — required for test discovery. Check <code>.csproj</code>.</li><li>SDK version mismatch — CI has older SDK that doesn't support the target framework. Fix: add <code>global.json</code> or specify SDK version in CI.</li><li>Runtime identifier mismatch — test project targets a framework not installed on CI agent.</li><p>Debug: run <code>dotnet test --verbosity detailed</code>, check <code>dotnet --info</code> on CI, ensure all test projects reference the SDK package.</p>
S04.09.Medium. You rotate the Stripe secret key in Azure Key Vault. Your production app still uses the old key. Why? How do you fix it without downtime?	<ul><li><b>Root cause</b> — Key Vault config is loaded once at startup and cached. The app doesn't poll for changes.</li><li><b>Fix</b> — set <code>AzureKeyVaultConfigurationOptions.ReloadInterval</code> (e.g. 5 min); use <code>IOptionsMonitor<StripeSettings></code> to receive live updates without restart.</li><li><b>Zero-downtime rotation</b> — add the new key in Key Vault, wait for the reload interval to propagate, then deactivate the old key. Or use a blue-green deployment swap.</li></ul>
S04.10.Medium. CI ran <code>dotnet test</code> and 12 tests failed on the first push — but they passed locally. What categories of bugs cause this and how do you investigate?	<p>Categories:</p><li><b>Environment-dependent</b>: hardcoded paths (<code>C:\...</code>), timezone assertions, culture-specific string formatting.</li><li><b>Missing dependencies</b>: database not available, no test data seeded, missing env vars.</li><li><b>Race conditions</b>: async tests with timing assumptions, tests sharing static state.</li><li><b>Test ordering</b>: tests depend on execution order or shared mutable state.</li><li><b>Resource conflicts</b>: port conflicts, file locks.</li><p>Debug: read CI log line by line, run locally with <code>--verbosity detailed</code>, reproduce in Docker.</p>
S04.11.Medium. Your <code>dotnet test</code> in CI passes but <code>ng build</code> fails. The deploy job still runs. What's missing?	<p>The deploy job only depends on the backend test job (or has no <code>needs</code> at all).</p><p>Fix: add separate <code>build-frontend</code> job with <code>ng build</code>, and make <code>deploy</code> need BOTH:</p><pre><code>deploy:   needs: [test-backend, build-frontend]</code></pre><p>If either fails, deploy is skipped.</p>
S04.12.Hard. Design a CI/CD pipeline for an e-commerce app with: staging and production environments, database migrations, feature flags, rollback capability, and zero-downtime deployment. Include the YAML structure and explain each step.	<p>Pipeline: build → test → deploy-staging (auto on <code>develop</code>) → deploy-prod (manual approval on <code>main</code>).</p><p>DB migrations run as a separate step BEFORE deploy — must be backward-compatible (add columns, not rename). Feature flags (LaunchDarkly/Azure App Config) decouple deploy from release.</p><p>Zero-downtime: Azure deployment slots — deploy to staging slot, warm up, swap to production. Rollback: swap back.</p><p>Structure migrations to be additive so rollback doesn't break the DB.</p><pre><code>jobs:   build-and-test:     runs-on: ubuntu-latest     steps: [checkout, build, test]    deploy-staging:     needs: [build-and-test]     if: github.ref == 'refs/heads/develop'     environment: staging     steps: [migrate-staging-db, deploy-to-staging-slot]    deploy-prod:     needs: [build-and-test]     if: github.ref == 'refs/heads/main'     environment: production  # requires manual approval     steps: [migrate-prod-db, deploy-to-prod-slot, swap-slots]</code></pre>
S04.13.Hard. Your Key Vault is in Azure region West Europe. Your app is in East US. Every startup takes 2 seconds because of key loading latency. On a cold start, it takes 8 seconds. How do you optimize this?	<li><b>Regional replication</b>: create Key Vault in East US (same region as app).</li><li><b>Azure App Configuration</b> as intermediary — cache secrets with Key Vault references, faster reads.</li><li><b>Reduce secret count</b>: combine related secrets into one JSON blob.</li><li><b>Startup warm-up</b>: Azure App Service warm-up path, health check endpoint.</li><li><b>Cache with long <code>ReloadInterval</code></b> (30min) — don't reload frequently.</li><li><b>Use <code>ManagedIdentityCredential</code> directly</b> instead of <code>DefaultAzureCredential</code> (skips the auth chain).</li>
S04.14.Hard. A junior developer accidentally pushes a secret to GitHub. The secret is now in the git history. What are the immediate steps (first 5 minutes)? What are the follow-up steps? Why is <code>git rebase</code> not enough?	<p><b>First 5 minutes:</b> ROTATE THE SECRET immediately (new API key, new password). Revoke the old one. The secret is compromised the moment it's pushed — bots scrape GitHub in seconds.</p><p><b>Follow-up:</b> use BFG Repo-Cleaner or <code>git filter-repo</code> to remove from history, force-push, have all contributors re-clone.</p><p><b>Why rebase isn't enough:</b> the old commits exist in reflog, forks, GitHub's cache, any CI that fetched the repo, and GitHub's event API.</p><p><b>Prevention:</b> <code>.gitignore</code>, <code>git-secrets</code> pre-commit hooks, GitHub secret scanning.</p>
S04.15.Hard. Your team wants to add a staging environment. Staging deploys on merge to <code>development</code>, production on merge to <code>main</code>. Both use Key Vault but with different secrets. Design the pipeline and config changes.	<p><b>Pipeline:</b> two GitHub environments (<code>staging</code>, <code>production</code>) with separate OIDC credentials. Two Key Vaults: <code>kv-myapp-staging</code>, <code>kv-myapp-prod</code>.</p><p>Workflow: push to <code>development</code> → build → test → deploy to staging (auto). PR to <code>main</code> → build → test → deploy to prod (requires approval).</p><p>Each deploy job uses <code>environment:</code> to select the right secrets. Config: <code>appsettings.Staging.json</code> + staging Key Vault, <code>appsettings.Production.json</code> + prod Key Vault. <code>ASPNETCORE_ENVIRONMENT</code> set per deployment slot.</p>
S04.16.Hard. You need to add secret rotation without downtime. The current setup loads secrets at startup only. Design a solution. Compare: polling <code>ReloadInterval</code>, blue-green deploy, and <code>IOptionsSnapshot<T></code>.	<li><b><code>ReloadInterval</code> (e.g., 5min) + <code>IOptionsMonitor<T></code></b>: provider polls Key Vault in background, <code>IOptionsMonitor.OnChange</code> updates cached values. Simple, no restart needed. Risk: up to N minutes of stale secrets.</li><li><b>Blue-green deploy</b>: deploy new instance with fresh config, swap traffic. Zero stale time but requires a deployment.</li><li><b><code>IOptionsSnapshot<T></code></b>: Scoped, re-reads from providers per request — but only sees changes if the provider has already reloaded.</li><p><b>Best approach:</b> <code>ReloadInterval</code> + <code>IOptionsMonitor<T></code> for live rotation + blue-green for major changes.</p>
