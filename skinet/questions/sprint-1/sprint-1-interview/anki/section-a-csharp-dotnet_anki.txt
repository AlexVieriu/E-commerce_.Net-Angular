S01.01.Easy. What is the difference between <code>readonly</code> and <code>const</code> in C#? When would you use each?	<ul><li><b><code>const</code></b> — compile-time, implicitly static, must be assigned at declaration, only works for primitives/strings.</li><li><b><code>readonly</code></b> — runtime, can be set in the constructor, works for any type.</li></ul><p>Use <code>const</code> for true constants (e.g. <code>Math.PI</code>), <code>readonly</code> for values set at construction (config, injected dependencies).</p><p>https://claude.ai/chat/b3e1ad34-130d-4c89-ae3f-2b0718974b59</p>
S01.02.Easy. What does <code>sealed</code> do on a class? Why would you seal a class?	<p><code>sealed</code> prevents inheritance. Reasons to use it:</p><ul><li><b>Security</b> — prevent malicious subclass overrides.</li><li><b>Performance</b> — JIT can devirtualize and inline calls.</li><li><b>Design clarity</b> — signals the class is not designed for extension.</li></ul><p>Many framework types are sealed — e.g. <code>string</code>.</p>
S01.03.Easy. What is the difference between <code>IEnumerable<T></code> and <code>IList<T></code>? When do you choose one over the other?	<ul><li><b><code>IEnumerable<T></code></b> — read-only, forward-only, lazy — supports deferred execution.</li><li><b><code>IList<T></code></b> — adds indexing, <code>Count</code>, <code>Add</code>/<code>Remove</code> — materialized in memory.</li></ul><p>Return <code>IEnumerable<T></code> when consumers only iterate; use <code>IList<T></code> when you need random access or mutation.</p><p>https://claude.ai/chat/46c27fdb-6053-4e9c-9fcc-755d1970603d</p>
S01.04.Easy. What does <code>async void</code> do differently than <code>async Task</code>? Why is <code>async void</code> dangerous?	<ul><li><b><code>async void</code></b> — can't be awaited, exceptions crash the process (no caller to catch them), fire-and-forget.</li><li><b><code>async Task</code></b> — awaitable, exceptions propagate normally to the caller.</li></ul><p><code>async void</code> is only acceptable for event handlers.</p><p>https://claude.ai/chat/5bd1eb7b-a65f-42ec-80a8-9043d925b1e8</p>
S01.05.Easy. Explain boxing and unboxing. Give one example where boxing happens implicitly in C#.	<p><b>Boxing</b> — wraps a value type in a heap-allocated <code>object</code> wrapper. <b>Unboxing</b> — extracts the value back out (must be the exact original type).</p><p><b>Implicit boxing happens in:</b></p><ul><li>Direct assignment: <code>object o = 42;</code></li><li>Collections: <code>ArrayList.Add(42)</code> (legacy non-generic)</li><li>String formatting: <code>string.Format("{0}", 42)</code></li><li>Interface casting: <code>IComparable c = 42;</code> (int implements IComparable)</li></ul><p>Example:</p><pre><code>int x = 42; object o = x;  // Boxing — x is copied to heap int y = (int)o;  // Unboxing — must cast back to int, not uint</code></pre><p>If you try <code>uint z = (uint)o;</code> on an <code>int</code>-boxed value, you get <code>InvalidCastException</code>.</p>
S01.06.Medium. What does this code print and why?  ``<code>csharp string a = "hello"; string b = "hello"; string c = new string("hello".ToCharArray());  Console.WriteLine(a == b); Console.WriteLine(a == c); Console.WriteLine(ReferenceEquals(a, b)); Console.WriteLine(ReferenceEquals(a, c)); </code>``	<p>Output: <code>True, True, True, False</code></p><ul><li><code>==</code> on strings is <b>value comparison</b> (operator overloaded) — always compares content, not reference.</li><li><code>a</code> and <code>b</code> point to the <b>same interned string literal</b> — <code>ReferenceEquals</code> is <code>true</code>.</li><li><code>c</code> is <code>new string(...)</code> — <b>new heap object</b> with the same content — <code>==</code> is <code>true</code> but <code>ReferenceEquals</code> is <code>false</code>.</li></ul>
S01.07.Medium. You have a <code>List<Order></code> with 50,000 orders. Find all where <code>Status == "Shipped"</code> and <code>Total > 100</code>, sorted by <code>Total</code> descending, top 10. Write the LINQ query. Does LINQ evaluate lazily or eagerly? When does it execute?	<pre><code>var result = orders     .Where(o =&gt; o.Status == "Shipped" &amp;&amp; o.Total &gt; 100)     .OrderByDescending(o =&gt; o.Total)     .Take(10)     .ToList();</code></pre><p>The query builds lazily via <code>Where</code>, <code>OrderByDescending</code>, <code>Take</code> — these return <code>IEnumerable<T></code> and compose a pipeline. Execution is deferred until <code>.ToList()</code> forces materialization. Without <code>.ToList()</code>, iterating the result also triggers execution. <code>OrderByDescending</code> must buffer all matching items to sort.</p>
S01.08.Medium. What is the difference between <code>Task.Run()</code> and <code>Task.Factory.StartNew()</code>? When would you explicitly choose one over the other?	<ul><li><b><code>Task.Run</code></b> — shorthand with safe defaults: thread pool, <code>DenyChildAttach</code>, <code>TaskScheduler.Default</code>. Use for 99% of cases.</li><li><b><code>Task.Factory.StartNew</code></b> — fine-grained control over <code>LongRunning</code>, custom schedulers, creation options.</li></ul><p>Choose <code>StartNew</code> only for long-running CPU-bound work or custom task schedulers.</p>
S01.09.Medium. Explain the difference between <code>ConfigureAwait(false)</code> and the default <code>ConfigureAwait(true)</code>. In what context does this matter? Does it matter in ASP.NET Core?	<ul><li><b><code>ConfigureAwait(true)</code></b> (default) — resumes on the captured <code>SynchronizationContext</code>. Needed in WPF/WinForms to get back to the UI thread after an <code>await</code>.</li><li><b><code>ConfigureAwait(false)</code></b> — resumes on any thread pool thread. Avoids the overhead of capturing/restoring the context.</li></ul><p><b>In ASP.NET Core:</b> no <code>SynchronizationContext</code> exists, so <code>ConfigureAwait(false)</code> has no practical effect. Still use it in <b>library code</b> for portability across UI frameworks.</p>
S01.10.Medium. What is the <code>IDisposable</code> pattern? What happens if you forget to dispose an <code>HttpClient</code> in a loop? How does <code>IHttpClientFactory</code> solve this?	<p><code>IDisposable</code> provides deterministic cleanup via <code>Dispose()</code> / <code>using</code>.</p><p><b>Problem — <code>HttpClient</code> in a loop:</b></p><ul><li>Creating/disposing <code>HttpClient</code> per request causes <b>socket exhaustion</b> — sockets linger in <code>TIME_WAIT</code> for minutes.</li><li>Even though <code>HttpClient</code> implements <code>IDisposable</code>, disposing it closes the underlying <code>HttpMessageHandler</code> prematurely.</li></ul><p><b><code>IHttpClientFactory</code> solution:</b></p><ul><li>Pools <code>HttpMessageHandler</code> instances (2-minute default lifetime).</li><li>Lets you call <code>CreateClient()</code> cheaply — no socket exhaustion.</li><li>Recycles handlers automatically to respect DNS changes.</li></ul>
S01.11.Medium. What does this code do? Is there a bug?  ``<code>csharp public async Task<List<Product>> GetAllAsync() {     var tasks = productIds.Select(id => GetByIdAsync(id));     var results = await Task.WhenAll(tasks);     return results.ToList(); } </code>``	<p>It fetches all products <b>in parallel</b> using <code>Task.WhenAll</code>.</p><p><b>Subtle bugs:</b></p><li><b>No throttling</b> — <code>Select</code> with an async lambda creates ALL tasks immediately. With a large <code>productIds</code>, this fires all requests simultaneously — could overwhelm the DB or downstream service.</li><li><b>Multiple enumeration risk</b> — if <code>productIds</code> is a lazy <code>IEnumerable</code>, iterating it creates two sets of tasks (once for <code>Select</code>, once for <code>WhenAll</code>).</li><p><b>Fix:</b> use <code>SemaphoreSlim</code> to cap concurrency, or <code>Parallel.ForEachAsync(productIds, new ParallelOptions { MaxDegreeOfParallelism = 10 }, ...)</code> .</p>
S01.12.Medium. What is the difference between <code>throw;</code> and <code>throw ex;</code> in a catch block? Why does it matter?	<ul><li><b><code>throw;</code></b> — re-throws the original exception, <b>preserving the full stack trace</b>. Always use this.</li><li><b><code>throw ex;</code></b> — creates a new throw point at the <code>catch</code> block, <b>resetting the stack trace</b>. You lose where the exception originally occurred.</li></ul><pre><code>catch (Exception ex) {     _logger.LogError(ex, "Failed");     throw;     // ✅ original stack trace preserved     // throw ex; ❌ stack trace reset — root cause hidden }</code></pre>
S01.13.Medium. You have a service registered as <code>Scoped</code>. A <code>Singleton</code> service tries to inject it. What happens? What is the name of this problem?	<p>This is called a <b>Captive Dependency</b>. The Scoped service gets captured by the Singleton and lives forever — it never gets disposed/recreated per request. This causes stale data, thread-safety issues, and DbContext tracking bugs. ASP.NET Core throws an <code>InvalidOperationException</code> if <code>ValidateScopes</code> is enabled (default in Development).</p>
S01.14.Hard. Explain the .NET garbage collector's generational model. What are Gen 0, Gen 1, Gen 2? What triggers a collection? What is the Large Object Heap and why does it matter?	<p><b>Generations:</b></p><ul><li><b>Gen 0</b> — short-lived objects (locals, temp strings). Collected frequently, very fast.</li><li><b>Gen 1</b> — buffer between short/long-lived. Collected less often.</li><li><b>Gen 2</b> — long-lived objects (statics, caches). Collected rarely, expensive.</li></ul><p>Objects <b>surviving a collection are promoted</b> to the next generation.</p><p><b>What triggers a collection:</b> Gen 0 budget exceeded → Gen 0 GC fires; may cascade to Gen 1/2.</p><p><b>Large Object Heap (LOH):</b></p><ul><li>Objects ≥ <b>85 KB</b> skip Gen 0/1 and go directly to the LOH.</li><li>Collected only with Gen 2 (rare).</li><li><b>Not compacted by default</b> — can cause memory fragmentation.</li><li>Force compaction: <code>GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce</code>.</li></ul>
S01.15.Hard. What is <code>Span<T></code> and why was it introduced? How does it reduce allocations compared to <code>Substring()</code>? Write a code example that parses a comma-separated string using <code>Span<T></code> without allocating new strings.	<p><code>Span<T></code> is a stack-only ref struct providing a type-safe view over contiguous memory (arrays, strings, native buffers) without copying. <code>Substring()</code> allocates a new string each time; <code>Span<T>.Slice()</code> just moves pointers — zero allocation. Key: <code>Span<T></code> can't be stored on the heap (no class fields, no async), enabling safe stack-only memory access.</p><pre><code>ReadOnlySpan&lt;char&gt; input = "alice,bob,carol"; while (input.Length &gt; 0) {     int comma = input.IndexOf(',');     ReadOnlySpan&lt;char&gt; name = comma == -1 ? input : input.Slice(0, comma);     Console.WriteLine(name.ToString());     input = comma == -1 ? ReadOnlySpan&lt;char&gt;.Empty : input.Slice(comma + 1); }</code></pre>
S01.16.Hard. You see this in a code review. What are the two subtle problems? How would you fix each?  ``<code>csharp public class OrderProcessor {     private static readonly HttpClient _client = new HttpClient();      public async Task ProcessAsync(Order order)     {         var response = await _client.PostAsJsonAsync("/api/process", order);         response.EnsureSuccessStatusCode();     } } </code>``	<p><b>Problem 1:</b> Static <code>HttpClient</code> never refreshes DNS — if the target IP changes, requests go to the stale address. Fix: use <code>IHttpClientFactory</code> or set <code>PooledConnectionLifetime</code>.</p><p><b>Problem 2:</b> No base address, no timeout, no resilience. <code>EnsureSuccessStatusCode</code> throws a generic exception with no detail. Fix: configure <code>BaseAddress</code>, add Polly retry policy, read error body before throwing.</p>
S01.17.Hard. Explain <code>ValueTask<T></code> vs <code>Task<T></code>. When is <code>ValueTask<T></code> faster? When is it dangerous? What happens if you <code>await</code> a <code>ValueTask<T></code> twice?	<ul><li><b><code>Task<T></code></b> — always allocates a heap object, even if the result is already available.</li><li><b><code>ValueTask<T></code></b> — wraps either a <code>T</code> value (stack-allocated) or a <code>Task<T></code>. <b>Avoids allocation</b> when the result is ready synchronously (e.g. cache hit).</li></ul><p><b>When <code>ValueTask<T></code> is faster:</b> hot paths where the method frequently completes synchronously (reading from a memory cache before hitting async I/O).</p><p><b>Dangers:</b></p><ul><li><b>Must be awaited exactly once.</b> Awaiting twice is <b>undefined behavior</b> — may throw, return the wrong value, or corrupt state.</li><li>Cannot use <code>.Result</code> or <code>.GetAwaiter()</code> concurrently.</li><li><b>Fix:</b> call <code>.AsTask()</code> if you need to store, share, or await multiple times.</li></ul>
S01.18.Hard. What are <code>record</code> types in C#? How do they differ from classes in terms of equality, immutability, and generated code? What is <code>with</code> expression? When would you use <code>record struct</code> vs <code>record class</code>?	<p><b>Key features of <code>record</code>:</b></p><ul><li><b>Value-based equality</b> — all properties compared (not reference).</li><li>Auto-generated: human-readable <code>ToString()</code>, <code>Deconstruct()</code>, <code>==</code> / <code>!=</code>.</li><li><b><code>with</code> expression</b> — non-destructive mutation: <code>var b = a with { Name = "Bob" };</code></li></ul><p><b><code>record class</code> vs <code>record struct</code>:</b></p><ul><li><b><code>record class</code></b> — reference type; immutable via <code>init</code> properties.</li><li><b><code>record struct</code></b> — value type; good for small, frequently-copied data (avoids heap allocation).</li></ul><p><b>When to use:</b> DTOs, domain events, immutable value objects.</p>
S01.19.Hard. You have a hot code path that creates thousands of small temporary objects per request. The GC is causing latency spikes. What strategies can you use to reduce GC pressure? Name at least four.	<li><code>ArrayPool<T>.Shared</code> / <code>ObjectPool<T></code> — rent and return instead of alloc/GC.</li><li><code>Span<T></code> + <code>stackalloc</code> — stack allocation, zero GC.</li><li>Use structs for small, short-lived data.</li><li><code>StringBuilder</code> pooling or <code>string.Create</code>.</li><li>Avoid LINQ in hot paths (allocates iterators/delegates).</li><li><code>RecyclableMemoryStream</code> for streams.</li><li>Cache frequently-used objects.</li><li>Use <code>ref struct</code> / <code>ref returns</code> to avoid copies.</li>
