S03.01.Easy. What does <code>HttpOnly</code> on a cookie prevent? What attack does it mitigate?	<ul><li><b>Prevents</b> JavaScript from accessing the cookie via <code>document.cookie</code>.</li><li><b>Mitigates</b> XSS-based session theft — even if an attacker injects script, they can't read the auth cookie.</li><li>The cookie is still sent automatically by the browser with every HTTP request.</li></ul>
S03.02.Easy. What is the difference between authentication and authorization?	<ul><li><b>Authentication</b> — WHO are you? (verifying identity — login, token, certificate).</li><li><b>Authorization</b> — WHAT can you do? (checking permissions — roles, policies, claims).</li><li>Auth happens first — you must know WHO before deciding WHAT they can access.</li><li><b>401</b> = not authenticated. <b>403</b> = authenticated but not authorized.</li></ul>
S03.03.Easy. What does <code>SameSite=Strict</code> protect against?	<ul><li><b>Prevents</b> the browser from sending the cookie on any cross-site request (links, forms, images).</li><li><b>Protects against CSRF</b> — an attacker's page can't trigger authenticated actions because the cookie is never sent.</li><li><b>Downside</b> — users clicking links from external sites (email, social media) arrive unauthenticated.</li></ul>
S03.04.Medium. Explain the three <code>SameSite</code> cookie values: <code>Strict</code>, <code>Lax</code>, and <code>None</code>. For each, describe when the browser sends the cookie and what attack it prevents or allows.	<p>| Value | Browser sends cookie | CSRF protection | Downside |</p><p>|---|---|---|---|</p><p>| <b><code>Strict</code></b> | Same-site requests only | Maximum | Links from email/social arrive unauthenticated |</p><p>| <b><code>Lax</code></b> (default) | Same-site + top-level GET navigation | Good | POST/AJAX/iframe from other origins blocked |</p><p>| <b><code>None</code></b> | All cross-site requests | None | Requires <code>Secure</code> flag; needed for OAuth, iframes |</p><p><b>Rule:</b> use <code>Lax</code> for most apps. Use <code>None</code> only when cross-site cookies are explicitly required (e.g. embedded Stripe form).</p>
S03.05.Medium. A user reports: "I log in successfully, but every API call after that returns 401." The login endpoint returns 200. What are the top 5 things you check?	<li>Cookie not being sent: check Domain, Path, SameSite, Secure flags — browser may silently drop it.</li><li>CORS: <code>withCredentials: true</code> on client AND <code>AllowCredentials()</code> on server (can't use wildcard origin).</li><li>Middleware order: <code>UseAuthentication</code> before <code>UseAuthorization</code>.</li><li>Token expired or clock skew.</li><li>Scheme mismatch: authenticating with cookies but API expects Bearer, or wrong <code>DefaultAuthenticateScheme</code>.</li>
S03.06.Medium. What is <code>SecurityStamp</code> in ASP.NET Identity? When is it updated? How does the cookie middleware use it? What happens if you set <code>SecurityStampValidatorOptions.ValidationInterval = TimeSpan.Zero</code>?	<ul><li><b><code>SecurityStamp</code></b> — a GUID that changes whenever security-sensitive data changes (password, roles, 2FA, email).</li><li>Cookie middleware validates the stamp against the DB periodically (default every 30 min). Mismatch = sign out.</li><li><b><code>TimeSpan.Zero</code></b> — validates on every request: immediate invalidation, but a DB hit per request (performance cost).</li></ul>
S03.07.Medium. What is <code>DefaultAzureCredential</code>? In Azure App Service, which auth method fires? Locally? What's the fixed order it tries?	<p><code>DefaultAzureCredential</code> is a chained credential that tries auth methods in order:</p><li>EnvironmentCredential</li><li>WorkloadIdentityCredential</li><li>ManagedIdentityCredential</li><li>AzureCLICredential</li><li>VisualStudioCredential</li><li>AzurePowerShellCredential</li><p>In Azure App Service: Managed Identity fires. Locally: Azure CLI (<code>az login</code>) or Visual Studio. This lets the same code work in dev and prod without changes.</p>
S03.08.Medium. Why does <code>SlidingExpiration = false</code> matter for security? What's the risk if sliding expiration is enabled and an attacker steals the cookie?	<ul><li><b>Sliding = true</b> — resets the cookie lifetime on every request. An attacker who steals the cookie can keep it alive indefinitely by making periodic requests.</li><li><b>Sliding = false</b> — the cookie has a fixed absolute expiry regardless of activity, limiting the stolen cookie's window of use.</li></ul><p>Best practice: <code>SlidingExpiration = false</code> with <code>ExpireTimeSpan = TimeSpan.FromHours(24)</code>.</p>
S03.09.Medium. A new developer clones the repo and runs <code>dotnet run</code>. They get <code>StripeSettings:SecretKey is not configured</code>. What do they do? Why can't they put it in <code>appsettings.json</code>?	<ul><li>Run <code>dotnet user-secrets set "StripeSettings:SecretKey" "sk_test_..."</code>.</li><li>User Secrets stores values in a per-user JSON file <b>outside the repo</b> (<code>%APPDATA%/Microsoft/UserSecrets/</code>).</li><li><b>Can't use <code>appsettings.json</code></b> — it's committed to git; secrets in git history are permanent and public.</li><li><b>Production</b> — use environment variables or Azure Key Vault with Managed Identity.</li></ul>
S03.10.Hard. A penetration tester finds that your <code>SameSite=Strict</code> cookie is not sent when a user clicks a link from Gmail to your site. The user lands unauthenticated. The product team says this is unacceptable UX. How do you fix it? What security do you lose? How do you compensate?	<p>Switch to <code>SameSite=Lax</code> — it sends the cookie on top-level GET navigations (link clicks) but blocks cross-site POST/AJAX.</p><p>You lose: protection against cross-site GET-based actions (but GETs should be idempotent anyway).</p><p>Compensate: ensure state-changing operations use POST + anti-forgery token.</p><p>Advanced: two-cookie pattern — Lax cookie for reading, Strict cookie required for mutations.</p>
S03.11.Hard. Your cookie has <code>SameSite=Strict</code>, <code>HttpOnly</code>, and <code>Secure</code>. A colleague claims the app is immune to session hijacking. List every remaining attack vector and mitigation for each.	<p>Still vulnerable to:</p><li><b>XSS</b> — can't read cookie but CAN make same-origin requests as the user. Mitigation: CSP, input sanitization.</li><li><b>Session fixation</b> — attacker pre-sets session ID. Mitigation: regenerate session on login.</li><li><b>Physical/malware access</b> to the device. Mitigation: short absolute expiry, 2FA.</li><li><b>TLS misconfiguration</b> (mixed content). Mitigation: HSTS, HTTPS everywhere.</li><li><b>Subdomain takeover</b> — cookie scoped to <code>.example.com</code> accessible from compromised subdomain. Mitigation: scope cookie to exact domain.</li><li><b>Browser extensions</b> with elevated permissions. Mitigation: nothing practical.</li><p>Not immune — defense-in-depth is essential.</p>
S03.12.Hard. Explain how ASP.NET Identity's password hashing works under the hood. What algorithm does it use? What is key stretching? What is a salt? Why is <code>bcrypt</code>/<code>PBKDF2</code> better than <code>SHA256(password + salt)</code> for passwords? How many iterations does Identity use by default?	<ul><li><b>Algorithm</b> — PBKDF2 with HMAC-SHA512 (v3 format).</li><li><b>Salt</b> — random 128-bit per user; prevents rainbow tables (same password hashes differently for each user).</li><li><b>Key stretching</b> — runs the hash N times (100K+ iterations, 600K in .NET 8); intentionally slow to defeat brute force.</li><li><b>Why not SHA256?</b> — too fast; GPUs can try billions of hashes/sec.</li><li><b>Bcrypt/Argon2</b> — even stronger (memory-hard), harder to attack with GPU farms.</li></ul>
S03.13.Hard. A user reports: "I changed my password but I'm still logged in on my phone from yesterday." Why? How do you fix it? What's the tradeoff?	<ul><li><b>Cause</b> — the cookie middleware validates the <code>SecurityStamp</code> only every 30 min by default. The password change updates the stamp, but the phone's cookie isn't re-validated until the next interval.</li><li><b>Fix</b> — reduce <code>SecurityStampValidatorOptions.ValidationInterval</code> (e.g. to 1 minute).</li><li><b>Tradeoff</b> — shorter interval = more DB hits per request; <code>TimeSpan.Zero</code> = every request (expensive at scale).</li><li><b>Better</b> — cache the stamp in Redis with a 1-minute TTL to get fast invalidation without per-request DB calls.</li></ul>
S03.14.Hard. Compare three approaches to storing session state: (1) encrypted cookie, (2) server-side session with Redis, (3) JWT in localStorage. For each: where is state stored, size limit, how do you revoke, XSS/CSRF attack surface?	<p>| | Encrypted cookie | Redis session | JWT in localStorage |</p><p>|---|---|---|---|</p><p>| State stored | In the cookie (~4KB) | Server (Redis), small session ID cookie | Client (localStorage) |</p><p>| Revocation | SecurityStamp / key rotation | Delete Redis key — instant | Blacklist required (defeats stateless) |</p><p>| XSS surface | Safe — HttpOnly blocks JS | Safe — HttpOnly session cookie | Vulnerable — JS can read localStorage |</p><p>| CSRF surface | Mitigated by SameSite | Mitigated by SameSite | Immune — not auto-sent by browser |</p><p>Cookies + Redis is the most secure combo.</p>
S03.15.Hard. You need to add MFA to your current cookie-based Identity setup. What changes in the backend, frontend, and user flow? What does <code>PasswordSignInAsync</code> return when MFA is required?	<p><code>PasswordSignInAsync</code> returns <code>SignInResult.TwoFactorRequired</code> — NOT a successful sign-in.</p><p><b>Backend:</b> generate TOTP key (<code>GenerateNewAuthenticatorKey</code>), store it, verify codes with <code>VerifyTwoFactorTokenAsync</code>. Call <code>TwoFactorAuthenticatorSignInAsync</code> to issue the cookie after verification.</p><p><b>Frontend:</b> detect <code>RequiresTwoFactor</code> in the response, redirect to 2FA page, collect code, POST to verify endpoint.</p><p><b>User flow:</b> email+password → 2FA prompt → 6-digit code → authenticated session.</p><p>Also generate recovery codes as fallback. Store the 2FA key encrypted.</p>
