# C1 — [EASY][HIGH] What does HttpOnly on a cookie prevent? What does it NOT prevent?
# ────────────────────────────────────────────────────────────────────────────
<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><p><b>Prevents:</b> JavaScript accessing <code class="c">document.cookie</code>. An XSS payload cannot read the session token and exfiltrate it.</p><p><b>Does NOT prevent:</b></p><ul><li><b>CSRF (Cross-Site Request Forgery)</b> — browser attaches the cookie automatically on cross-site requests; no JS needed.</li><li>Fix: <code class="c">options.Cookie.SameSite = SameSiteMode.Strict;</code></li><li><b>Network interception (MITM)</b> — cookie travels in plaintext over HTTP.</li><li>Fix: <code class="c">options.Cookie.SecurePolicy = CookieSecurePolicy.Always;</code></li><li><b>XSS session abuse</b> — XSS makes authenticated API calls from the victim's tab; cookie attaches automatically even though JS can't read it.</li><li>Fix: CSP(Content Security Policy) header to block injected scripts from running.</li></ul><p><b>Practical impact:</b> <code class="c">HttpOnly</code> prevents <b>session hijacking</b> (steal token → replay from another machine), not <b>session abuse</b> (XSS makes requests from inside the victim's tab).</p><p><b>Full defence requires all three:</b></p><p>| Flag | Prevents | C# setting |</p><p>|---|---|---|</p><p>| <code class="c">HttpOnly</code> | Cookie theft via <code class="c">document.cookie</code> | <code class="c">options.Cookie.HttpOnly = true;</code> |</p><p>| <code class="c">Secure</code> | Cookie over HTTP (MITM capture) | <code class="c">options.Cookie.SecurePolicy = CookieSecurePolicy.Always;</code> |</p><p>| <code class="c">SameSite=Strict</code> | Cookie on cross-site requests (CSRF) | <code class="c">options.Cookie.SameSite = SameSiteMode.Strict;</code> |</p></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"<code class="c">HttpOnly</code> prevents XSS." <code class="c">HttpOnly</code> prevents cookie theft via XSS. XSS itself — arbitrary JavaScript execution — is still fully functional. The attacker just can't steal the token to another machine.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning that even with <code class="c">HttpOnly</code>, XSS can call <code class="c">fetch('/api/account/address', { method: 'PUT', body: ... })</code> from the victim's tab and the cookie is attached automatically. <code class="c">HttpOnly</code> only blocks <code class="c">document.cookie</code> — it doesn't prevent XSS-driven API abuse.</p></div></div>

A user who logs in at 9am is logged out at 9am the next day even if they were actively using the app at 8:59am.</li><li><b><code class="c">true</code>:</b> the expiry resets to <code class="c">ExpireTimeSpan</code> from the current time on each request. An active user never gets logged out.</li></ul><p><b>Security tradeoff:</b></p><ul><li><code class="c">false</code> is more secure: abandoned sessions expire predictably. An attacker with a stolen session token has at most 24h of access regardless of usage.</li><li><code class="c">true</code> is more user-friendly: no surprise logouts for active users. But a stolen session token remains valid indefinitely as long as anyone uses it — attacker-controlled activity extends the window.</li></ul><p>This project chose <code class="c">false</code> — e-commerce apps with stored payment info benefit from daily re-authentication. The UX cost (users log in once a day) is acceptable for the security gain.</p></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"<code class="c">SlidingExpiration = true</code> is always better UX." Not when the session can be stolen. Sliding expiration on a stolen session means indefinitely valid access — the attacker just keeps making requests to keep the token alive.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning PCI-DSS: payment card industry compliance requires re-authentication after periods of inactivity. <code class="c">SlidingExpiration = false</code> with a 24h absolute expiry satisfies this requirement. Banking and fintech apps use <code class="c">false</code> universally — session continuity is a security liability, not a feature.</p></div></div>

Answer</p><div class="ac"><ul><li><b><code class="c">Lax</code>:</b></li><li>Cookie <b>sent</b> on top-level navigations: link click, bookmark, address bar</li><li>Cookie <b>sent</b> on all same-site requests</li><li>Cookie <b>blocked</b> on cross-site background requests: <code class="c">fetch</code>, form POST, images loaded from another site</li><li>CSRF attacks rely on background requests → <code class="c">Lax</code> still blocks CSRF while keeping email links and social shares working</li><li>ASP.NET Core default since .NET 6</li><li><b><code class="c">Strict</code>:</b> cookie never order" email links:</b> a user receives an order confirmation email and clicks the link. The browser navigates from the email client's domain to <code class="c">skinet.com</code> — that's a cross-site navigation. <code class="c">Strict</code> means no session cookie attached → user sees the login page despite having an active session.</li></ol><ol><li><b>OAuth/Social login flows:</b> IdP (Google, GitHub) redirects back to your app after authentication. That redirect is cross-site. <code class="c">Strict</code> → cookie not attached on redirect → app sees user as unauthenticated after successful OAuth.</li></ol><ol><li><b>Bookmark/referral links from other sites:</b> sharing a product link on Twitter, clicking through an affiliate partner — all are cross-site navigations that <code class="c">Strict</code> blocks.</li></ol><p><b>Why this project uses <code class="c">Strict</code>:</b></p><ul><li>No OAuth (cookie-only auth, no external IdPs in scope)</li><li>The cost (re-login from email links) is acceptable</li><li>Maximum CSRF protection is the priority</li></ul></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"Always use <code class="c">Strict</code> for maximum security." The right choice depends on architecture. A site with OAuth login, email links, or affiliate traffic should use <code class="c">Lax</code> — <code class="c">Strict</code> would silently break user flows that require cross-site navigation.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Knowing that same-site is determined by <b>eTLD+1</b> (registrable domain), not the full hostname — so subdomains like <code class="c">app.skinet.com</code> + <code class="c">api.skinet.com</code> are same-site and <code class="c">Strict</code> won't block them, but <code class="c">app.skinet.com</code> + <code class="c">api.otherdomain.com</code> are cross-site and <code class="c">Strict</code> will.</p></div></div>

# ────────────────────────────────────────────────────────────────────────────
<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><p><code class="c">ConfigureApplicationCookie</code> modifies the options for <code class="c">IdentityConstants.ApplicationScheme</code> — the specific cookie scheme that <code class="c">AddIdentityApiEndpoints</code> registers internally. It's equivalent to:</p><pre class="p"><code>services.Configure&lt;CookieAuthenticationOptions&gt;(IdentityConstants.ApplicationScheme, options =&gt; ...);</code></pre><p><b>What breaks with <code class="c">AddCookie("MyCookie")</code>:</b></p><p>This registers a <b>new, separate</b> cookie scheme named <code class="c">"MyCookie"</code>. Identity's own scheme (<code class="c">"Identity.Application"</code>) remains with default settings:</p><ul><li><code class="c">HttpOnly = true</code> (default, fine)</li><li><code class="c">SecurePolicy = CookieSecurePolicy.SameAsRequest</code> (default — allows HTTP)</li><li><code class="c">SameSite = SameSiteMode.Lax</code> (default — less restrictive)</li><li><code class="c">ExpireTimeSpan = TimeSpan.FromDays(14)</code> (default — 2 weeks)</li></ul><p>Your hardened settings apply to <code class="c">"MyCookie"</code> — a scheme nothing uses. Identity continues using its unhardened scheme. You'd have a false sense of security.</p><p><b>Correct:</b></p><pre class="p"><code>services.ConfigureApplicationCookie(options =&gt; {<br>    options.Cookie.HttpOnly = true;<br>    options.Cookie.SecurePolicy = CookieSecurePolicy.Always;<br>    options.Cookie.SameSite = SameSiteMode.Strict;<br>    options.ExpireTimeSpan = TimeSpan.FromHours(24);<br>    options.SlidingExpiration = false;<br>});</code></pre></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"Use <code class="c">AddAuthentication().AddCookie(...)</code> with your settings." Same problem — that registers a new scheme. Identity uses <code class="c">IdentityConstants.ApplicationScheme</code>, not whatever name you choose.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning that <code class="c">IdentityConstants.ApplicationScheme</code> is the literal string <code class="c">"Identity.Application"</code> — you can verify in the ASP.NET Identity source. Calling <code class="c">ConfigureApplicationCookie</code> is the idiomatic helper; calling <code class="c">services.Configure&lt;CookieAuthenticationOptions&gt;("Identity.Application", ...)</code> is equivalent and more explicit about the scheme name.</p></div></div>
