S11.01.Easy. You join a project with 0% test coverage. You have one sprint to improve it. Where do you start? How do you decide what to test first? What coverage target is realistic?	<p><b>Where to start:</b> Core domain logic and the highest-risk business code — not utilities, DTOs, or CRUD. The code most likely to contain bugs and most expensive to break in production.</p><p><b>Priority order:</b></p><li><b>Domain entities with logic</b> — <code>Order.GetTotal()</code>, <code>Order.CanBeCancelled()</code>, price calculations. Pure C#, no mocks, fastest to write.</li><li><b>Critical service paths</b> — <code>OrderService.CreateOrderAsync</code> (stock check, price validation, order creation). Test happy path + stock out + price mismatch.</li><li><b>Payment flow</b> — <code>PaymentService</code> (mock Stripe). Money bugs are catastrophic.</li><li><b>Concurrency scenarios</b> — stock decrement race conditions. Use SQLite in-process, not InMemory.</li><p><b>What NOT to test first:</b> controllers (thin mapping), migrations (generated code), DTOs, simple repositories with no logic.</p><p><b>Realistic target in one sprint:</b></p><ul><li><b>Core entities:</b> 90%+ (they're trivial to test)</li><li><b>Application services (critical paths only):</b> 60-70%</li><li><b>Global coverage:</b> 40-50% is realistic and meaningful — better than 80% that includes test noise</li></ul><p>Document what's NOT covered and why, so the next sprint has a clear backlog.</p>
S11.02.Easy. You're debugging a race condition that only reproduces under high load. You can't reproduce it locally. What tools and strategies do you use?	<li><b>Add structured logging</b> around the critical section — log timestamp, thread ID, user ID, stock value before and after every read/write. Query logs (Seq, Application Insights) for two writes within milliseconds on the same product.</li><li><b>Check if <code>[ConcurrencyCheck]</code> is correctly applied</b> — if stock goes negative without a <code>DbUpdateConcurrencyException</code>, the attribute is missing or on the wrong property.</li><li><b>Write a load test</b> — use k6 or NBomber to reproduce the load locally. 100 concurrent requests for the same product should trigger the race within seconds.</li><li><b>Add metrics</b> — count <code>DbUpdateConcurrencyException</code> occurrences and retry counts via Application Insights custom metrics. A spike tells you WHEN and HOW OFTEN the race happens.</li><li><b>Use Azure Monitor / SQL Insights</b> — check for lock timeouts, deadlocks, long-running transactions in the production DB.</li><li><b>Review the code for the read-modify-write pattern</b> — any <code>FindAsync</code> followed by mutation followed by <code>SaveChangesAsync</code> without a concurrency token IS a race condition waiting to happen.</li>
S11.03.Easy. A colleague pushes a test with no <code>Verify</code> and says "it passes, ship it." How do you handle this in code review without being condescending?	<p><b>In code review — leave a specific, actionable comment:</b></p><p>> "Quick question on this test — what code change would break it? I was trying to figure out what regression it would catch, but I think it might pass even if we remove the Redis call entirely (no <code>Verify</code> on <code>StringSetAsync</code>). Could be wrong — what's your read? If I'm right, adding <code>_mockDb.Verify(x => x.StringSetAsync(...), Times.Once)</code> would make it a real safety net."</p><p><b>Key principles:</b></p><li><b>Ask a question, don't make an accusation</b> — "what code change would break this?" forces them to think it through without being told they're wrong</li><li><b>Show you might be wrong</b> — "could be wrong" reduces defensiveness</li><li><b>Offer the fix</b> — don't just point out the problem</li><li><b>Use the concrete example</b> — "remove the Redis call" is specific and falsifiable, not vague criticism</li><p>If they push back: pair on it. Delete the Redis call together, run the test. Let the outcome speak.</p>
