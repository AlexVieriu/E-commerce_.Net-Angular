S04.01.Easy. What is the difference between a unit test and an integration test? Which is faster? Which gives more confidence?	<ul><li><b>Unit test</b> — tests one class/method in isolation; all dependencies are mocked. Fast (milliseconds), deterministic, no I/O.</li><li><b>Integration test</b> — tests multiple real components together (e.g. service + EF Core + SQLite). Slower, but proves real components work together.</li></ul><p><b>Speed</b>: unit tests win. <b>Confidence</b>: integration tests win — mocks can lie, a real DB can't. Use both: unit tests for logic coverage, integration tests for data access and wiring.</p>
S04.02.Easy. What is the AAA pattern (Arrange, Act, Assert)?	<ul><li><b>Arrange</b> — set up the system under test, dependencies, and input data.</li><li><b>Act</b> — call the single method/operation being tested.</li><li><b>Assert</b> — verify the outcome matches expectations.</li></ul><p>One Act per test. If you have two Act sections, you have two tests. The pattern forces tests to be focused and readable.</p>
S04.03.Easy. What does <code>Mock<T></code> do in Moq? What is the difference between <code>Setup</code> and <code>Verify</code>?	<ul><li><b><code>Mock<T></code></b> — creates a fake implementation of interface <code>T</code> at runtime. By default all methods return default values (<code>null</code>, <code>0</code>, <code>false</code>). You control behavior via <code>Setup</code>.</li><li><b><code>Setup</code></b> — configures what the mock returns or does when a specific method is called. Runs during the Act.</li><li><b><code>Verify</code></b> — asserts after the Act that a specific method was (or was not) called with specific arguments. Without <code>Verify</code>, you have no proof the method was called.</li></ul><p><code>Setup</code> controls behavior. <code>Verify</code> proves the interaction happened.</p>
S04.04.Easy. What three properties make a test valuable vs noise?	<ul><li><b>Fast</b> — runs in milliseconds; slow tests get skipped.</li><li><b>Deterministic</b> — same result every run, regardless of time, order, or environment.</li><li><b>Meaningful</b> — fails when real bugs exist and passes only when the code is correct. A test that never fails (or fails randomly) is noise.</li></ul><p>A bonus fourth: <b>readable</b> — the intent is clear without comments; when it fails, you know exactly what broke.</p>
S04.05.Easy. When should you use <code>[ExcludeFromCodeCoverage]</code>? When is it a code smell?	<p><b>Legitimate uses:</b></p><ul><li>Auto-generated code (EF migrations, scaffolded files).</li><li>Boilerplate with no logic (DTOs, simple POCO constructors).</li><li>Infrastructure glue code that only runs with a real external system.</li></ul><p><b>Code smell when:</b></p><ul><li>Applied to business logic to inflate coverage numbers.</li><li>Used on a method because "it's hard to test" — that's a design problem.</li><li>Covering up untested error paths or edge cases.</li></ul><p>Rule: if a method has a branch, a calculation, or a decision — it should be tested, not excluded.</p>
S04.06.Medium. You have this test. Is it a good test? Why or why not?  ``<code>csharp [Fact] public async Task CreateOrder_ShouldWork() {     var result = await _service.CreateOrderAsync("buyer@test.com", _orderDto);     Assert.NotNull(result); } </code>``	<p><b>No — it's noise.</b> Problems:</p><ul><li><code>Assert.NotNull</code> only proves <i>something</i> was returned, not that it's correct.</li><li>No assertions on buyer email, order items, total, status, or any business behavior.</li><li>The test name "ShouldWork" communicates nothing about what "working" means.</li><li>No <code>Verify</code> — doesn't confirm the order was saved to the repository.</li><li>Will pass even if the method returns <code>new Order()</code> with all default values.</li></ul><p>A test that doesn't constrain behavior provides false confidence.</p>
S04.07.Medium. Your Moq <code>Setup</code> uses <code>It.IsAny<TimeSpan?>()</code> but the production code calls an overload that takes <code>Expiration</code> (not <code>TimeSpan?</code>). The test passes. You delete the production method. The test still passes. Explain the full chain of events. How do you prevent this?	<p><b>Chain of events:</b></p><li><code>Setup</code> targets <code>StringSetAsync(..., TimeSpan?, ...)</code> — the <code>TimeSpan?</code> overload.</li><li>Production code calls <code>StringSetAsync(..., Expiration, ...)</code> — a <b>different overload</b>.</li><li>Moq finds no matching setup → falls back to <b>loose mock default</b> → returns <code>false</code>.</li><li>Production code proceeds as if the setup never existed.</li><li>Delete the production method → test still compiles (calling through mock) → <code>Setup</code> still targets dead air → test still passes.</li><p><b>Prevention:</b></p><ul><li><b><code>MockBehavior.Strict</code></b> — any unmocked call throws immediately, exposing the overload mismatch.</li><li><b><code>Verify</code></b> — explicitly assert the exact overload was called with exact arguments.</li><li><b>Check IntelliSense</b> — confirm the method signature before writing <code>Setup</code>.</li></ul>
S04.08.Medium. Write a test for this method. Include happy path and at least two edge cases:  ``<code>csharp public decimal GetTotal() {     return Subtotal - Discount + DeliveryMethod.Price; } </code>``	<pre><code>[Fact] public void GetTotal_WithSubtotalDiscountAndDelivery_ReturnsCorrectSum() {     var order = new Order     {         Subtotal = 100m,         Discount = 20m,         DeliveryMethod = new DeliveryMethod { Price = 5m }     };     Assert.Equal(85m, order.GetTotal()); // 100 - 20 + 5 }  [Fact] public void GetTotal_WhenDiscountExceedsSubtotal_ReturnsNegativeTotal() {     var order = new Order     {         Subtotal = 50m,         Discount = 60m,         DeliveryMethod = new DeliveryMethod { Price = 5m }     };     Assert.Equal(-5m, order.GetTotal()); // reveals whether negative totals are intended }  [Fact] public void GetTotal_WhenDiscountIsZero_ReturnsSubtotalPlusDelivery() {     var order = new Order     {         Subtotal = 100m,         Discount = 0m,         DeliveryMethod = new DeliveryMethod { Price = 10m }     };     Assert.Equal(110m, order.GetTotal()); }</code></pre>
S04.09.Medium. What is the difference between <code>mockDb.Setup(...)</code> and <code>mockDb.As<IDatabaseAsync>().Setup(...)</code>? When do you need the <code>As<></code> cast? What happens if you use the wrong one?	<ul><li><b><code>mockDb.Setup(...)</code></b> — sets up methods on the <b>concrete mock type</b> <code>T</code> (<code>IDatabase</code>).</li><li><b><code>mockDb.As<IDatabaseAsync>().Setup(...)</code></b> — sets up methods on a specific <b>interface</b> that <code>T</code> implements. Required when production code holds the reference as <code>IDatabaseAsync</code>, not <code>IDatabase</code>.</li></ul><p><b>If you use the wrong one:</b></p><pre><code>// Production code holds: IDatabaseAsync _db // This setup NEVER fires — wrong interface face: mockDb.Setup(x =&gt; x.KeyDeleteAsync(...)).ReturnsAsync(true);  // Correct: mockDb.As&lt;IDatabaseAsync&gt;().Setup(x =&gt; x.KeyDeleteAsync(...)).ReturnsAsync(true);</code></pre><p>Moq finds no matching setup on the interface face → returns the <b>default value</b> → your setup silently never fires → test passes but the mock was never called.</p>
S04.10.Medium. You want to test that <code>OrderService.CreateOrderAsync</code> decrements stock correctly. You use EF Core InMemory database. You seed two products with stock=10. After creating an order with qty=2 for product 1, you assert <code>product1.QuantityInStock == 8</code>. The test passes. Is this test reliable? What can go wrong?	<p><b>Not fully reliable.</b> The test passes but gives false confidence because:</p><ul><li>EF Core InMemory <b>does not enforce concurrency tokens</b> (<code>[ConcurrencyCheck]</code>, <code>[Timestamp]</code>). Two simultaneous decrements won't throw <code>DbUpdateConcurrencyException</code> — both succeed, giving wrong stock.</li><li>InMemory <b>doesn't enforce foreign keys, unique constraints, or CHECK constraints</b> — the test passes with data that would be rejected by a real database.</li><li>The test might be testing <b>the same <code>DbContext</code> instance</b> used to seed, so the entity is already tracked and the assertion reads from the change tracker, not from a real "re-fetched" state.</li></ul><p>Use <b>SQLite in-process</b> for tests that care about constraints or concurrency.</p>
S04.11.Medium. What is mutation testing? How does it differ from code coverage? If you have 100% code coverage, does that mean your tests are good? Give an example where 100% coverage still misses a bug.	<ul><li><b>Code coverage</b> — measures which <b>lines/branches were executed</b>. Does not check whether assertions would catch a bug.</li><li><b>Mutation testing</b> — introduces small code changes (mutations) and verifies your tests fail:</li><li><code>></code> changed to <code>>=</code></li><li><code>return true</code> changed to <code>return false</code></li><li><code>+</code> changed to <code>-</code></li></ul><p>If a test still passes after a mutation → the test is <b>weak</b>.</p><p><b>100% coverage ≠ good tests:</b></p><pre><code>// Covers every line but catches no bug: [Fact] public void GetTotal_ReturnsNotNull() {     Assert.NotNull(order.GetTotal()); // ✅ executes the line, ❌ catches nothing }  // Mutation: changes '-' to '+' in GetTotal() → test still passes</code></pre>
S04.12.Medium. You have a Moq <code>Setup(...).ReturnsAsync(false)</code> but no <code>Verify</code>. You delete the production method. The test still passes. Why?	<p><code>Setup</code> only configures what the mock <i>returns if called</i> — it's not an assertion. If the production method is deleted, the mock method is never called, the <code>Setup</code> never fires, and no error occurs. Without a <code>Verify</code>, there's nothing to fail.</p><p>The test was testing the wrong thing: it was asserting the output of a method that may or may not have used the mock, not that the mock was actually called.</p><p><b>Fix:</b> add <code>mockService.Verify(x => x.TheMethod(...), Times.Once)</code> after the Act.</p>
S04.13.Medium. <code>Order.GetTotal()</code> returns <code>-5</code> when discount is <code>60</code>, subtotal is <code>50</code>, shipping is <code>5</code>. You don't know if this is intentional. What do you do? Write the test.	<p>Don't silently accept it — surface the question. Write the test to document current behavior, then raise the design question with the team.</p><pre><code>[Fact] public void GetTotal_WhenDiscountExceedsSubtotal_ReturnsNegativeTotal() {     // Current behavior: no floor. Negative totals are possible.     // TODO: confirm with business — should this be clamped to 0?     var order = new Order     {         Subtotal = 50m,         Discount = 60m,         DeliveryMethod = new DeliveryMethod { Price = 5m }     };     Assert.Equal(-5m, order.GetTotal()); }</code></pre><p>If the business confirms it's wrong, update the implementation and the test together.</p>
S04.14.Medium. What coverage target do you set for each layer (Core, Application, Infrastructure, API controllers) and why?	<ul><li><b>Core (entities, value objects, domain logic)</b> — 90–100%. Pure C#, no I/O, easy to test. This is where your most valuable logic lives.</li><li><b>Application (services, use cases)</b> — 80–90%. Complex orchestration; mock dependencies. Cover all branches and error paths.</li><li><b>Infrastructure (EF repositories, Redis, Stripe)</b> — 40–60%. Integration tests replace unit tests here; InMemory/SQLite tests for EF, skip Redis/Stripe unless critical.</li><li><b>API controllers</b> — 30–50%. Thin mapping layer; if service layer is covered, controllers add little value. Test only routing, model validation, and status codes.</li></ul><p>Never chase a single global coverage number — it averages out the meaningful (Core) with the meaningless (migrations, DTOs).</p>
S04.15.Hard. Design a test for optimistic concurrency. You need to prove that two simultaneous orders for the last item result in exactly one success and one failure. You cannot use <code>Thread.Sleep</code>. How do you simulate concurrency in a unit test? What database provider do you use? Why can't you use InMemory?	<p>Use <b>SQLite in-process</b> (not InMemory — it doesn't enforce concurrency tokens). Simulate concurrency with two separate <code>DbContext</code> instances reading the same product, then saving in sequence — the second save should throw <code>DbUpdateConcurrencyException</code>.</p><p>You don't need real threading. The race condition is captured by the optimistic lock: both contexts read stock=1, first saves stock=0, second tries to save stock=0 with original=1 but the DB already shows 0 → mismatch → exception.</p>
S04.16.Hard. A colleague writes this test and says "It validates the happy path":  ``<code>csharp [Fact] public async Task SetCart_ReturnsCart() {     _mockDb.Setup(x => x.StringSetAsync(         It.IsAny<RedisKey>(),         It.IsAny<RedisValue>(),         It.IsAny<TimeSpan?>(),         It.IsAny<When>(),         It.IsAny<CommandFlags>()))         .ReturnsAsync(true);      var result = await _cartService.SetCartAsync(new ShoppingCart { Id = "cart1" });      result.Should().NotBeNull();     result!.Id.Should().Be("cart1"); } </code>`<code>  Delete </code>SetCartAsync` from the service. Does the test break? Why or why not? Write the corrected test.	<ul><li><b>Yes — the test breaks with a compile error</b> because it directly calls <code>_cartService.SetCartAsync(...)</code> which no longer exists. The test can't compile, let alone run.</li><li><b>However, the test is still weak</b>: there is no <code>Verify</code> confirming <code>StringSetAsync</code> was actually called. If <code>SetCartAsync</code> returns the cart without calling Redis at all, the test passes — the Setup's absence is invisible.</li></ul><p><b>The corrected test</b> adds a <code>Verify</code> on the Redis call and pins the exact cart ID in the key argument.</p>
S04.17.Hard. Your test suite has 128 tests. 126 pass, 2 fail intermittently (sometimes pass, sometimes fail on CI). These are called "flaky tests." Name five common causes of flaky tests and how to fix each.	<li><b>Shared mutable state</b> — tests pollute a static field or singleton. Fix: reset state in <code>[SetUp]</code>/<code>Dispose</code>, use fresh instances per test.</li><li><b>Time-dependent assertions</b> — <code>DateTime.Now</code> changes between runs or across timezones. Fix: inject <code>TimeProvider</code> and freeze time in tests.</li><li><b>Race conditions in async tests</b> — <code>Task.Run</code> + no proper await. Fix: always <code>await</code> in tests; use <code>Task.WhenAll</code> for true parallel.</li><li><b>Test ordering dependency</b> — test B relies on state created by test A. Fix: each test must arrange its own state independently.</li><li><b>External resource unavailability</b> — CI has no network, no Redis, no real DB. Fix: mock external calls or use containers (<code>Testcontainers</code>).</li>
S04.18.Hard. You need to test <code>PaymentService</code> but it calls <code>new PaymentIntentService()</code> directly — no DI seam. You can't modify the production code (it's a third-party SDK pattern). What are your options? Compare at least three approaches with trade-offs.	<li><b>Wrapper interface</b> — create <code>IStripePaymentIntentService</code> wrapping <code>PaymentIntentService</code>; inject the interface. Best option if you <i>can</i> add a seam — clean, testable.</li><li><b>Integration test only</b> — don't unit-test; write an integration test against the Stripe test API. Honest but slow and requires network.</li><li><b>Extract and override</b> — extract the <code>new PaymentIntentService()</code> call into a <code>protected virtual</code> method; subclass in tests to inject a fake. Works without changing the public API.</li><li><b>Functional seam (delegate)</b> — pass a <code>Func<PaymentIntentService></code> factory; tests inject a factory returning a fake.</li><p>If you truly cannot touch the production code, option 2 (integration test) is the most honest.</p>
S04.19.Hard. A colleague's PR has a <code>CartService_Tests.cs</code> failure-path test with no <code>Verify</code>. You run the tests — they pass. You delete <code>SetCartAsync</code> entirely — they still pass. Walk through why and what you'd say in code review.	<p><b>Why the test still passes:</b></p><p>The test asserts on the return value of <code>SetCartAsync</code> — but without a <code>Verify</code>, there is no assertion that any Redis mock was called. If the failure path never reaches the Redis layer (e.g. throws early, or returns null before calling the service), the <code>Setup</code> never fires and no error occurs.</p><p>The test is a <b>false safety net</b> — it passes whether or not the production code calls Redis.</p><p><b>In code review — what to say:</b></p><p>> "Quick question: what code change would break this test? I think it might pass even if we remove the Redis call entirely — there's no <code>Verify</code> on <code>StringSetAsync</code>. Adding <code>_mockDb.Verify(x => x.StringSetAsync(...), Times.Never)</code> for the failure path would make it a real safety net."</p><p>Ask, don't accuse. Offer the fix.</p>
S04.20.Hard. You need to test that calling <code>CreateOrderAsync</code> twice with the same cart returns the existing order, not a duplicate. Your first approach: seed an order into EF InMemory, then call the service once. The test fails — a new order is created. Why does manual seeding fail? What's the correct approach?	<p><b>Why seeding fails:</b></p><p>Seeded data was inserted into a <b>different <code>DbContext</code> instance</b> than the one the service uses. Each <code>DbContext</code> in EF InMemory gets a fresh, isolated store by default — seeded data in one context is <b>not visible</b> to a service using another context.</p><p><b>Fix — Option 1:</b> use the same <code>DbContext</code> instance for seeding AND the service:</p><pre><code>context.Orders.Add(existingOrder); await context.SaveChangesAsync(); var service = new OrderService(context); // same instance</code></pre><p><b>Fix — Option 2:</b> use a named InMemory database (both contexts share the same store):</p><pre><code>var options = new DbContextOptionsBuilder&lt;AppDbContext&gt;()     .UseInMemoryDatabase("TestDb") // named → shared across instances     .Options;</code></pre><p><b>Note:</b> even with these fixes, InMemory still doesn't enforce unique constraints or concurrency tokens. Switch to SQLite in-process when you need those.</p>
