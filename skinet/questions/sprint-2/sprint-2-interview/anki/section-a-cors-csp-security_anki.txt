S01.01.Easy. What is CORS? Why does it exist? What happens if you don't configure CORS on your API?	<p><b>CORS</b> (Cross-Origin Resource Sharing) is a <b>browser security mechanism</b> that blocks JavaScript from making requests to a different origin (different domain, port, or protocol) than the page that loaded it.</p><ul><li><b>Why it exists:</b> enforces the <b>Same-Origin Policy</b> — prevents a malicious site from silently calling your bank's API using the victim's cookies.</li><li><b>Without CORS configured:</b> every cross-origin AJAX call from your Angular app is blocked by the browser <b>before it reaches your server</b>. The .NET API never sees the request — the browser rejects it client-side.</li></ul>
S01.02.Easy. What's the difference between CORS and CSP?	<ul><li><b>CORS</b> — controls which <i>external origins</i> can call your API. Server-side configuration that tells browsers "I accept requests from these origins." Protects your <b>API</b> from being called by unauthorized sites.</li><li><b>CSP</b> (Content Security Policy) — controls what resources your <b>own web page</b> is allowed to load: scripts, styles, images, fonts, frames. Protects your <b>frontend</b> from injected malicious content (XSS).</li></ul><p>Both are enforced by the browser, but they solve completely different problems.</p>
S01.03.Easy. What does <code>X-Frame-Options: DENY</code> protect against?	<p>Protects against <b>clickjacking</b> — the page is embedded in an invisible <code><iframe></code> on a malicious site; the attacker overlays a fake UI on top, tricking users into clicking real buttons (e.g. "Confirm Transfer").</p><ul><li><b><code>DENY</code></b> — never render this page inside any frame, on any site (including same-origin).</li><li><b><code>SAMEORIGIN</code></b> — allow framing only from the same origin.</li></ul><p>Modern replacement: <code>Content-Security-Policy: frame-ancestors 'none'</code> (more flexible, same effect).</p>
S01.04.Easy. What does <code>X-Content-Type-Options: nosniff</code> do?	<p>Prevents <b>MIME type sniffing</b> — some browsers "guess" the content type by inspecting response bytes, ignoring the declared <code>Content-Type</code>.</p><p><b>Attack without <code>nosniff</code>:</b> attacker uploads an HTML file with <code>Content-Type: image/png</code>. Browser sniffs the bytes, detects HTML, and executes it as a script → XSS.</p><p><b>With <code>nosniff</code>:</b> browser strictly trusts the declared <code>Content-Type</code> and refuses to execute content that doesn't match. Required on all responses serving user-uploaded content.</p>
S01.05.Medium. Your Angular app works on <code>localhost:4200</code> but after deploying to Azure, API calls fail silently. No errors in the .NET logs. What's wrong?	<p>The deployed origin (e.g. <code>https://myapp.azurestaticapps.net</code>) is <b>not in the .NET CORS allowed origins list</b> — only <code>localhost</code> was added during development.</p><p><b>What happens:</b></p><li>Browser sends preflight or request with <code>Origin: https://myapp.azurestaticapps.net</code>.</li><li>Server responds <b>without</b> <code>Access-Control-Allow-Origin</code>.</li><li>Browser blocks JavaScript from reading the response — client-side rejection.</li><li>.NET logs show nothing (or a 200 Angular never sees) because the blocking is in the browser, not the server.</li><p><b>Fix:</b> add the production origin to your CORS policy and redeploy.</p>
S01.06.Medium. What is a preflight request? When does the browser send one? What headers does it include? What must the server respond with for the preflight to succeed?	<p>A preflight is an automatic <code>OPTIONS</code> request the browser sends before a "non-simple" cross-origin request. It asks the server: "Will you accept this kind of request?" The server must respond with the right <code>Access-Control-Allow-*</code> headers. Only if the preflight succeeds does the browser send the real request.</p><ul><li><b>Triggers</b> — any request with a custom header (<code>Authorization</code>, <code>Content-Type: application/json</code>), or a method other than GET/POST/HEAD.</li><li><b>Preflight request headers</b> — <code>Origin</code>, <code>Access-Control-Request-Method</code>, <code>Access-Control-Request-Headers</code></li><li><b>Required server response</b> — <code>Access-Control-Allow-Origin</code>, <code>Access-Control-Allow-Methods</code>, <code>Access-Control-Allow-Headers</code> (and optionally <code>Access-Control-Max-Age</code>)</li></ul>
S01.07.Medium. You add <code>Content-Security-Policy: default-src 'self'</code> to your API. Your Angular app's Material components break. The console shows CSP violation errors for inline styles. Explain why and give two solutions with different security trade-offs.	<p>Angular Material injects <code><style></code> tags directly into the DOM at runtime via JavaScript. CSP <code>default-src 'self'</code> covers <code>style-src</code>, which by default blocks all inline styles. The browser sees these dynamically injected <code><style></code> tags and blocks them.</p><p><b>Solution 1 — <code>'unsafe-inline'</code></b> (weaker): <code>style-src 'self' 'unsafe-inline'</code> — allows all inline styles everywhere. Easy to implement but defeats much of the XSS protection CSP provides for styles.</p><p><b>Solution 2 — Nonce</b> (stronger): Server generates a random nonce per request, adds it to the CSP header and to every <code><style></code> tag. Only <code><style></code> tags with the matching nonce are allowed. Harder to implement with Angular but provides real protection.</p>
S01.08.Medium. Why does <code>AllowCredentials()</code> in CORS matter for cookie auth? What happens if you remove it?	<p>By default, browsers <b>strip cookies and <code>Authorization</code> headers</b> from cross-origin requests.</p><p><b><code>AllowCredentials()</code> + <code>withCredentials: true</code> on the client</b> tells the browser: include cookies and auth headers in this cross-origin request.</p><p><b>Without it:</b></p><ul><li>Browser sends the request without the session cookie.</li><li>Server sees an unauthenticated request → returns 401.</li><li>Cookie-based auth <b>never works</b> across origins.</li></ul><p><b>Constraint:</b> <code>AllowCredentials()</code> requires a specific origin — you <b>cannot</b> combine it with <code>AllowAnyOrigin()</code> (wildcard <code>*</code>).</p>
S01.09.Medium. Compare these two CORS configurations. Which is insecure and why?  ``<code>csharp // Config A builder.Services.AddCors(o => o.AddPolicy("default", p =>     p.WithOrigins("https://myapp.com")      .AllowAnyHeader()      .AllowCredentials()));  // Config B builder.Services.AddCors(o => o.AddPolicy("default", p =>     p.AllowAnyOrigin()      .AllowAnyHeader()      .AllowCredentials())); </code>``	<ul><li><b>Config B is both insecure AND invalid at runtime.</b></li><li>.NET throws <code>InvalidOperationException</code> at startup: <code>AllowAnyOrigin()</code> + <code>AllowCredentials()</code> is forbidden by the CORS spec.</li><li>Conceptually: any website on the internet could make credentialed requests with the user's cookies, calling your API as the authenticated user.</li><li><b>Config A is correct</b> — credentials are only accepted from a specific, trusted origin.</li></ul><pre><code>// ✅ Correct p.WithOrigins("https://myapp.com").AllowAnyHeader().AllowCredentials()  // ❌ Runtime exception + security hole p.AllowAnyOrigin().AllowAnyHeader().AllowCredentials()</code></pre>
S01.10.Medium. Write the <code>Permissions-Policy</code> header value that disables accelerometer, camera, and microphone. What does each API do and why disable them?	<pre><code>Permissions-Policy: accelerometer=(), camera=(), microphone=()</code></pre><p>An empty <code>()</code> means "denied for all origins including the page itself."</p><ul><li><b>Accelerometer</b>: reads device motion/orientation. Could fingerprint users or detect keystrokes via vibration analysis.</li><li><b>Camera</b>: access to device camera. Dangerous if XSS runs — silently captures video.</li><li><b>Microphone</b>: access to device microphone. Same risk as camera — silent audio capture via injected script.</li></ul><p>Disabling APIs your app doesn't use is defence-in-depth: even if XSS occurs, the attacker can't use these hardware APIs.</p>
S01.11.Hard. Design a CSP policy for an e-commerce app that uses: Angular (self-hosted), Angular Material (inline styles), Stripe Elements (loads from <code>js.stripe.com</code>), Google Fonts, and your own API. Write the full CSP header value. Explain each directive.	<pre><code>Content-Security-Policy:   default-src 'self';   script-src 'self' https://js.stripe.com;   style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;   font-src 'self' https://fonts.gstatic.com;   img-src 'self' data: https:;   frame-src https://js.stripe.com;   connect-src 'self' https://api.stripe.com;   object-src 'none';   base-uri 'self';   form-action 'self';</code></pre>
S01.12.Hard. You're auditing a codebase and find:  ``<code>csharp app.UseCors(x => x     .SetIsOriginAllowed(_ => true)     .AllowAnyMethod()     .AllowAnyHeader()     .AllowCredentials()); </code>`<code>  Explain exactly what </code>SetIsOriginAllowed(_ => true)` does, why it's dangerous, and write a realistic attack scenario. Then write the corrected version.	<p><code>SetIsOriginAllowed(_ => true)</code> is a lambda that always returns <code>true</code> — every origin on the internet is allowed.</p><p><b>Why it's more dangerous than <code>AllowAnyOrigin()</code>:</b></p><ul><li><code>AllowAnyOrigin()</code> sets <code>*</code> — .NET <b>blocks</b> combining it with <code>AllowCredentials()</code>.</li><li><code>SetIsOriginAllowed(_ => true)</code> <b>bypasses that guard</b> by echoing the exact origin the browser sent, while still passing .NET's own validation check. Combined with <code>AllowCredentials()</code>, any website can make fully authenticated credentialed requests using the victim's cookies.</li></ul><p><b>Attack scenario:</b> attacker hosts <code>evil.com</code>. Victim is logged in to <code>myapp.com</code>. <code>evil.com</code> script calls <code>POST /api/orders</code> — browser sends the victim's cookie, your API accepts it, order placed.</p><p><b>Corrected version:</b></p><pre><code>app.UseCors(x =&gt; x     .WithOrigins("https://myapp.com", "https://staging.myapp.com")     .AllowAnyMethod()     .AllowAnyHeader()     .AllowCredentials());</code></pre>
S01.13.Hard. Angular Material uses <code>ViewEncapsulation.None</code> which injects global <code><style></code> tags. Why does this conflict with CSP? What would a production-grade solution look like? Explain the nonce-based approach.	<p><code>ViewEncapsulation.None</code> — Angular doesn't scope component styles; instead it dumps them as plain <code><style></code> tags into <code><head></code> <b>at runtime via JavaScript</b>.</p><p><b>The conflict:</b> CSP's <code>style-src</code> (or <code>default-src</code> fallback) blocks inline styles unless <code>'unsafe-inline'</code>, a hash, or a nonce is present. Static hashes can't work because Angular injects styles dynamically — the original HTML has no <code><style></code> tags to hash.</p><p><b>Production-grade solution — nonce-based approach:</b></p><li>Server generates a <b>random nonce</b> per request (e.g. <code>crypto.randomBytes(16).toString('base64')</code>).</li><li>Nonce is embedded in the CSP header: <code>style-src 'nonce-abc123'</code>.</li><li>Angular's <b>SSR renderer</b> attaches the nonce to each <code><style></code> tag it outputs.</li><li>Browser only executes <code><style></code> tags whose nonce matches the header.</li><p><b>Requires Angular SSR</b> — cannot be done with client-side-only rendering because there's no server to generate the nonce per request.</p>
S01.14.Hard. You use <code>SameSite=Strict</code> for CSRF protection. A colleague argues you should add anti-forgery tokens (<code>[ValidateAntiForgeryToken]</code>) too. Are they right? When would one not be enough?	<p>Your colleague is right. <code>SameSite=Strict</code> is strong but has gaps:</p><ul><li>It's a <b>client-side browser feature</b> — doesn't protect if the browser is old, the cookie predates the <code>SameSite</code> attribute, or the attacker controls a subdomain of your domain.</li><li>A subdomain cookie scope (<code>Domain=.example.com</code>) means a compromised subdomain can still send your cookie on same-site requests.</li></ul><p><b>Anti-forgery tokens (synchronizer token pattern)</b> are <b>server-side and independent of cookie attributes</b> — they provide defence-in-depth. The server generates a unique token per session, embeds it in the form/header, and rejects requests where it's missing or wrong.</p><p><b>Rule:</b> neither alone covers all attack scenarios — use both for sensitive state-changing operations.</p>
