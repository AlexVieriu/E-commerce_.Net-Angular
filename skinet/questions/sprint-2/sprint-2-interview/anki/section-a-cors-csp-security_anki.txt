S01.01.Easy. What is CORS? Why does it exist? What happens if you don't configure CORS on your API?	<p>CORS (Cross-Origin Resource Sharing) is a browser security mechanism that blocks JavaScript from making requests to a different origin (different domain, port, or protocol) than the page that loaded it. It exists to enforce the <b>Same-Origin Policy</b> — preventing a malicious site from silently calling your bank's API using the victim's cookies. Without CORS configured on your API, every cross-origin AJAX call from your Angular app will be blocked by the browser before it even reaches your server. The .NET API never sees the request.</p>
S01.02.Easy. What's the difference between CORS and CSP?	<ul><li><b>CORS</b> — controls which <i>external origins</i> can call your API. Server-side configuration that tells browsers "I accept requests from these origins." Protects your <b>API</b> from being called by unauthorized sites.</li><li><b>CSP</b> (Content Security Policy) — controls what resources your <b>own web page</b> is allowed to load: scripts, styles, images, fonts, frames. Protects your <b>frontend</b> from injected malicious content (XSS).</li></ul><p>Both are enforced by the browser, but they solve completely different problems.</p>
S01.03.Easy. What does <code>X-Frame-Options: DENY</code> protect against?	<p>It protects against <b>clickjacking</b> — an attack where your page is embedded inside an invisible <code><iframe></code> on a malicious site. The attacker overlays their UI on top of your page, tricking users into clicking your buttons (e.g., "Confirm Transfer") while thinking they're clicking something else. <code>DENY</code> tells the browser: never render this page inside any frame, anywhere.</p>
S01.04.Easy. What does <code>X-Content-Type-Options: nosniff</code> do?	<p>It prevents <b>MIME type sniffing</b>. Without it, browsers try to "guess" the content type of a response by inspecting its bytes, even if the server declared a different <code>Content-Type</code>. An attacker could upload an HTML file disguised as an image (<code>Content-Type: image/png</code>), and without <code>nosniff</code>, some browsers would execute it as HTML/script. With <code>nosniff</code>, the browser strictly trusts the declared <code>Content-Type</code> and refuses to execute mismatched content.</p>
S01.05.Medium. Your Angular app works on <code>localhost:4200</code> but after deploying to Azure, API calls fail silently. No errors in the .NET logs. What's wrong?	<p>The deployed origin (<code>https://myapp.azurestaticapps.net</code> or similar) isn't in your .NET CORS allowed origins list. Your localhost origin was allowed during development. The browser sends the preflight/request, the server responds without the correct <code>Access-Control-Allow-Origin</code> header, and the browser blocks the JS from reading the response. Because the browser blocks it client-side before processing the actual response body, your .NET logs may show nothing (for simple requests) or a 200 response that Angular never sees.</p>
S01.06.Medium. What is a preflight request? When does the browser send one? What headers does it include? What must the server respond with for the preflight to succeed?	<p>A preflight is an automatic <code>OPTIONS</code> request the browser sends before a "non-simple" cross-origin request. It asks the server: "Will you accept this kind of request?" The server must respond with the right <code>Access-Control-Allow-*</code> headers. Only if the preflight succeeds does the browser send the real request.</p><ul><li><b>Triggers</b> — any request with a custom header (<code>Authorization</code>, <code>Content-Type: application/json</code>), or a method other than GET/POST/HEAD.</li><li><b>Preflight request headers</b> — <code>Origin</code>, <code>Access-Control-Request-Method</code>, <code>Access-Control-Request-Headers</code></li><li><b>Required server response</b> — <code>Access-Control-Allow-Origin</code>, <code>Access-Control-Allow-Methods</code>, <code>Access-Control-Allow-Headers</code> (and optionally <code>Access-Control-Max-Age</code>)</li></ul>
S01.07.Medium. You add <code>Content-Security-Policy: default-src 'self'</code> to your API. Your Angular app's Material components break. The console shows CSP violation errors for inline styles. Explain why and give two solutions with different security trade-offs.	<p>Angular Material injects <code><style></code> tags directly into the DOM at runtime via JavaScript. CSP <code>default-src 'self'</code> covers <code>style-src</code>, which by default blocks all inline styles. The browser sees these dynamically injected <code><style></code> tags and blocks them.</p><p><b>Solution 1 — <code>'unsafe-inline'</code></b> (weaker): <code>style-src 'self' 'unsafe-inline'</code> — allows all inline styles everywhere. Easy to implement but defeats much of the XSS protection CSP provides for styles.</p><p><b>Solution 2 — Nonce</b> (stronger): Server generates a random nonce per request, adds it to the CSP header and to every <code><style></code> tag. Only <code><style></code> tags with the matching nonce are allowed. Harder to implement with Angular but provides real protection.</p>
S01.08.Medium. Why does <code>AllowCredentials()</code> in CORS matter for cookie auth? What happens if you remove it?	<p>By default, browsers strip cookies and <code>Authorization</code> headers from cross-origin requests. <code>AllowCredentials()</code> on the server, combined with <code>withCredentials: true</code> on the client, tells the browser: "include cookies and auth headers in this cross-origin request." Without it, your cookie-based auth never works across origins — the browser sends the request without the session cookie, the server sees an unauthenticated request, and returns 401.</p>
S01.09.Medium. Compare these two CORS configurations. Which is insecure and why?  ``<code>csharp // Config A builder.Services.AddCors(o => o.AddPolicy("default", p =>     p.WithOrigins("https://myapp.com")      .AllowAnyHeader()      .AllowCredentials()));  // Config B builder.Services.AddCors(o => o.AddPolicy("default", p =>     p.AllowAnyOrigin()      .AllowAnyHeader()      .AllowCredentials())); </code>``	<ul><li><b>Config B is both insecure AND invalid at runtime.</b> .NET throws an <code>InvalidOperationException</code> when you combine <code>AllowAnyOrigin()</code> with <code>AllowCredentials()</code> — the CORS spec explicitly forbids it. Conceptually it's also dangerous: it would allow any website on the internet to make credentialed requests using the user's cookies, enabling attacker-controlled sites to call your API as the authenticated user.</li><li><b>Config A is correct</b> — credentials are only accepted from a specific, trusted origin.</li></ul>
S01.10.Medium. Write the <code>Permissions-Policy</code> header value that disables accelerometer, camera, and microphone. What does each API do and why disable them?	<pre><code>Permissions-Policy: accelerometer=(), camera=(), microphone=()</code></pre><p>An empty <code>()</code> means "denied for all origins including the page itself."</p><ul><li><b>Accelerometer</b>: reads device motion/orientation. Could fingerprint users or detect keystrokes via vibration analysis.</li><li><b>Camera</b>: access to device camera. Dangerous if XSS runs — silently captures video.</li><li><b>Microphone</b>: access to device microphone. Same risk as camera — silent audio capture via injected script.</li></ul><p>Disabling APIs your app doesn't use is defence-in-depth: even if XSS occurs, the attacker can't use these hardware APIs.</p>
S01.11.Hard. Design a CSP policy for an e-commerce app that uses: Angular (self-hosted), Angular Material (inline styles), Stripe Elements (loads from <code>js.stripe.com</code>), Google Fonts, and your own API. Write the full CSP header value. Explain each directive.	<pre><code>Content-Security-Policy:   default-src 'self';   script-src 'self' https://js.stripe.com;   style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;   font-src 'self' https://fonts.gstatic.com;   img-src 'self' data: https:;   frame-src https://js.stripe.com;   connect-src 'self' https://api.stripe.com;   object-src 'none';   base-uri 'self';   form-action 'self';</code></pre>
S01.12.Hard. You're auditing a codebase and find:  ``<code>csharp app.UseCors(x => x     .SetIsOriginAllowed(_ => true)     .AllowAnyMethod()     .AllowAnyHeader()     .AllowCredentials()); </code>`<code>  Explain exactly what </code>SetIsOriginAllowed(_ => true)` does, why it's dangerous, and write a realistic attack scenario. Then write the corrected version.	<p><code>SetIsOriginAllowed(_ => true)</code> is a lambda that receives any origin string and always returns <code>true</code> — meaning every origin on the internet is allowed. Unlike <code>AllowAnyOrigin()</code> (which sets <code><i></code> and is blocked from combining with <code>AllowCredentials()</code> by .NET), <code>SetIsOriginAllowed</code> bypasses that guard by setting the origin to the </i>exact value sent by the browser*, while still passing .NET's validation. Combined with <code>AllowCredentials()</code>, it means any website can make fully authenticated cross-origin requests to your API using the victim's cookies.</p>
S01.13.Hard. Angular Material uses <code>ViewEncapsulation.None</code> which injects global <code><style></code> tags. Why does this conflict with CSP? What would a production-grade solution look like? Explain the nonce-based approach.	<p><code>ViewEncapsulation.None</code> means Angular doesn't scope component styles — instead it dumps them as plain <code><style></code> tags into the document's <code><head></code> at runtime, injected by JavaScript. CSP's <code>style-src</code> directive (or <code>default-src</code> fallback) blocks inline styles unless <code>'unsafe-inline'</code>, a hash, or a nonce is present. Since Angular injects these styles dynamically via JS (not in the original HTML), static hashes don't work. A production-grade solution uses <b>Angular SSR with nonces</b>: the server generates a fresh nonce per request, embeds it in the CSP header, and Angular's server-side renderer attaches it to each <code><style></code> tag it outputs.</p>
S01.14.Hard. You use <code>SameSite=Strict</code> for CSRF protection. A colleague argues you should add anti-forgery tokens (<code>[ValidateAntiForgeryToken]</code>) too. Are they right? When would one not be enough?	<p>Your colleague is right. <code>SameSite=Strict</code> is strong but has gaps:</p><ul><li>it's a client-side browser feature — doesn't work if the cookie predates the SameSite attribute, the user's browser is old, or the attacker controls a subdomain</li></ul><p>Anti-forgery tokens (synchronizer token pattern) are server-side and independent of cookie attributes — they provide defence-in-depth. Neither alone covers all attack scenarios.</p>
