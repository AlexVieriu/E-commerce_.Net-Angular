# G1 — [EASY][HIGH] What are the 3 properties of a good unit test?
# ────────────────────────────────────────────────────────────────────────────

A test that still passes when the code is gone is untested wishful thinking.</li><li><b>It fails for the right reason</b> — the assertion is the thing you care about, not a side effect. If the assertion is <code class="c">result.Should().NotBeNull()</code> but the test was meant to verify a side-effect on Redis, the assertion is wrong.</li><li><b>It tests behaviour, not implementation</b> — if you refactor the code without changing behaviour, the test shouldn't break. Tests coupled to implementation are maintenance burden.</li></ol></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"The test should pass." The point of a test is not to pass — it's to <b>fail reliably when the code is broken</b>.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning that property #1 is best verified by <b>mutation testing</b> — tools like Stryker intentionally break the code and check if any test fails. Tests that don't detect the mutation are "dead weight."</p></div></div>

# G2 — [EASY][HIGH] What does mock.Verify(...) do that mock.Setup(...) doesn't?
# ────────────────────────────────────────────────────────────────────────────
<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><ul><li><code class="c">Setup</code> — <b>conditional</b>: "if this method is called with these args, return this value." Silent if never called.</li><li><code class="c">Verify</code> — <b>assertion</b>: "this method was called with these args exactly N times." Fails if not called.</li></ul><p>Without <code class="c">Verify</code>, a mock setup that never matches returns the default (<code class="c">null</code> for objects, <code class="c">false</code> for bool, <code class="c">0</code> for int) and the test silently proves nothing.</p><pre class="p"><code>mock.Setup(x =&gt; x.Save(It.IsAny&lt;Cart&gt;())).ReturnsAsync(true);<br>// Code never calls Save → mock returns default (false)<br>// Test assertion on return value fails, but for the wrong reason<br><br>mock.Verify(x =&gt; x.Save(It.IsAny&lt;Cart&gt;()), Times.Once);<br>// If code never called Save → Verify throws → test fails with clear message</code></pre></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"Setup is for mocking, Verify is for verifying." Tautology. You need to show the silent-default failure mode.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning <code class="c">Mock.VerifyAll()</code> / strict mocks (<code class="c">MockBehavior.Strict</code>) as alternatives — strict mocks fail if ANY unconfigured method is called. More rigorous but more fragile. Favour explicit <code class="c">Verify</code> for clarity.</p></div></div>

# G3 — [MEDIUM][HIGH] Why does this test pass but prove nothing? Explain step by step.
# ────────────────────────────────────────────────────────────────────────────
<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><p><b>Step by step:</b></p><ol><li>The <code class="c">Setup</code> targets the <b>OLD</b> <code class="c">StringSetAsync</code> overload: <code class="c">(key, value, TimeSpan?, When, CommandFlags)</code>. Since StackExchange.Redis 2.6+, the production code calls the NEW overload: <code class="c">(key, value, Expiration, ValueCondition, CommandFlags)</code>.</li></ol><ol><li>The types differ: <code class="c">TimeSpan?</code> vs <code class="c">Expiration</code>, <code class="c">When</code> vs <code class="c">ValueCondition</code>. Moq's matcher sees different signatures → <b>the setup never matches</b>.</li></ol><ol><li>When the production code calls the real overload, Moq has no matching setup → returns the <b>default value</b> (<code class="c">false</code> for <code class="c">bool</code>).</li></ol><ol><li><code class="c">SetCartAsync</code> sees <code class="c">false</code> → returns null → test assertion <code class="c">result.Should().BeNull()</code> passes.</li></ol><ol><li>The test passes for the WRONG reason: <b>not because the setup simulated a failed save, but because the unmatched setup returned default(false)</b>.</li></ol><ol><li><b>Proof it's worthless:</b> delete the <code class="c">Setup</code> call entirely. Test still passes. The mock's default behaviour alone produces the assertion.</li></ol><ol><li><b>Proof it doesn't verify anything:</b> delete the entire <code class="c">SetCartAsync</code> implementation body (replace with <code class="c">return null;</code>). Test still passes.</li></ol><p><b>Fix — match the real overload AND add <code class="c">Verify</code>:</b></p><pre class="p"><code>mockDatabase.As&lt;IDatabaseAsync&gt;()<br>    .Setup(x =&gt; x.StringSetAsync(<br>        It.IsAny&lt;RedisKey&gt;(),<br>        It.IsAny&lt;RedisValue&gt;(),<br>        It.IsAny&lt;Expiration&gt;(),<br>        It.IsAny&lt;ValueCondition&gt;(),<br>        It.IsAny&lt;CommandFlags&gt;()))<br>    .ReturnsAsync(false);<br><br>var result = await cartService.SetCartAsync(shoppingCart);<br><br>result.Should().BeNull();<br><br>mockDatabase.As&lt;IDatabaseAsync&gt;()<br>    .Verify(x =&gt; x.StringSetAsync(<br>        It.IsAny&lt;RedisKey&gt;(),<br>        It.IsAny&lt;RedisValue&gt;(),<br>        It.IsAny&lt;Expiration&gt;(),<br>        It.IsAny&lt;ValueCondition&gt;(),<br>        It.IsAny&lt;CommandFlags&gt;()),<br>        Times.Once);</code></pre></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>Only spotting "no Verify." The overload mismatch is the root cause — Verify catches it but doesn't explain it.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning that upgrading a mocked library (StackExchange.Redis 2.5 → 2.6) silently broke this test — a common hidden cost of dependency updates. This argues for <b>explicit contract tests</b> against real Redis (Testcontainers) for the hot paths, not just mocked unit tests.</p></div></div>

# G4 — [MEDIUM][MEDIUM] Why do you need As<IDatabaseAsync>() when mocking StringSetAsync?
# ────────────────────────────────────────────────────────────────────────────
<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><p><code class="c">StringSetAsync</code> is an <b>explicit interface implementation</b> on <code class="c">StackExchange.Redis.IDatabase</code>. The method is declared on <code class="c">IDatabaseAsync</code> (parent interface) and implemented explicitly:</p><pre class="p"><code>public interface IDatabaseAsync { Task&lt;bool&gt; StringSetAsync(...); }<br>public interface IDatabase : IDatabaseAsync { /* inherits */ }<br><br>// In Redis: explicit interface implementation<br>Task&lt;bool&gt; IDatabaseAsync.StringSetAsync(...) { ... }</code></pre><p>When called through <code class="c">IDatabase</code>, the compiler routes the call to the <code class="c">IDatabaseAsync</code> vtable slot. Moq's setup on <code class="c">Mock&lt;IDatabase&gt;</code> targets the <code class="c">IDatabase</code> dispatch table, which doesn't have <code class="c">StringSetAsync</code> as a member (it's inherited and explicitly implemented elsewhere).</p><p><code class="c">mockDatabase.As&lt;IDatabaseAsync&gt;()</code> tells Moq: "treat the mock as its <code class="c">IDatabaseAsync</code> facet and set up on <i>that</i> dispatch table." Now the setup matches.</p></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"Because of inheritance." Inheritance alone doesn't cause this — most mocks work across interfaces. The explicit implementation is the specific cause.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning that explicit interface implementations are a <b>.NET-specific subtlety</b> — Java doesn't have them. A common trap for Java devs coming to C#. Mentioning this shows deep .NET idioms.</p></div></div>

# G5 — [MEDIUM][MEDIUM] It.IsAny<RedisKey>() vs It.Is<RedisKey>(k => k == "cart-1") — when to...
# ────────────────────────────────────────────────────────────────────────────
<style>.c{background:#3e4451;color:#56b6c2;padding:1px 6px;border-radius:4px;font-family:monospace;font-size:.88em}.p{background:#282c34;color:#abb2bf;padding:12px 16px;border-radius:6px;border-left:3px solid #61afef;font-family:monospace;font-size:13px;white-space:pre-wrap;word-break:break-word;margin:10px 0;display:block}.ac{font-family:system-ui,-apple-system,sans-serif;line-height:1.65;font-size:0.95em;text-align:left}.ac p{margin:.4em 0}.ac ul,.ac ol{margin:.4em 0;padding-left:1.6em}.ac li{margin:.35em 0}.ac li>p{margin:0}.ac b{color:#56b6c2}.ac li::marker{color:#61afef}.rf{border-left:3px solid #e06c75;background:#2a1f22;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.rf-label{color:#e06c75;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.gf{border-left:3px solid #98c379;background:#1b2b1e;padding:10px 14px;border-radius:0 6px 6px 0;margin:14px 0}.gf-label{color:#98c379;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}.af{border-left:3px solid #61afef;background:#1e2430;padding:10px 14px;border-radius:0 6px 6px 0;margin:0 0 14px}.af-label{color:#61afef;font-family:monospace;font-size:0.72em;font-weight:700;letter-spacing:0.08em;text-transform:uppercase;margin:0 0 6px}</style><div class="af"><p class="af-label">★ The 5% Answer</p><div class="ac"><ul><li><code class="c">It.IsAny&lt;T&gt;()</code> — "any value of type T." Use when the specific value doesn't matter to the test.</li><li><code class="c">It.Is&lt;T&gt;(predicate)</code> — "a value matching this predicate." Use when the test is specifically about the argument.</li></ul><p><b>Rule of thumb:</b></p><ul><li>Setup for the HAPPY path (return a value): use <code class="c">It.IsAny</code> — don't constrain more than needed.</li><li>Verify to assert the call site: use <code class="c">It.Is</code> with a specific value to prove "the right key was passed."</li></ul><p>Example:</p><pre class="p"><code>// Setup: don't care, any call returns the value<br>mock.Setup(x =&gt; x.Get(It.IsAny&lt;string&gt;())).ReturnsAsync(cart);<br><br>// Verify: proves the code called Get with the RIGHT key<br>mock.Verify(x =&gt; x.Get(It.Is&lt;string&gt;(k =&gt; k == "cart-1")), Times.Once);</code></pre><p><b>Over-specifying setups</b> (using <code class="c">It.Is</code> everywhere) makes tests brittle — any refactor that adds a new argument transformation breaks unrelated tests.</p></div></div><div class="rf"><p class="rf-label">🚩 Red Flag — shallow answer</p><div class="ac"><p>"Always use <code class="c">It.Is</code> for safety." Over-specified setups fail when the code changes in safe ways. You want just enough specificity.</p></div></div><div class="gf"><p class="gf-label">✓ Green Flag — pro insight</p><div class="ac"><p>Mentioning <code class="c">Moq.Protected</code> for protected members, and <code class="c">It.IsAny</code> combined with captured arguments via <code class="c">Callback&lt;...&gt;(...)</code> for advanced assertion — the interviewer sees you know Moq beyond the surface API.</p></div></div>

# G7 — [MEDIUM][MEDIUM] When is [ExcludeFromCodeCoverage] legitimate vs lazy?
# ────────────────────────────────────────────────────────────────────────────
