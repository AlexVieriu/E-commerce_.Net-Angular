S09.01.Hard. You're designing the checkout flow for an e-commerce app. Walk through every step from "user clicks Place Order" to "user sees confirmation." Include: client validation, API call, stock check, payment processing, order creation, stock decrement, cart cleanup, real-time notification, and error handling at each step. What happens if the payment succeeds but the order insert fails?	<p><b>Full flow:</b></p><li><b>Client validation</b> — Angular validates form (address filled, card element complete via Stripe Elements). If invalid, show inline errors. No API call.</li><li><b>Create/confirm PaymentIntent</b> — POST <code>/api/payments/create-intent</code> → server creates PaymentIntent with Stripe (uses SecretKey) → returns <code>clientSecret</code>. Angular calls <code>stripe.confirmPayment({ clientSecret })</code> → Stripe charges the card. If declined → show Stripe error, stop.</li><li><b>Wait for webhook</b> — Angular connects to SignalR hub and waits for <code>OrderCompleteNotification</code>. Spinner shown.</li><li><b>Stripe webhook fires</b> → POST <code>/api/payments/webhook</code>. Server verifies signature, extracts <code>paymentIntentId</code>.</li><li><b>Stock check</b> — <code>OrderService</code> loads cart, checks each product's <code>QuantityInStock >= cartItem.Quantity</code>. If not → throw <code>InsufficientStockException</code> → return 409 (but payment already charged — see below).</li><li><b>Order creation</b> — insert <code>Order</code> record with <code>PaymentIntentId</code>, buyer, items, delivery method.</li><li><b>Stock decrement</b> — <code>product.QuantityInStock -= qty</code> within same <code>SaveChangesAsync</code> (covered by optimistic concurrency).</li><li><b>Cart cleanup</b> — <code>DeleteCartAsync(cartId)</code> called after <code>SaveChangesAsync</code>. Best-effort; failure logged but not re-thrown.</li><li><b>SignalR notification</b> — server pushes <code>OrderCompleteNotification</code> to user's hub group. Angular hides spinner, shows confirmation.</li><p><b>If payment succeeds but order insert fails:</b></p><p>The money is charged but no order exists. This is a critical failure. The webhook should be idempotent — Stripe will retry the webhook. On retry: attempt order creation again. If it keeps failing: log a critical alert, trigger a Stripe refund automatically, email the user. Store failed webhook events in a dead-letter table for manual review.</p>
S09.02.Hard. Two users add the last item to their carts. Both click "Place Order" at the same time. Trace the exact execution path for both requests through: stock read, stock check, payment intent, <code>SaveChangesAsync</code> with <code>[ConcurrencyCheck]</code>, exception handling, and user notification. What does each user see?	<pre><code>t=0ms   User A &amp; B both have stock=1 in their carts  t=10ms  A: POST /api/payments/create-intent → PI_A created (idempotency key: cartA) t=10ms  B: POST /api/payments/create-intent → PI_B created (idempotency key: cartB)  t=50ms  A: stripe.confirmPayment(PI_A) → Stripe charges card A → "succeeded" t=50ms  B: stripe.confirmPayment(PI_B) → Stripe charges card B → "succeeded"         (Both payments succeed — Stripe doesn't know about stock)  t=100ms Webhook for PI_A fires → OrderService:         - reads product stock = 1         - stock check: 1 &gt;= 1 ✓         - decrement: stock → 0         - SaveChangesAsync succeeds (WHERE QuantityInStock = 1 → 1 row updated)         - Order A created, cart A deleted         - SignalR → User A sees: "Order confirmed!"  t=101ms Webhook for PI_B fires → OrderService:         - reads product stock = 0 (already decremented by A)         - stock check: 0 &gt;= 1 ✗ → InsufficientStockException         (OR if both read stock=1 simultaneously: SaveChangesAsync → DbUpdateConcurrencyException)         - Catch exception → issue Stripe refund for PI_B         - SignalR → User B sees: "Sorry, item sold out — full refund issued within 5-10 days"</code></pre><p><b>User A:</b> order confirmed, charged successfully.</p><p><b>User B:</b> payment refunded automatically, clear message explaining why.</p>
S09.03.Hard. Your app gets featured on Reddit and traffic spikes 50x. The database starts timing out. Your Redis cart store is fine. Walk through your scaling strategy: what do you scale first? What changes in architecture? When do you introduce caching, read replicas, CDN, and queue-based processing?	<p><b>Immediate (day 1):</b></p><li><b>Scale out the API horizontally</b> — run multiple instances behind a load balancer (Azure App Service scale-out, or Kubernetes replicas). This costs nothing in architecture changes — stateless API, Redis handles sessions.</li><li><b>Identify the bottleneck</b> — check slow query log, Application Insights, or Azure Monitor. Is it a missing index? A hot query? Fix the cheapest thing first.</li><li><b>Connection pooling</b> — ensure <code>DbContext</code> is registered as <code>Scoped</code> (not Singleton). Check connection pool size.</li><p><b>Short-term (week 1):</b></p><li><b>Add read replicas</b> — route all GET queries (product listing, search) to the replica. Writes stay on primary. This halves the primary DB load for read-heavy workloads.</li><li><b>Cache the product catalog</b> — product data changes rarely. Cache in Redis with a 5-minute TTL. 90% of traffic is "browse products" — hitting the DB for that is wasteful.</li><p><b>Medium-term (month 1):</b></p><li><b>CDN for static assets</b> — Angular build, images, product photos on Azure CDN. Removes all static file serving from the origin.</li><li><b>Move webhook processing to a queue</b> — Stripe webhooks → Azure Service Bus → worker service processes orders asynchronously. API responds to Stripe in 200ms, processing happens in background.</li><p><b>Longer-term (if needed):</b></p><li><b>CQRS / read models</b> — separate read and write databases. Write model is normalized EF Core; read model is denormalized for fast queries.</li>
S09.04.Hard. Design an order status tracking system. An order goes through: Pending -> PaymentReceived -> Processing -> Shipped -> Delivered. Each transition should: validate the transition is legal, record the timestamp, notify the buyer via SignalR, and send an email. Design the state machine, the notification system, and the audit trail. How do you prevent an order from going from "Pending" directly to "Delivered"?	<p><b>State machine — valid transitions:</b></p><pre><code>private static readonly Dictionary&lt;OrderStatus, OrderStatus[]&gt; ValidTransitions = new() {     [OrderStatus.Pending]         = [OrderStatus.PaymentReceived],     [OrderStatus.PaymentReceived] = [OrderStatus.Processing],     [OrderStatus.Processing]      = [OrderStatus.Shipped],     [OrderStatus.Shipped]         = [OrderStatus.Delivered],     [OrderStatus.Delivered]       = [], };</code></pre><p><b>Transition method on the Order entity:</b></p><pre><code>public void TransitionTo(OrderStatus newStatus) {     if (!ValidTransitions[Status].Contains(newStatus))         throw new InvalidOperationException(             $"Cannot transition from {Status} to {newStatus}");     Status = newStatus;     StatusUpdatedAt = DateTime.UtcNow; }</code></pre><p><b>Audit trail:</b></p><pre><code>public class OrderStatusHistory {     public int Id { get; set; }     public int OrderId { get; set; }     public OrderStatus FromStatus { get; set; }     public OrderStatus ToStatus { get; set; }     public DateTime Timestamp { get; set; }     public string ChangedBy { get; set; } // user or system }</code></pre><p><b>Notification:</b> after each <code>SaveChangesAsync</code>, publish <code>OrderStatusChangedEvent</code> → handled by two consumers: SignalR hub (real-time) + email queue (async).</p><p><b>Prevention of invalid transitions:</b> the dictionary acts as a whitelist. <code>Pending → Delivered</code> is not in <code>ValidTransitions[Pending]</code> → <code>Contains</code> returns false → <code>InvalidOperationException</code> thrown before any save.</p>
S09.05.Hard. Your e-commerce app grows to 1000 concurrent users. The optimistic concurrency approach means popular products get frequent <code>DbUpdateConcurrencyException</code> during flash sales. Design a better solution. Compare: retry with jitter, atomic SQL decrement, Redis-based stock reservation, and queue-based ordering.	<p>| Approach | Throughput | Complexity | Oversell risk | Best for |</p><p>|---|---|---|---|---|</p><p>| Retry with jitter | Low-medium | Low | None | Low contention |</p><p>| Atomic SQL decrement | High | Low | None | Medium contention |</p><p>| Redis reservation | Very high | Medium | None (if done right) | Flash sales |</p><p>| Queue-based | Unlimited (sequential) | High | None | Extreme load |</p><p><b>Retry with jitter:</b> on <code>DbUpdateConcurrencyException</code>, wait <code>Random(50-300ms)</code> and retry up to 3 times. Simple, no infrastructure change. Fails under sustained high load — retries pile up, DB overwhelmed.</p><p><b>Atomic SQL decrement:</b> <code>UPDATE Products SET Stock = Stock - @qty WHERE Id = @id AND Stock >= @qty</code>. One round-trip, no ORM overhead, rows-affected tells you success/fail. Best default upgrade from optimistic concurrency.</p><p><b>Redis reservation:</b> reserve stock in Redis (sub-millisecond), process orders asynchronously. Near-zero DB contention at checkout. Requires two-phase protocol (reserve in Redis + confirm in DB). Complex to keep in sync.</p><p><b>Queue-based:</b> all order requests go to a message queue. Single worker processes them sequentially — zero concurrency conflicts. Handles any throughput. Users wait in a "virtual queue." High infrastructure complexity.</p><p><b>Recommendation for this project:</b> implement atomic SQL decrement now (one-line change, huge improvement). Add Redis reservation when flash sales are planned.</p>
