S06.01.Medium. Draw the full Stripe payment flow from button click to order creation: ``<code> Browser → Stripe.js → Stripe API → Your API → OrderService → DB → Stripe webhook → SignalR → Angular </code>`` Include: what tokens are passed, where the SecretKey is used, what the webhook verifies.	<pre><code>1. Angular → POST /api/payments/create-intent    Your API uses SecretKey to call Stripe → creates PaymentIntent    Returns { clientSecret } to Angular  2. Angular → Stripe.js.confirmPayment({ clientSecret, payment_element })    Stripe.js sends card details directly to Stripe API (SecretKey never leaves server)    Stripe returns: { paymentIntent.status = "succeeded" }  3. Angular → GET /api/orders (or poll) — waits for order confirmation via SignalR  4. Stripe → POST /api/payments/webhook  (async, minutes later or seconds)    Header: Stripe-Signature (HMAC with WebhookSecret)    Your API: ConstructEvent(payload, signature, WebhookSecret) → verifies authenticity    Payload: { type: "payment_intent.succeeded", data.object.id: "pi_xxx" }  5. Your API → OrderService.CreateOrUpdateOrder(paymentIntentId)    Finds or creates Order by PaymentIntentId → saves to DB → deletes cart  6. Your API → SignalR Hub → pushes "OrderCompleteNotification" to client group  7. Angular hub listener fires → hides spinner → shows order confirmation</code></pre><p><b>Token summary:</b></p><ul><li><code>SecretKey</code> — server-side only, never in browser, used to call Stripe REST API</li><li><code>clientSecret</code> — returned to browser, used by Stripe.js to confirm the payment</li><li><code>Stripe-Signature</code> — HMAC header on webhook; verified with <code>WebhookSecret</code> to prove Stripe sent it</li></ul>
S06.02.Medium. Two webhook callbacks arrive for the same <code>PaymentIntentId</code>. How do you prevent duplicate orders?	<p><b>Idempotency via unique constraint on <code>PaymentIntentId</code>.</b></p><p>Before creating an order, check if one already exists for that <code>PaymentIntentId</code>. If it does, return early (or update status if needed) instead of inserting a new row.</p><pre><code>public async Task&lt;Order?&gt; UpdateOrderPaymentSucceeded(string paymentIntentId) {     var order = await _context.Orders         .FirstOrDefaultAsync(o =&gt; o.PaymentIntentId == paymentIntentId);      if (order == null) return null; // no matching order — ignore      order.Status = OrderStatus.PaymentReceived;     await _context.SaveChangesAsync();     return order; }</code></pre><p>Add a unique index on <code>PaymentIntentId</code> in the DB schema as a belt-and-suspenders guard. Even if two concurrent webhook calls both pass the "does order exist?" check, the second <code>INSERT</code> will fail at the DB level with a unique constraint violation.</p>
S06.03.Medium. Why is the cart deleted AFTER the transaction commits, not inside it? What happens if cart deletion fails after commit?	<p><b>Cart is in Redis; the order is in SQL. You cannot put them in the same transaction — they're different systems.</b></p><p>The safe order is:</p><li><code>SaveChangesAsync()</code> — commits order to SQL (durable)</li><li><code>_cartService.DeleteCartAsync(cartId)</code> — removes from Redis (best-effort)</li><p>If you deleted the cart first and <code>SaveChangesAsync</code> then failed, the user loses their cart with no order created — unrecoverable data loss from the customer's perspective.</p><p><b>If cart deletion fails after commit:</b> the order exists in the DB (good). The Redis cart is orphaned but harmless — it will expire via TTL, or the user's next login/cart fetch can clean it up. An orphaned cart is far less damaging than a lost order.</p>
S06.04.Medium. What is <code>IdempotencyKey</code> in Stripe? Why do you use <code>cart.Id</code> as the key? What happens if two requests use the same key?	<p><code>IdempotencyKey</code> is a client-supplied string that tells Stripe: "if you've seen this key before, return the same result — don't create a new resource."</p><p>Using <code>cart.Id</code> means: if the user's browser retries the "create payment intent" call (network blip, double-click), Stripe returns the EXISTING PaymentIntent with the same <code>client_secret</code> — no second charge is created.</p><p><b>If two requests use the same key:</b></p><ul><li>Same endpoint + same key → Stripe returns the cached response (same PaymentIntent object)</li><li>Different endpoint + same key → Stripe returns 400 Idempotency error</li></ul><p>The key must be unique per cart, not per user session — if the user empties and refills their cart, a new cart ID generates a new PaymentIntent.</p>
S06.05.Hard. Your Angular app suddenly shows the checkout spinner forever. The payment succeeded (you see the charge in Stripe Dashboard). What's the debugging checklist? (Give at least 6 steps.)	<li><b>Stripe Dashboard → Webhooks → check delivery status.</b> Did the webhook fire? Did your endpoint return 200? If it shows "Failed" with a 500/timeout, the webhook never processed.</li><li><b>Check server logs for the webhook endpoint.</b> Did the signature verification (<code>ConstructEvent</code>) throw? Did the order creation succeed? Did <code>SaveChangesAsync</code> throw a concurrency exception?</li><li><b>Browser DevTools → Network tab → filter by WS.</b> Is the SignalR WebSocket connection established? Is it open at the time the webhook should fire?</li><li><b>Check SignalR hub group membership.</b> Did the Angular client call <code>HubConnection.invoke("JoinGroup", email)</code> BEFORE the webhook fired? If not, the notification was sent to a group with no members.</li><li><b>Check CORS for SignalR.</b> Does <code>app.UseCors(...)</code> allow the SignalR hub's origin and credentials (<code>AllowCredentials()</code>)?</li><li><b>Check <code>hubConnection.on("OrderCompleteNotification", ...)</code> registration.</b> Is the listener registered before calling <code>hubConnection.start()</code>? If registered after, the first notification is missed.</li><li><b>Stripe test mode timing.</b> In test mode, webhooks can fire in milliseconds — faster than Angular mounts the hub. Add a "join group then confirm payment" sequence to guarantee the listener is ready.</li><li><b>Check if the webhook is hitting the right environment.</b> Dev webhook pointing at localhost? Stripe CLI proxy (<code>stripe listen --forward-to localhost:5001/...</code>) needed for local testing.</li>
S06.06.Hard. <code>PaymentService</code> calls <code>new PaymentIntentService()</code> and <code>new RefundService()</code> directly — no DI seam. You want to unit test it. What are the three options, and which is right for this project?	<li><b>Wrapper interface</b> — create <code>IStripeService</code> wrapping <code>PaymentIntentService</code> and <code>RefundService</code>. Inject the interface. Mock it in tests. <b>Best option</b> — clean, testable, follows DI principles.</li><li><b>Protected virtual factory method</b> — extract <code>new PaymentIntentService()</code> into a <code>protected virtual</code> method. Subclass in tests to inject a fake. Works without changing the public API. Acceptable if you truly can't change the constructor.</li><li><b>Integration test against Stripe test API</b> — use real Stripe with <code>sk_test_...</code> keys. No mocks. Honest but slow, requires network, can be flaky, and leaks test keys unless handled carefully via environment variables.</li><p><b>Right for this project:</b> Option 1. We control the code, DI is already set up, and the Stripe SDK classes aren't sealed — wrapping them is trivial. Write the wrapper, register it in DI, mock the interface in unit tests.</p>
S06.07.Hard. Design a "stock reservation" system: when a user starts checkout, reserve their items for 15 minutes. If they don't complete, release the reservation. Design the data model, reserve/release flows, and the background job. How do you handle a reservation expiring exactly when checkout completes?	<p><b>Data model:</b></p><pre><code>public class StockReservation {     public int Id { get; set; }     public int ProductId { get; set; }     public string UserId { get; set; }     public string CartId { get; set; }     public int Quantity { get; set; }     public DateTime ExpiresAt { get; set; }     public ReservationStatus Status { get; set; } // Active, Fulfilled, Released }</code></pre><p><b>Reserve flow:</b> on checkout start → insert reservation → decrement <code>AvailableStock</code> (separate from <code>QuantityInStock</code>) → if <code>AvailableStock < 0</code>, rollback and return 409.</p><p><b>Release flow:</b> background job polls every 1 minute → finds <code>Status=Active AND ExpiresAt < UtcNow</code> → restores <code>AvailableStock</code> → marks <code>Status=Released</code>.</p><p><b>Checkout completes at expiry moment:</b> use optimistic concurrency on the reservation. The checkout marks <code>Status=Fulfilled</code> before decrementing real stock. Background job skips <code>Status=Fulfilled</code> rows. If the background job releases first, checkout finds <code>AvailableStock=0</code>, detects no reservation → returns 409 (item gone).</p>
