S10.01.Easy. What is <code>@if</code> vs <code>*ngIf</code> in Angular 17+? Why did Angular add the new syntax?	<ul><li><b><code><i>ngIf</code></b> — structural directive, requires <code>NgIf</code> imported in <code>imports[]</code>, uses microsyntax (<code><div </i>ngIf="condition; else tmpl"></code>), requires a separate <code><ng-template #tmpl></code> for else.</li><li><b><code>@if</code></b> — built-in control flow (Angular 17+), no imports needed, supports <code>@else if</code> inline, compiles to more efficient code, easier to read.</li></ul><p>Angular added <code>@if</code> to: reduce import boilerplate, improve compile-time optimisation, enable better SSR streaming (templates can be deferred), and make templates more readable (looks like actual control flow, not magic attributes).</p><pre><code>&lt;!-- Old --&gt; &lt;div *ngIf="user; else loading"&gt;{{ user.name }}&lt;/div&gt; &lt;ng-template #loading&gt;&lt;p&gt;Loading...&lt;/p&gt;&lt;/ng-template&gt;  &lt;!-- New --&gt; @if (user) {   &lt;p&gt;{{ user.name }}&lt;/p&gt; } @else {   &lt;p&gt;Loading...&lt;/p&gt; }</code></pre>
S10.02.Easy. What does <code>inject()</code> function do in Angular? How is it different from constructor injection?	<p><code>inject()</code> is a function-based DI mechanism (Angular 14+) that retrieves a service from the DI container without requiring it to be a constructor parameter.</p><pre><code>// Constructor injection constructor(private router: Router) {}  // inject() — works anywhere in injection context readonly router = inject(Router);</code></pre><p><b>Differences:</b></p><ul><li>Works in field initializers, factory functions, functional guards/interceptors — not just constructors</li><li>Enables composable utility functions that inject services internally</li><li>Reduces constructor boilerplate in components with many dependencies</li><li>Limitation: must be called during construction (in an injection context — constructor body, field initializer, or <code>runInInjectionContext</code>)</li></ul>
S10.03.Easy. What does <code>takeUntilDestroyed()</code> do? Why is it important for preventing memory leaks?	<p><code>takeUntilDestroyed()</code> (Angular 16+) is an RxJS operator that automatically completes a subscription when the component/directive/service that contains it is destroyed.</p><pre><code>// Old — manual cleanup required export class MyComponent implements OnDestroy {   private destroy$ = new Subject&lt;void&gt;();    ngOnInit() {     this.data$.pipe(takeUntil(this.destroy$)).subscribe(...);   }   ngOnDestroy() { this.destroy$.next(); this.destroy$.complete(); } }  // New — zero boilerplate export class MyComponent {   constructor() {     this.data$.pipe(takeUntilDestroyed()).subscribe(...);   } }</code></pre><p><b>Why it prevents memory leaks:</b> when a component is destroyed but its subscriptions aren't cancelled, the observable keeps running and the callback keeps firing — even though the component is gone. This holds a reference to the component in memory (preventing GC) and can cause errors when the callback tries to update destroyed UI. <code>takeUntilDestroyed()</code> ensures cleanup is automatic and guaranteed.</p>
S10.04.Easy. What is the difference between <code>subscribe()</code> and the <code>async</code> pipe? Which one requires manual cleanup?	<ul><li><b><code>subscribe()</code></b> — manually subscribes to an observable in component code. You own the subscription lifecycle. Requires manual cleanup: call <code>unsubscribe()</code> in <code>ngOnDestroy</code>, or use <code>takeUntilDestroyed()</code>.</li><li><b><code>async</code> pipe</b> — used in templates (<code>{{ data$ | async }}</code>). Angular automatically subscribes when the component renders and unsubscribes when it destroys. Zero cleanup code.</li></ul><p><b><code>subscribe()</code> requires manual cleanup. <code>async</code> pipe does not.</b></p><pre><code>// subscribe() — must clean up subscription = this.data$.subscribe(d =&gt; this.data = d); ngOnDestroy() { this.subscription.unsubscribe(); }  // async pipe — automatic // Template: {{ data$ | async }} // No ngOnDestroy needed</code></pre><p>Use <code>async</code> pipe when you only need the value in the template. Use <code>subscribe()</code> when you need to react to the value in component logic (e.g. navigate, show a toast, set multiple properties).</p>
S10.05.Easy. What does <code>@defer</code> do in Angular? When would you use it?	<p><code>@defer</code> (Angular 17+) lazy-loads a block of content — including components, directives, and pipes — only when a specified trigger condition is met. The deferred block is not included in the initial bundle.</p><pre><code>@defer (on viewport) {   &lt;heavy-chart-component [data]="chartData" /&gt; } @loading {   &lt;p&gt;Loading chart...&lt;/p&gt; } @placeholder {   &lt;div class="chart-skeleton"&gt;&lt;/div&gt; } @error {   &lt;p&gt;Failed to load chart&lt;/p&gt; }</code></pre><p><b>When to use:</b></p><ul><li>Heavy components below the fold (charts, data grids, code editors)</li><li>Third-party widgets loaded only on interaction</li><li>Admin panels or rarely-accessed tabs</li><li>Any component that slows Initial Contentful Paint (ICP) and isn't needed immediately</li></ul>
S10.06.Easy. What is <code>ChangeDetectionStrategy.OnPush</code>? What are the three things that trigger change detection in an OnPush component?	<p><code>ChangeDetectionStrategy.OnPush</code> tells Angular: only check this component for changes in specific situations — don't check it on every event/timer in the app.</p><p><b>Three triggers that cause OnPush to check the component:</b></p><li><b>An <code>@Input()</code> reference changes</b> — a new object/array reference is passed in (mutation of the same object does NOT trigger)</li><li><b>An event fires from within the component</b> — user clicks a button, types in an input, any <code>(event)</code> binding inside this component's template</li><li><b>An Observable/Signal emits</b> — when using <code>async</code> pipe or signals (<code>.set()</code>, <code>.update()</code>) inside the component</li><p><b>Benefit:</b> Angular can skip entire subtrees of the component tree when checking for changes. Critical for performance in large apps with many components.</p>
