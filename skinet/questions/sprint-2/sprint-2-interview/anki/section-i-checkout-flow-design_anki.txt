Answer</p><div class="ac"><p><b>What is 3DS / SCA:</b></p><ul><li><b>3DS (3-D Secure)</b>: card-network protocol for authenticating the cardholder via a challenge (SMS code, banking app approval).</li><li><b>SCA (Strong Customer Authentication)</b>: the <b>EU regulation (PSD2)</b> that mandates 3DS on most card-not-present payments above ~€30 from EU customers. US/UK cards have similar pressure but are less uniformly enforced.</li></ul><p><b>Trigger:</b> Stripe applies 3DS based on card-issuer rules, amount, user location, and merchant history. The merchant doesn't choose — the issuer does.</p><p><b>Where it fires in the flow:</b></p><pre class="p"><code>Client: stripe.confirmPayment(clientSecret)<br>  ↓<br>Stripe sees issuer requires 3DS<br>  ↓<br>Stripe returns { status: "requires_action", next_action: { ... } }<br>  ↓<br>Stripe.js auto-opens 3DS challenge iframe/modal<br>  ↓<br>User completes challenge (SMS code, banking app tap)<br>  ↓<br>Stripe confirms → status: "succeeded" OR "requires_payment_method" (failed)</code></pre><p><b>Critical client-side change — the state machine has a new state:</b></p><pre class="p"><code>// Before 3DS (happy path only):<br>'idle' → 'confirming' → 'succeeded' | 'failed'<br><br>// With 3DS:<br>'idle' → 'confirming' → 'requires_action' → 'authenticating' → 'succeeded' | 'failed'</code></pre><p><b>What your code needs:</b></p><ol><li><b>Call <code class="c">stripe.confirmPayment</code> with <code class="c">redirect: "if_required"</code></b> — lets Stripe.js handle the challenge in-app without forcing a full page redirect.</li><li><b>Handle the intermediate status:</b> Stripe.js resolves the promise with <code class="c">paymentIntent.status = "requires_action"</code> if 3DS is pending. You must NOT treat this as failure — it's intermediate.</li><li><b>Await the second confirm:</b> Stripe.js returns control after the challenge. Your promise resolves with final status.</li><li><b>Timeout handling:</b> users abandon challenges. Default Stripe timeout is a few minutes; your UI should show "waiting for authentication" with a cancel option.</li></ol><p><b>Simplified code:</b></p><pre class="p"><code>const { paymentIntent, error } = await this.stripe.confirmPayment({<br>    elements: this.elements,<br>    confirmParams: { return_url: window.location.origin + '/checkout/success' },<br>    redirect: 'if_required'<br>});<br><br>if (error) {<br>    // Card declined, 3DS failed, etc.<br>    this.state.set('failed');<br>    return;<br>}<br><br>if (paymentIntent.status === 'succeeded') {<br>    this.state.set('succeeded');<br>    return;<br>}<br><br>if (paymentIntent.status === 'processing') {<br>    // Async method — bank approval in progress. SignalR will update via webhook.<br>    this.state.set('pending_webhook');<br>    return;<br>}</code></pre><p><b>Server-side — no extra work:</b></p><p>3DS happens entirely client-side between Stripe.js and the card issuer. Your webhook still fires on <code class="c">payment_intent.succeeded</code> or <code class="c">payment_intent.payment_failed</code>. No new endpoint, no new state in your DB beyond the existing status transitions.</p><p><b>What breaks if you ignore 3DS:</b></p><ul><li>EU customers hit a <code class="c">requires_action</code> status they don't understand → UI treats it as "failure" → user retries → Stripe refuses (same idempotency key, different params — see D9/K6 pattern).</li><li>Support tickets: "my payment worked in France but not on your site."
