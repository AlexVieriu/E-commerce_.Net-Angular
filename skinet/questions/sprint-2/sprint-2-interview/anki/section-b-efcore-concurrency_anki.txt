S02.01.Easy. What does <code>[ConcurrencyCheck]</code> do in EF Core?	<p><code>[ConcurrencyCheck]</code> marks a property as a <b>concurrency token</b>. When EF Core generates an <code>UPDATE</code> or <code>DELETE</code>, it adds the original value of that property to the <code>WHERE</code> clause. If no rows are matched (because another request already changed that value), EF throws <code>DbUpdateConcurrencyException</code>. It's optimistic concurrency — no locks taken, conflict detected at save time.</p>
S02.02.Easy. What are the three value states in <code>DbUpdateConcurrencyException</code>?	<p>When <code>DbUpdateConcurrencyException</code> is thrown, <code>exception.Entries</code> contains the conflicting entities. Each entry exposes three value sets:</p><ul><li><b><code>OriginalValues</code></b> — what you read from the DB at the start (the values EF used in the WHERE clause)</li><li><b><code>CurrentValues</code></b> — what you tried to write (your in-memory changes)</li><li><b><code>DatabaseValues</code></b> — what's actually in the DB right now (fetched on demand, requires a DB round-trip)</li></ul><p>These three sets let you implement merge strategies: who wins, how to combine, or whether to reject.</p>
S02.03.Easy. What is the difference between <code>FirstOrDefault()</code> and <code>SingleOrDefault()</code> in EF Core? When would you use each?	<ul><li><b><code>FirstOrDefault()</code></b> returns the first matching row. SQL uses <code>TOP 1</code> (SQL Server) or <code>LIMIT 1</code>. No error if multiple rows match.</li><li><b><code>SingleOrDefault()</code></b> asserts exactly one row matches. SQL uses <code>TOP 2</code> (fetches two rows to detect duplicates). Throws <code>InvalidOperationException</code> if more than one row matches.</li></ul><p>Use <code>FirstOrDefault()</code> for sorted lists (e.g., latest order). Use <code>SingleOrDefault()</code> when business logic requires uniqueness — looking up by email, username, or any column that <i>should</i> be unique.</p>
S02.04.Easy. What does <code>Include()</code> do in EF Core? What SQL does it generate?	<p><code>Include()</code> performs <b>eager loading</b> — loads a navigation property in the <b>same query</b> as the parent entity using a SQL <code>JOIN</code>.</p><p><b>Without <code>Include()</code>:</b></p><ul><li>In a <b>no-tracking</b> context: navigation properties are <code>null</code>.</li><li>In a <b>tracking</b> context: lazy-loaded on first access (requires proxy configuration).</li></ul><p><b>Generated SQL:</b> a <code>LEFT JOIN</code> between parent and related table — all data in one round-trip.</p><pre><code>var orders = await context.Orders     .Include(o =&gt; o.OrderItems)        // LEFT JOIN OrderItems     .Include(o =&gt; o.DeliveryMethod)    // LEFT JOIN DeliveryMethods     .ToListAsync();</code></pre>
S02.05.Easy. What is a migration in EF Core? What happens if you modify an entity but forget to create a migration?	<p>A migration is a C# class representing the <b>delta</b> between your current entity model and the last applied schema state.</p><ul><li><b><code>Up()</code></b> — applies the change (DDL SQL: <code>ALTER TABLE</code>, <code>CREATE INDEX</code>, etc.)</li><li><b><code>Down()</code></b> — reverses it (for rollback)</li></ul><p><b>If you forget to create a migration:</b></p><ul><li>The in-memory model is <b>out of sync</b> with the actual database schema.</li><li>Result: runtime <code>SqlException</code> on queries that reference the missing/changed column, or <b>silent data loss</b> if columns exist in the DB but are no longer in the model.</li></ul>
S02.06.Medium. You have <code>[ConcurrencyCheck]</code> on <code>QuantityInStock</code>. Two requests read <code>stock = 5</code> simultaneously. Request A saves <code>stock = 4</code>. Request B tries to save <code>stock = 4</code>. What SQL does EF generate for Request B? What happens? What exception is thrown?	<p>EF generates:</p><pre><code>UPDATE Products SET QuantityInStock = 4 WHERE Id = 7 AND QuantityInStock = 5</code></pre><p>By the time Request B executes this, the DB has <code>stock = 4</code> (Request A already changed it). The <code>WHERE</code> clause matches 0 rows. EF checks rows affected — expects 1, got 0 — and throws <code>DbUpdateConcurrencyException</code>. Request B's transaction is rolled back.</p>
S02.07.Medium. What does <code>AsNoTracking()</code> do? When should you use it? What breaks if you use <code>AsNoTracking()</code> and then try to update the entity? What happens to <code>[ConcurrencyCheck]</code> if you read with <code>AsNoTracking()</code>?	<ul><li><b>What it does</b> — tells EF not to add returned entities to the change tracker. Faster reads (no snapshot, no identity map lookup), less memory. Use for read-only queries (DTOs, projections, display data).</li><li><b>If you try to update</b> — EF treats the entity as detached and throws <code>InvalidOperationException</code> unless you manually <code>Attach()</code> it and set the state.</li><li><b><code>[ConcurrencyCheck]</code> + no-tracking</b> — EF can still read the token value, but doesn't store the original value in its tracking snapshot. If you Attach and update, you must manually set <code>OriginalValues</code> for the concurrency check to work correctly.</li></ul>
S02.08.Medium. Compare <code>[ConcurrencyCheck]</code> and <code>[Timestamp]</code> (rowversion). When would you choose each? Which databases support <code>[Timestamp]</code>? What SQL does each generate?	<ul><li><b><code>[ConcurrencyCheck]</code></b> — uses an existing business column as the token; original value included in the WHERE clause. Portable across all databases, but requires the column to change detectably with every update.</li><li><b><code>[Timestamp]</code></b> (or <code>[RowVersion]</code>) — dedicated <code>rowversion</code>/<code>timestamp</code> binary column the database automatically increments on every update. More reliable (DB handles it), smaller WHERE clause (8-byte binary). SQL Server native — requires workarounds for PostgreSQL (<code>xmin</code>) or SQLite.</li></ul>
S02.09.Medium. You call <code>SaveChangesAsync()</code> and it throws <code>DbUpdateConcurrencyException</code>. You want to implement "client wins" resolution. Write the code to reload the database values and force your changes through.	<p>"Client wins" means: your in-memory changes override whatever is in the DB. You reload the DB values into <code>OriginalValues</code> (so EF's WHERE clause matches the current DB state), keeping your <code>CurrentValues</code> intact, then retry <code>SaveChangesAsync()</code>.</p><pre><code>catch (DbUpdateConcurrencyException ex) {     foreach (var entry in ex.Entries)     {         var dbValues = await entry.GetDatabaseValuesAsync();         if (dbValues == null)             throw; // row was deleted — client wins has no meaning         entry.OriginalValues.SetValues(dbValues); // WHERE now uses current DB state     }     await context.SaveChangesAsync(); // retry — client's CurrentValues win }</code></pre>
S02.10.Medium. What is the N+1 query problem? Give an example with Orders and OrderItems. How does <code>Include()</code> fix it? What's the downside of over-using <code>Include()</code>?	<p><b>N+1:</b> 1 query fetches N parent entities, then N more queries (one per parent) load the related collection.</p><pre><code>-- Without Include: 101 queries for 100 orders SELECT * FROM Orders                              -- 1 query SELECT * FROM OrderItems WHERE OrderId = 1        -- ×100 more</code></pre><p><b><code>Include()</code> fix:</b> collapses into a single JOIN.</p><pre><code>SELECT Orders.*, OrderItems.* FROM Orders LEFT JOIN OrderItems ON Orders.Id = OrderItems.OrderId  -- 1 query</code></pre><p><b>Downside of over-using <code>Include()</code>:</b></p><ul><li>Over-fetches data you don't need.</li><li>Multiple collection includes create a <b>cartesian product</b> (rows multiply).</li><li>Use projections (<code>Select(o => new { o.Id, Items = o.OrderItems })</code>) when you only need a subset.</li></ul>
S02.11.Medium. What does this code do? Is there a performance problem?  ``<code>csharp var products = await context.Products.ToListAsync(); var expensive = products.Where(p => p.Price > 100).ToList(); </code>``	<p>Yes, there is a serious performance problem. <code>ToListAsync()</code> materializes the entire <code>Products</code> table into memory first — all rows, all columns. The <code>.Where(p => p.Price > 100)</code> then filters in-memory (LINQ to Objects), not in the database. If there are 100,000 products, all 100,000 rows are loaded over the network before the filter runs.</p><p>The fix: apply the filter before materializing.</p><pre><code>var expensive = await context.Products     .Where(p =&gt; p.Price &gt; 100)     .ToListAsync();</code></pre><p>This generates <code>SELECT * FROM Products WHERE Price > 100</code> — only matching rows transfer.</p>
S02.12.Medium. What is the Specification pattern? Why use it instead of putting query logic directly in the repository? What are the trade-offs?	<p>The Specification pattern encapsulates a <b>query's criteria</b> (filter, sort, pagination, includes) in a reusable object.</p><p><b>Without it — repository method explosion:</b></p><pre><code>GetActiveProductsByCategoryAsync(int categoryId) GetProductsWithLowStockAsync(int threshold) GetProductsByPriceRangeAsync(decimal min, decimal max) // grows endlessly with every new query variation</code></pre><p><b>With Specification:</b></p><pre><code>var spec = new ProductsWithFiltersSpec(categoryId, minPrice, maxPrice); var products = await repo.GetAsync(spec); // thin, generic repository</code></pre><p><b>Trade-offs:</b></p><ul><li>Keeps repositories thin and generic.</li><li>Makes queries composable and unit-testable in isolation.</li><li>Overkill for simple CRUD — adds abstraction overhead.</li></ul>
S02.13.Medium. What is the difference between <code>IQueryable<T></code> and <code>IEnumerable<T></code> when used with EF Core? If your repository returns <code>IEnumerable<Product></code> and the caller does <code>.Where(p => p.Price > 100)</code>, where does the filtering happen? Why is this a performance disaster?	<ul><li><b><code>IQueryable<T></code></b> — unexecuted query. EF translates further LINQ into SQL. Filtering happens <b>in the database</b>.</li><li><b><code>IEnumerable<T></code></b> — already materialized in memory. Further LINQ runs as C# iteration, <b>not SQL</b>.</li></ul><p><b>If repository returns <code>IEnumerable<Product></code>:</b></p><pre><code>// Repository — entire table loaded var products = repo.GetAll(); // SELECT * FROM Products (all rows transferred)  // Caller filters in C#, not SQL var cheap = products.Where(p =&gt; p.Price &lt; 10); // LINQ to Objects on all rows</code></pre><p>This is a <b>full-table scan in application memory over the network</b>. With 1 million rows, all 1 million are loaded before the filter runs.</p><p><b>Fix:</b> return <code>IQueryable<T></code> so callers can compose queries that EF translates to efficient SQL.</p>
S02.14.Hard. You have a Unit of Work with <code>BeginTransactionAsync()</code>. Inside the transaction, you decrement stock (with concurrency check), create an order, and insert a payment record. The stock update succeeds, the order insert succeeds, but a subsequent write to Redis fails with a network timeout. What happens to the SQL transaction? What happens to the stock? Design the correct rollback behavior.	<p><b>SQL and Redis are separate systems</b> — they can't participate in the same transaction.</p><p>The SQL transaction is independent of Redis. If you don't call <code>RollbackAsync()</code> explicitly after the Redis failure, SQL Server rolls back when the connection closes — but this is <b>non-deterministic</b>.</p><p><b>Correct design:</b></p><pre><code>await using var tx = await context.Database.BeginTransactionAsync(); try {     // stock decrement, order insert, payment record — all SQL     await context.SaveChangesAsync();     await tx.CommitAsync(); } catch {     await tx.RollbackAsync(); // explicit, synchronous rollback     throw; } // Redis call AFTER commit — best-effort await cartService.DeleteCartAsync(cartId);</code></pre><p><b>Source of truth:</b> the SQL database. Redis is a cache. Redis failures should be handled with retry/outbox, not rolled back in SQL.</p>
S02.15.Hard. EF Core's <code>InMemoryDatabase</code> doesn't enforce foreign keys, unique constraints, or concurrency tokens. You wrote a concurrency test using InMemory and it passed — but the same scenario fails in production. Explain why InMemory gave a false positive. What testing database should you use instead? What are the trade-offs?	<p><b>Why InMemory gave a false positive:</b></p><p><code>InMemoryDatabase</code> is a <b>simple dictionary</b> — not a SQL engine. It doesn't implement SQL semantics:</p><ul><li><b>Concurrency tokens</b> (<code>[ConcurrencyCheck]</code>, <code>[Timestamp]</code>) are <b>not enforced</b> — two saves both succeed silently.</li><li><b>No foreign keys, unique constraints, or CHECK constraints</b>.</li><li>No real WHERE clause evaluation — all saves go through.</li></ul><p><b>In production (SQL Server):</b> the <code>WHERE</code> clause with the original concurrency token fails to match → <code>DbUpdateConcurrencyException</code> fires correctly.</p><p><b>Use instead: SQLite in-process</b> — a real SQL engine that enforces constraints and concurrency tokens.</p><pre><code>var options = new DbContextOptionsBuilder&lt;AppDbContext&gt;()     .UseSqlite("DataSource=:memory:")     .Options; // Open and keep connection alive for the test — SQLite in-memory drops on disconnect</code></pre>
S02.16.Hard. You have 10 million products. Your query filters by <code>Category</code>, sorts by <code>Price</code>, and paginates (<code>Skip(100).Take(20)</code>). The query takes 3 seconds. Explain the execution plan, identify the bottleneck, and design the correct index. What's the difference between a covering index and a filtered index here?	<p>Without an index, SQL Server does a full table scan of 10 million rows, then sorts all matching rows by price in a temporary work area (sort spill), then offsets 100 and returns 20 — processing millions of rows for a 20-row result.</p><p>The bottleneck is the full scan + sort. The fix is a <b>composite index on <code>(CategoryId, Price)</code></b> — SQL Server can use it to seek directly to the category, already sorted by price, then skip 100 and take 20. A <b>covering index</b> adds all projected columns to the index itself (using <code>INCLUDE</code>) so no table lookup is needed. A <b>filtered index</b> is an index with a WHERE clause, useful if most queries target a specific subset (e.g., only active products).</p>
S02.17.Hard. Compare three EF Core concurrency strategies. For each, give the generated SQL and a use case: 1. No concurrency control (default) 2. <code>[ConcurrencyCheck]</code> on a specific column 3. <code>[Timestamp]</code> (rowversion)	<p><b>1. No concurrency control (last-write wins)</b></p><pre><code>UPDATE Products SET QuantityInStock = @p0 WHERE Id = @p1</code></pre><p>Use: non-critical data where overwrites are acceptable (e.g., user preference settings, display order).</p><p><b>2. <code>[ConcurrencyCheck]</code> on a column</b></p><pre><code>UPDATE Products SET QuantityInStock = @p0 WHERE Id = @p1 AND QuantityInStock = @p2</code></pre><p>Use: business-meaningful conflict detection on a specific field (stock, balance, version counter). Portable across all databases.</p><p><b>3. <code>[Timestamp]</code> / rowversion</b></p><pre><code>UPDATE Products SET Name = @p0 WHERE Id = @p1 AND RowVersion = @p2</code></pre><p>Use: general-purpose "was this entity touched by anyone" check. SQL Server native, detects all changes regardless of which column changed.</p>
S02.18.Hard. Design a retry strategy for <code>DbUpdateConcurrencyException</code> in a background order processor. Include: max retries, backoff, what to reload, when to give up. Write the code.	<pre><code>public async Task ProcessOrderAsync(OrderMessage message) {     const int maxRetries = 3;      for (int attempt = 1; attempt &lt;= maxRetries; attempt++)     {         try         {             var entity = await context.Orders.FindAsync(message.OrderId);             if (entity == null) return; // deleted — give up              entity.Status = OrderStatus.Processing;             await context.SaveChangesAsync();             return; // success         }         catch (DbUpdateConcurrencyException ex)         {             if (attempt == maxRetries)             {                 await deadLetterQueue.SendAsync(message); // give up                 return;             }              foreach (var entry in ex.Entries)             {                 var dbValues = await entry.GetDatabaseValuesAsync();                 if (dbValues == null) return; // row deleted — terminal failure                 entry.OriginalValues.SetValues(dbValues); // reload before retry             }              // Exponential backoff + jitter (avoids thundering herd)             var delay = TimeSpan.FromMilliseconds(100 * Math.Pow(2, attempt)                         + Random.Shared.Next(50));             await Task.Delay(delay);         }     } }</code></pre><p><b>Key principles:</b></p><ul><li><b>Reload <code>OriginalValues</code></b> before every retry — not just the first.</li><li><b>Exponential backoff + jitter</b> prevents all workers retrying simultaneously.</li><li><b>Null <code>DatabaseValues</code></b> = row was deleted → terminal failure, don't retry.</li><li><b>Dead-letter after max retries</b> — never retry indefinitely.</li></ul>
