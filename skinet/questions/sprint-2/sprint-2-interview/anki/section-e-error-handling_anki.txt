S05.01.Medium. You have a custom <code>ExceptionMiddleware</code> that catches exceptions and maps them to HTTP status codes. An <code>InvalidOperationException</code> maps to 400, everything else to 500. A developer throws <code>ArgumentNullException</code> from a service. What status code does the client get? Is this correct?	<p>The client gets <b>500</b>. <code>ArgumentNullException</code> inherits from <code>ArgumentException → SystemException → Exception</code>, not from <code>InvalidOperationException</code>. It falls through to the <code>catch (Exception)</code> block.</p><p>Is it correct? <b>It depends — but probably not.</b> <code>ArgumentNullException</code> usually indicates a programming mistake (null passed where it shouldn't be), which is an internal bug → 500 is defensible. But if the null came from invalid user input, 400 would be more appropriate. The real fix: throw a domain-specific exception (<code>InvalidOrderException</code>, <code>CartNotFoundException</code>) and map those deliberately rather than relying on .NET base types.</p>
S05.02.Medium. What does this middleware do? Trace the flow for a request that throws <code>InvalidOperationException("Insufficient stock")</code>.  ``<code>csharp public class ExceptionMiddleware {     private readonly RequestDelegate _next;      public ExceptionMiddleware(RequestDelegate next) => _next = next;      public async Task InvokeAsync(HttpContext context)     {         try         {             await _next(context);         }         catch (InvalidOperationException ex)         {             context.Response.StatusCode = 400;             await context.Response.WriteAsJsonAsync(new { error = ex.Message });         }         catch (Exception ex)         {             context.Response.StatusCode = 500;             await context.Response.WriteAsJsonAsync(new { error = "Internal server error" });         }     } } </code>``	<p><b>What it does:</b> wraps every subsequent middleware/controller in a try-catch. Maps <code>InvalidOperationException</code> to 400 Bad Request and everything else to 500.</p><p><b>Trace for <code>InvalidOperationException("Insufficient stock")</code>:</b></p><li>Request arrives → <code>InvokeAsync</code> called → <code>await _next(context)</code> hands control to the next middleware/controller</li><li>Controller calls <code>OrderService.CreateOrderAsync()</code></li><li><code>OrderService</code> detects stock = 0 → <code>throw new InvalidOperationException("Insufficient stock")</code></li><li>Exception bubbles up through the pipeline (controller → routing → middleware chain)</li><li><code>ExceptionMiddleware</code> catches it in <code>catch (InvalidOperationException ex)</code></li><li>Sets <code>StatusCode = 400</code></li><li>Writes <code>{"error":"Insufficient stock"}</code> as JSON to the response body</li><li>Client receives HTTP 400 with that JSON body</li>
S05.03.Medium. Trace the full error chain when a concurrency conflict happens during checkout: ``<code> [EF Core] → [OrderService] → [ExceptionMiddleware] → [HTTP Response] → [error.interceptor] → [user sees ???] </code>``	<li><b>EF Core</b>: <code>SaveChangesAsync()</code> sends <code>UPDATE Products SET Stock = 0 WHERE Id = 1 AND Stock = 1</code> → 0 rows affected → throws <code>DbUpdateConcurrencyException</code></li><li><b>OrderService</b>: does not catch <code>DbUpdateConcurrencyException</code> → exception propagates</li><li><b>ExceptionMiddleware</b>: not <code>InvalidOperationException</code> → falls to <code>catch (Exception)</code> → sets status 500, writes <code>{"error":"Internal server error"}</code></li><li><b>HTTP Response</b>: <code>500 Internal Server Error</code> with generic message</li><li><b>Angular error.interceptor</b>: catches 500 → shows generic snackbar: "Something went wrong"</li><li><b>User sees</b>: "Something went wrong" — no useful information, no way to know it was a stock conflict</li><p><b>What should happen instead</b>: catch <code>DbUpdateConcurrencyException</code> explicitly → return 409 Conflict → Angular shows "Item sold out — please refresh your cart"</p>
S05.04.Hard. Your exception middleware catches <code>DbUpdateConcurrencyException</code> and returns 409 Conflict. But in some cases, the caller should retry automatically (background job), and in others, the user should be told to refresh (API call). How do you design the error response to support both consumers?	<p>Return a structured error response with machine-readable fields — not just a message string.</p><pre><code>{   "type": "ConcurrencyConflict",   "title": "Resource was modified by another request",   "status": 409,   "retryable": true,   "retryAfterMs": 500,   "detail": "Product stock was updated concurrently. Reload and retry." }</code></pre><ul><li><b>Background job</b> reads <code>retryable: true</code> → waits <code>retryAfterMs</code> → retries automatically</li><li><b>Angular</b> reads <code>type: "ConcurrencyConflict"</code> → shows user-facing message with a "Refresh Cart" button</li><li>Both consumers use the same response, interpreted differently by their error handling logic</li></ul><p>Use <b>Problem Details (RFC 7807)</b> as the envelope — it's the standard, Angular's <code>HttpClient</code> handles it well, and ASP.NET Core has built-in support.</p>
