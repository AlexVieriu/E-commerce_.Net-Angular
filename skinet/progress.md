| Aug 20 | BUG-19 *(PR #75)* | **A coupon was validated once — when the customer typed it — and trusted forever after: by the order, by the charge, and by time.** Three cases proven live. Forging `amountOff` through `POST /api/cart` wrote **−$999.00** onto an order (#37). Forging `coupon.id` charged **$100 on a $185 order**, because `ApplyDiscountAsync` re-read Stripe by an id **the client controls** — a customer can replay a coupon id the shop handed them months earlier. Worst, a coupon applied before its campaign was retired still paid out: **$90 on a $180 order, with the order total and the charge agreeing**, so `PaymentMismatch` never fired and nothing anywhere flagged it. `POST /api/cart` writes the request body to Redis verbatim, so none of this needs stolen credentials, and the third case needs no attacker at all. Fix (spike 1a/2d/3b/4b): `OrderService` **and** `PaymentService` both re-derive from `cart.Coupon.PromotionCode`, the only field the customer typed. **By code, not by id, because it fails closed** — `promotion_codes list` with `Active = true` returns nothing for a retired campaign, while `coupons retrieve` ignores `valid` entirely; Stripe ties promo-code `active` to coupon validity, so expired and spent coupons are filtered for free. A lookup that resolves to nothing drops the coupon, nulls the intent and 409s on the price-change path — **dropping it matters**, or the retry hits the same 409 forever. **Two defects the fix would otherwise have introduced:** `Coupon.AmountOff` is `long?` cents, so `/ 100` truncated $5.50 to $5.00 — harmless while only the order record read it, a 50¢ overcharge the moment the charge did (`/ 100m`); and a blank `promotionCode` left Stripe's `Code` filter **unset**, which drops the filter rather than matching nothing, so `FirstOrDefault` would have returned an arbitrary live coupon. Client: `POST /api/payments` could not 409 before, so neither caller handled it — `afterNextRender` (page load) reported a misleading "Failed to load payment elements" over the real message, and `onStepChange` had no catch at all. **Two existing unit tests asserted the bug** — that the cart's `AmountOff` reaches `Order.Discount` — and were inverted. 159 tests green (was 152), including two API-layer tests that forge over real HTTP and were red before the fix.
