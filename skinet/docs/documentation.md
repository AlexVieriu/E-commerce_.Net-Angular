# How to Write Documentation

Read before creating or modifying any doc in `docs/`.

## File Naming & Location

- kebab-case: `error-handling.md`, `create-component.md`
- Action docs (step-by-step) → `docs/frontend/actions/` or `docs/backend/actions/`
- Concept docs (how it works) → `docs/frontend/` or `docs/backend/`
- Cross-cutting → `docs/` root

## Concept Doc Structure

```
# Title
One sentence: what this is and why it exists.

## How it works / [Subsections]
## Rules / Constraints
## Common Mistakes  ← only real ones caught in a session
```

## Action Doc Structure

```
# How to: [action]
## When to use this
## Steps
## Example
## Pitfalls  ← only real ones
```

## Style Rules

- Terse. One idea per sentence. Keep the docs as short as possible.
- Code blocks for anything typed or pasted.
- No filler: "It's important to note..." → just say the thing.
- No future tense: "will be used" → "used for".

## New File vs Update

Create new file: topic is independently searchable, or existing file would exceed 50 lines.
Update existing: correction, clarification, or new pitfall.

## /refine Workflow

Run at session end when something went wrong or a new pattern emerged:
1. `find docs/ -name "*.md" | sort`
2. Read `docs/documentation.md`.
3. Update or create docs for new knowledge. Do not touch `CLAUDE.md`.
